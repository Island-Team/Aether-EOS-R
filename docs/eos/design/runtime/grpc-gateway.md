# R02 Rust gRPC gateway design

[中文](../../../../docs_cn/eos/design/runtime/grpc-gateway_cn.md) · [Owner contract](../../interfaces/grpc.md#r02-frozen-rust-subset) · [First-use replay](../../develop/grpc-gateway.md) · [Machine cases](../../../../tests/fixtures/r02_grpc_gateway/README.md)

**Status:** The default Rust runtime implements the reviewed R02 gRPC Gateway and CapabilityService subset for the EGIA typed client, with R03 admission on the same Dispatcher. The published C++ service remains compatibility evidence. R06 stop-order and the final M3 qualification have separate gates in the [cross-repository task](../../../island/implementation-todo.md).

## Composition and publication

Add a bounded `tonic`/`prost` server module to `aether-runtime` and generate Rust stubs from the existing checked-in protobuf files at build time. Pin generator versions and vendor or verify Google API imports; compare a descriptor set against the committed wire identities so a build cannot silently renumber fields. The five public Rust executable names and crate version `0.2.0` stay unchanged. The public `eosd` launcher still selects `aether-runtime`. CLI configuration adds a loopback gRPC port (default 16200) and optional owner-permissioned Unix path; these are distinct from the current private JSON-control socket. Reject wildcard binds unless an explicit deployment policy authorizes them. A duplicate or unsafe socket path fails before readiness.

Startup order is profile/registry and generated-config pin verification → exclusive durable journal → adapters and direct MuJoCo child → immutable Gateway projection → gRPC bind → aggregate health `SERVING` and existing owner ready event. The current implementation fails incomplete admission before binding; no pre-admission listener or ready event is published. If a listener is bound earlier in a future implementation, health must remain `NOT_SERVING` and all required methods must fail `UNAVAILABLE`. The projection holds robot identity, device-to-path map, exact control binding map, resource registrations, capability map and `started_at`. It is constructed once before listener publication; there is no in-process graph refresh or `Arc` swap in R02. `GetStatus` overlays live health without mixing identity across generations. A rejected candidate cannot replace the current complete projection or publish half a catalog; live health may independently become degraded. Health changes to `NOT_SERVING` before rejecting writes and draining bounded streams. Keep the current private control socket and browser bridge as callers of the same runtime/Dispatcher, never as a second actuator implementation.

The current graph has robot `id`/`name` but no physical model field. Use literal `eos-runtime` for `RobotDescriptor.model` and a transparent runtime description; derive device class/part from admitted hardware node kind/placement, `id` and description from the admitted node, state and health from its adapter. Normalize only registered, verifiable type metadata. Readiness requires `Discover`, `ListResources`, `GetStatus`, and `ListCapabilities` to be mutually consistent and EGIA-parseable. In particular, `GetStatus` carries the same `robot_id` and `robot_name` as Discover plus nonempty `status`, `version`, and `started_at`; EGIA checks `robot_name` during rediscovery. The EGIA client makes health `Check("")`, those four calls, then `SkillService.ListSkills`; until a Rust skill catalog exists, respond to the latter with `UNAVAILABLE` so its optional-skill path works. Returning `UNIMPLEMENTED` there would make EGIA fail startup. Do not advertise ready in the absence of a required response or by fabricating a physical device, primitive, resource, or health sample.

The applied graph is read-only for this process; a new graph generation requires process restart, so the four startup discovery calls cannot straddle an in-process graph replacement. Live health and capability availability may change, but binding identity does not. If later hot refresh is added, it must publish a complete generation and provide a client retry boundary rather than returning a mixed set across separate RPCs.

The implemented Rust projection samples HAL health and lifecycle status on one background worker per admitted projection. The sampler holds at most one outstanding adapter probe, so a stalled owner socket cannot consume a tonic worker or multiply probes under read load. Projection construction waits at most 200 ms for an initial complete sample; missing samples are reported unavailable while the admitted identity and listener remain complete. Discovery, status, capability listing and camera precheck only read the retained sample. Each probe is dated before its health and status calls; a slow status response cannot refresh old health. A failed, missing or older-than-`min(profile stale_after_ms, 1000 ms)` sample degrades availability; a fresh probe restores it. A complete fresh projection supplies `eos-sample-age-ms` as the age of its oldest sampled node, while missing/stale data omit the age. ReadResource and CaptureFrames use the age of their retained product or frame. Shutdown prevents later sampler publication without waiting for a blocked adapter call. Dispatcher still rechecks physical admission before write release. The gRPC worker limits reserve distinct lanes for sixteen movements, one controlled stop and one emergency stop; saturation of movement workers cannot consume both stop lanes.

## Reads and bounded streams

Project only registered producers into `ListResources`; each URI is `robots/{name}/...` and each entry has `uri` and `class`. Current EOS hardware camera frames are captured on demand, not a world resource. The current graph has no world/detection/ASR producer, so those classes are absent until a verified producer exists. `ReadResource` checks the exact listed URI, schema, health, sample age ≤1 s and response cap before returning a Struct. `WatchResource` subscribes to changes on that same URI, emits `ResourceChanged{uri}` after a validated product, and never carries raw image bytes. A bounded per-watcher queue closes a lagging consumer with `RESOURCE_EXHAUSTED`. There is no cursor. EGIA automatically rediscovers on `NOT_FOUND` and `UNAVAILABLE`, then pairs a new watch with `ReadResource`. A slow-watch `RESOURCE_EXHAUSTED` escapes to its caller today; explicit caller retry/re-read is required unless a separately reviewed EGIA change extends the retry set. Do not equate a watch notification with a complete state sample.

`CaptureFrames` resolves the admitted camera device ID once, checks robot name and live health, and takes 1 or 2 distinct fresh frames from an EOS-owned two-frame cache. Encode with the existing `VisionFrame::encode_jpeg` boundary or validated JPEG preview; verify SOI/EOI, dimensions, timestamp and distinct capture identity. Response ≤16 MiB and JPEG ≤8 MiB each. Honor deadline and cancellation at both cache wait and encode; a timeout cannot leave an unbounded task. An unavailable cache yields `UNAVAILABLE`, and an overfull response yields `RESOURCE_EXHAUSTED`.

## Operations and durable identity

Construct movement capability descriptors only for supported registered primitive-to-`Movement` conversions and actual control edges. Stop descriptors are separate Dispatcher control-operation kinds with distinct target scopes. Each descriptor's canonical name, logical primitive/version/device, and `available` matches exactly one Discover binding. Do not advertise an operation merely because the graph mentions a wire; no graph edge executes a command. R02 can expose a deliberately smaller executable catalog than the historical C++ service. EGIA must still see a complete, internally consistent generation. R02 implements three distinct, journaled Dispatcher stop kinds: `MotionStop{device}`, `RobotStop`, and `SafetyEstop`; these safety bindings remain available when ordinary motion is unhealthy. They share operation ID and single-release rules with movement but have their own stop targets, phase transitions, terminal confirmation and acknowledgement results. The existing Rust Dispatcher currently supports base velocity/relative pose and manipulator joint/end-effector movement; it does not yet provide all historical v1 primitives or the full acknowledgement envelope.

The initial conversion table is `body_velocity → base.velocity@1.0.0`, `relative_pose → base.navigate@1.0.0` with **relative** reference only, `joint_positions → arm.movej@1.0.0` with **absolute** positions only, and `end_effector_pose → arm.movel@1.0.0` with **absolute** pose only. Each row is conditional on the matching profile mode, exact control edge, caller argument schema and numeric bounds. Do not announce absolute base navigation, relative arm targets or other historical primitives merely because EGIA knows their names. Runtime shutdown still calls `emergency_stop`; public stop capabilities use their own journaled command route. `MotionStop` stops exactly one admitted part and treats already stopped as success; `RobotStop` fans out controlled stop to all active actuators without engaging the emergency latch and reports bounded `result.parts`; `SafetyEstop` engages the configured emergency path and latch. Each returns `SUCCEEDED` only after the adapter or emergency path confirms its terminal stopped boundary. A known failed part makes the aggregate `FAILED`; an unconfirmed release makes it `OUTCOME_UNKNOWN`. Current `stop_node` and `emergency_stop` calls have no public command journal identity or sufficient terminal result on their own and cannot be exposed directly. Only bindings with a complete parameters schema, limits and dependency-health projection are announced.

Extend one durable Dispatcher journal record to retain canonical operation request signature, primitive/version, exact target/binding, admission state and enough typed acknowledgement data for post-restart `GetOperation`. Migrate/read old journal records safely, never guessing a missing primitive alias. A legacy record without enough metadata for a canonical acknowledgement remains sealed: `GetOperation` returns `DATA_LOSS` for that ID, startup reports degraded journal recovery, and it is never re-released. A new public operation record must always have enough metadata for a terminal acknowledgement. The current journal validates every `node_path` as a hardware path. R02 introduces a versioned, tagged `JournalTarget` with `Hardware{node_path}` (validated by the existing hardware-path rule) and `Robot{robot_id}` (validated against the admitted profile), plus a signed `OperationKind` of `Movement`, `MotionStop`, `RobotStop`, or `SafetyEstop`. Existing journal records decode only to `Hardware` on migration; no synthetic hardware path stands in for a robot-wide command. The signed request includes target and kind, and the journal forbids changing either after reservation. Robot-wide stop commands are not command-cancellable. On restart, an unfinished estop becomes `OUTCOME_UNKNOWN` without physical re-release; its persisted latch conservatively blocks new motion until an explicit authorized recovery path exists. `RobotStop` never sets that latch. Raise its current 120-byte ID ceiling to the public 128-byte limit. Validate the ID and request before reservation, compare duplicate signatures atomically, then durably persist Prepared and Releasing before one **logical** release. Movement and `MotionStop` release at most once to one adapter. `RobotStop` snapshots all admitted stop-capable hardware paths in canonical order before Prepared, persists that immutable list with the typed robot target, then makes at most one bounded stop call to each listed part under a separate durable movement inhibit that blocks new Dispatcher movement releases before Releasing and remains until verified completion or recovery. This inhibit is not the emergency latch. Each part is marked attempting before its call and its confirmed result is durably recorded afterward in the same journal record. `SafetyEstop` latches once and fans out through its own configured emergency path; it is also one logical release. A crash after partial fanout recovers the overall operation as `OUTCOME_UNKNOWN`, retaining only confirmed per-part results and marking all other parts unknown; neither completed nor unfinished parts are automatically called again for that ID. The admitted registry is limited to 64 stop-capable parts so the snapshot and terminal `result.parts` fit the bounded journal record. Each sanitized per-part reason is at most 256 bytes. Exceeding that registry bound prevents SERVING; a detected serialization overflow before release returns `RESOURCE_EXHAUSTED`, while overflow after possible release preserves `OUTCOME_UNKNOWN` and never retries. The gRPC adapter never holds a backend handle. Exact duplicate concurrent calls join the same record; conflicting reuse returns `ALREADY_EXISTS`. A journal write failure before release prevents actuation; after a possible release it records or reconstructs `OUTCOME_UNKNOWN` and never retries.

The same journal carries a synced RobotStop inhibit control state; it is set before Releasing, consulted at every movement release including concurrent Submit, and cleared durably only after every part in the immutable snapshot has a confirmed terminal stop and the current admitted stop-capable set is also confirmed. A known partial failure, uncertain release, crash, or failed clear write leaves it set. After restart, a partial-fanout record becomes `OUTCOME_UNKNOWN` and its original ID is query-only. A new, locally authorized RobotStop ID may recover by snapshotting the union of unresolved old targets and current admitted stop-capable nodes; it must confirm all before clearing the inhibit. If an old target cannot be verified, keep the inhibit until explicit authorized maintenance supplies equivalent per-target stop evidence. The emergency estop latch is separate and cannot be cleared by this recovery. With inhibit active, the complete gRPC surface may report health `SERVING` for safe discovery and stop recovery; `GetStatus.status` and robot health are `degraded`, movement capabilities are unavailable, and movement Submit rejects before release. Stop capabilities remain available. This describes process availability, not physical motion readiness.

Implement the release coordinator as a writer-preferred movement permit barrier owned by Dispatcher, separate from the journal mutex and emergency-stop latch. A movement acquires a permit before `begin_release`, checks inhibit/deadline under the barrier, writes `Releasing`, and holds the permit across the adapter call and its terminal or fenced physical boundary. RobotStop atomically closes new movement permits before persisting its inhibit; after the inhibit sync it waits for prior permits, including a movement paused after `Releasing` but before the adapter, to drain before fanout. No journal mutex is held while waiting or calling an adapter. A call returning `Accepted`, `Ambiguous` or an error after possible physical release leaves an unresolved generation even if its thread exits. The stop route must obtain adapter-proven quiescence or fence that generation at the physical write boundary before it can claim a terminal stop; otherwise it times out as `OUTCOME_UNKNOWN`, leaves inhibit durable, and never clears it using a single stopped observation. After a crash, reconstruct unresolved `Releasing` movements from the journal and establish an adapter epoch fence or equivalent proof before declaring movement available or clearing any RobotStop inhibit. The independent `SafetyEstop` path remains preemptive and does not wait on this barrier. A deterministic test pauses movement immediately after synced `Releasing` but before its adapter call, starts RobotStop, confirms no stop fanout or clear can overtake that movement, then releases it and confirms the ordered stop; a second branch leaves the movement ambiguous and checks inhibited unknown recovery.

Before Prepared, validate the maximum 64-target snapshot and reserve bounded result space using the 256-byte per-part reason cap; sanitize and truncate actual reasons on return. If serialization exceeds its bound before Releasing, return `RESOURCE_EXHAUSTED` with zero adapter calls and no inhibit transition. If a write or result serialization fails after a call may have occurred, preserve `OUTCOME_UNKNOWN` and the inhibit, never retry that ID, and retain only durably confirmed per-part results. Test a concurrent movement request during fanout, a pre-release injected overflow, and a post-possible-release injected overflow separately.

Translate `DispatchResult` to v2 Operation and canonical `primitive.ack` in one pure projection, including matching ID, primitive/version, accepted bit, status, sequence and bounded result. Do not invent `FAILED` or `TIMED_OUT` from undifferentiated movement outcomes; R02 stop commands have their own confirmed `FAILED` result and R03 may add distinguishable movement causes. `WatchOperation` sends the current record then at most one terminal update. A disconnected watch neither cancels nor retries the command; recovery is `GetOperation` with the same ID. `CancelOperation` uses Dispatcher cancellation and is command-targeted; it cannot stop a subsequent command on that device. The explicit stop capability and shutdown path handle motion clamping. The current synchronous Dispatcher may return terminal immediately; the watch contract still works for future pending adapters.

## Errors, limits and verification

Keep transport errors separate from terminal domain outcomes. The [owner contract](../../interfaces/grpc.md#r02-frozen-rust-subset) freezes the error map, deadline, frame and stream limits. Bound gRPC decode, protobuf Struct nesting, URI and ID length, per-method concurrency, queues and response bytes before spawning work. `x-request-id` is only log correlation. Redact arguments, images and environment from shared JSONL events. A drop in transport after Submit is uncertain at EGIA: the server must retain the command by ID for `GetOperation` and cannot infer it was not released.

The [cases](../../../../tests/fixtures/r02_grpc_gateway/cases.json) require fake-clock unit tests for freshness and deadlines; golden protobuf/EGIA-stub parity; a real Rust gRPC listener with the selected EGIA typed client; duplicate/concurrent/conflicting Submit across journal restart; lost response and watch reconnect; malformed schema and frame bounds; slow watcher and cancellation; partial discovery refresh; cold resource; backend loss; and shutdown health/stop ordering. Store complete format, Clippy, unit, integration and build output in `logs/test/<run-id>/`; record exact commands in the first-use guide. No performance claim is made before fixed-workload throughput, median and p99 are measured.
