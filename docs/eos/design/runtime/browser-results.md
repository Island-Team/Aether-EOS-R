# Browser primitive result routing

[中文](../../../../docs_cn/eos/design/runtime/browser-results_cn.md) · [Owner control contract](../../interfaces/control.md#r07-authorized-browser-result) · [Primitive binding](../../interfaces/primitive-bindings.md)

**R07 EOS and IsosUI scoped implementation is merged and qualified.** R03 already accepts `primitive_typed` from the loopback bridge and admits it through one Dispatcher route. R07 adds an authorized read for a command that is still `InProgress`, preserves active-revision checking, and proves the browser cannot reach a raw actuator or another caller's journal record. IsOS owns the saved and active graph revision and run-scoped grant; EOS owns the active binding, command journal and live result. The graph edge declares a binding and never executes a browser request.

The bridge validates Host, approved Origin, HTTP body size, exact operation and public fields before reading its private operator grant. It rewrites the public `result` operation to private `primitive_result`, attaches the grant only to that owner-socket request, and never returns or logs the grant. It never forwards public `result` unchanged; the managed runtime keeps rejecting the historical raw `result` operation. The runtime checks the admitted saved-byte revision and maps the grant to the operator role. Dispatcher adds a dedicated read-only lookup over one journal lock: it checks the current run, stored active revision and role, `Movement` kind, and `PrivateBridge` ingress stored with the admitted command before returning `DispatchResult`. The existing `gateway_operation_authorized` helper does not expose ingress and cannot alone prove a browser binding. Wrong run, role, kind, ingress, legacy identity and absent ID all receive the same opaque response. A new run rotates grants and makes the old result opaque even when its command ID remains in the durable journal. The owner contract defines the exact fields, response bounds and errors.

For `primitive_typed`, the HTTP bridge is also the private IPC serializer. JavaScript and Rust may render a finite payload number with different byte lengths. The bridge checks that the public declared length and its parsed payload are each within the 16 KiB bound, then writes the private `payload_length_bytes` from its own compact `serde_json` bytes. The public declaration is a bounded hint, while the private header is authoritative; the runtime still checks an exact private match. This prevents a valid browser command from failing only because a number such as `0.000001` is rendered as `1e-6` after the bridge parses it. A malformed or oversized public header returns fixed HTTP 400 `invalid typed request` before grant use; payload content and all admission identities remain unchanged.

The browser first compares IsOS saved and active revisions, obtains EOS monotonic time, inspects the active binding's one target and live health, and sends the bounded typed request. A local `sending` indicator ends only when the bridge returns a correlated command ID and EOS status. `InProgress` permits bounded follow-up reads while the same revision is active; `Completed`, `Failed`, `Cancelled`, `Rejected` and `OutcomeUnknown` are terminal display states, with `Failed` shown as an explicit terminal failure. A bridge outage, changed revision or stopped runtime leaves the result visibly unavailable, not completed. The UI's deployment Stop remains visible through IsOS; R06 supplies physical actuator stop proof before MuJoCo movement can be enabled. Vision continues on its read-only WebSocket with its independent active-revision check.

## Managed submission correction — target design

**Prerequisite behavior.** Before this async slice, the `primitive_typed` handler called synchronous `dispatch_managed_movement`: it inserts `Prepared` with `InProgress`, waits for the adapter, writes a terminal result and only then replies. The current CXX mock returns `Accepted`, which Dispatcher maps to terminal `OutcomeUnknown`; the normal browser can never receive `InProgress` from that path. A concurrent journal read can observe the transient state, but the UI correctly does not poll while its send is pending. The existing bridge, journal reader and UI stub tests establish authorized follow-up semantics; they do not satisfy the managed mock first-use `InProgress` clause. The [owner contract](../../interfaces/control.md#r07-managed-browser-submission) specifies the corrected acknowledgement and stop behavior without adding a wire operation.

Split the **managed browser** Dispatcher call into a synchronous `prepare` and one bounded execution worker. The preparation step parses and authorizes the same private envelope, checks the active binding and typed target, acquires one of eight browser movement slots, and writes `Prepared` durably with the existing full managed identity. Only after this write may the socket handler return the journal's correlated `InProgress` snapshot. A worker then uses the existing admission and release gate, including deadline and live-health checks, writes `Releasing` durably, invokes the adapter once, and writes the terminal result. Preparation and worker must share the current Dispatcher journal and release gate; a new executor must not own a second hardware handle. Keep the gRPC submission path synchronous and preserve the existing public `primitive_typed` and `result` bodies. A fast worker may win the race and yield a terminal initial reply; a controlled-delay mock fixture supplies a deterministic live `InProgress` replay without adding a graph setting or claiming a production latency guarantee.

Capacity and duplicate handling are part of the preparation transaction. Look up an existing ID and compare its durable signature and current authorization **before** requesting a slot; an exact duplicate returns the stored state and cannot enqueue or release again, while a mismatch is rejected. A new ID gets a slot before durable `Prepared`. If the lane is full, add a separate atomic terminal journal insert for the full signature and identity with `accepted:false` and `Rejected`: the existing `Journal::insert` cannot be used because its mandatory `Prepared` phase would make a crash before the next write recover as `Cancelled`. A failed atomic insert returns the fixed unavailable error and performs no release. A failed worker start after durable reservation rechecks the phase: it durably seals only `Prepared` as `Rejected`; a `Cancelled` written by Stop wins and remains unchanged. A failed necessary seal returns unavailable and inhibits movement. Worker slots stay occupied until durable terminal sealing or generation exit; a detached physical worker retains the old journal/adapter ownership and never enters the new generation. No queue or worker count may grow without bound. Do not hold the journal lock during an adapter call or wait for a slot. The safety-stop lane remains independent, and a full movement lane cannot delay Stop admission.

At shutdown, enter R06 `Closing`, register its stop writer and start the preemptive physical stop before waiting for an ordinary worker or journal lock. A worker checks `Closing` and its phase under the journal lock immediately before the durable `Prepared` → `Releasing` update. A worker that already passed this check keeps the generation/stop-epoch token captured before that update; it cannot fetch a new token after Stop. Once the physical stop is scheduled, seal a still-`Prepared` browser record as durable `Cancelled` under the same journal lock. Its worker rechecks the phase and cannot overwrite `Cancelled` or call the adapter. A `Releasing` worker participates in the physical stop attempt and cannot be treated as completed by timing alone. With confirmed MuJoCo dual-part proof, the advanced epoch rejects an old-token movement. With lost or unknown stop proof, the epoch may not advance and an in-flight worker may still reach the old child; R06 keeps the receipt unknown and terminates and reaps that child within its deadline. The worker remains bound to the old EOS process's adapter/session and captured generation, cannot retoken or reconnect to a replacement child, and the next IsOS run launches a distinct EOS process. Child cleanup is not a confirmed physical stop. Do not join an ordinary blocked worker on the safety path. A detached worker retains old journal/adapter ownership while live and cannot contaminate a replacement generation. Existing journal recovery seals `Prepared` as `Cancelled` and `Releasing` as `OutcomeUnknown`, inhibits movement for the uncertain case and never replays either. Terminal journal writes are single-writer transitions that cannot overwrite a stop or recovery terminal record. IsOS run rotation makes the old result opaque through the existing grant and run check.

After possible physical release, a failed terminal journal write is a distinct live fault. Latch movement inhibit; retain that worker slot until durable seal or generation exit, and retain old journal/adapter ownership while its physical call is live. The authorized result lookup returns the existing fixed `result unavailable` error for this ID rather than the durable but stale `InProgress` or an in-memory terminal guess; identical duplicate submission returns the same error and never schedules another worker. Once the call returns, a confirmed stop epoch fences it, or an unknown-stop cleanup reaps its old child, attempt a durable `OutcomeUnknown` seal. Only that durable seal permits an authorized terminal read; if the write still fails, reads remain unavailable and the R06 stop receipt is based solely on its separate physical evidence. A restart recovers the durable `Releasing` record as `OutcomeUnknown` with movement inhibited before readiness, or fails startup if recovery cannot persist. Inject failure on the initial terminal write, the fallback seal and recovery write, with an adapter response arriving after Stop, to prove no false completion, slot reuse or replay.

A pre-release terminal-write failure also needs an explicit live fault state. If a queued worker rejects expiry, health or `Closing` while its durable phase is `Prepared`, and the `Rejected` or `Cancelled` write fails, fence that ID from `begin_release` before dropping the journal lock. Keep its slot, latch movement inhibit, and make both the authorized read and exact duplicate return the fixed `result unavailable` error; neither may expose the stale durable `InProgress` or schedule an adapter. Retry the terminal write under the journal lock, choosing `Cancelled` if Stop has begun and otherwise `Rejected` for expiry or health. The first successful durable terminal transition wins, releases the slot and becomes readable. If no retry succeeds before exit, the existing journal recovery seals `Prepared` as `Cancelled` before readiness without any physical replay; recovery persistence failure blocks startup. Fault tests hold a queued mock movement at the release gate, inject this terminal-write failure for expiry, health and Stop, and assert no adapter call, unavailable reads and duplicates, retained capacity, successful seal or restart cancellation.

The browser keeps its current single-submit, guarded-read state machine. A correlated `InProgress` reply starts bounded read-only polling only after fresh IsOS status confirms the captured run and active revision; a terminal reply ends polling. If the initial reply is lost, the browser may use the same guarded result read by generated ID but may never resend the command. A Stop click remains available via IsOS during `InProgress`, bridge outage or a stale revision. After Stop or restart, the UI retains the last owner state and ID as an unavailable old-run record, ignores late responses, and never claims that Stop converted the command to `Completed`.
