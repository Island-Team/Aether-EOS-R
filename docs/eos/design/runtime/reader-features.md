# Reader preflight design

[中文](../../../../docs_cn/eos/design/runtime/reader-features_cn.md) · [Owner contract](../../interfaces/reader-features.md) · [P05 task](../../../island/implementation-todo.md)

**EOS probe slice implemented; IsOS admission pending.** EOS exposes what each selected binary can read. IsOS owns the decision to admit a saved deployment. The [reader contract](../../interfaces/reader-features.md) defines the wire fields and exact feature tokens; this page explains their use without creating another graph manifest.

The profile tool, runtime and config server share the same built-in EOS registry. Their `--capabilities` implementations should obtain the exact built-in ID list from that registry rather than duplicate a handwritten table. The profile tool's setup identity should reuse its own capability constants, so `setup --json` cannot disagree with `--capabilities`. Package-contributed types remain a separate verified input: IsOS passes only P01-verified sidecars to `setup catalog`, and the profile tool builds the effective registry from those sidecars. A static probe never claims the package has been installed, selected or admitted.

For each candidate or saved graph, IsOS first fixes the exact saved-byte revision, verifies referenced package pins and resolves its P04 binary/default input inventory. It derives selected EOS process roles and required features from actual EOS nodes, edges and launch flags. It executes each selected binary file directly and checks the reported identity, version arrays, exact built-in IDs and required feature subset. It then asks the profile adapter to validate the EOS projection with the verified sidecars. A probe failure or mismatch rejects before owner Render, generation selection, active-child stop or spawn. On Run and Restart the immutable generation's binary hashes and P05 observations must still match; Apply is the explicit path to a new generation. A binary name or product version alone cannot stand in for these checks.

The oldest supported profile probes report scalar graph/type versions. Their absence of arrays is treated as a known legacy compatibility case only when the graph uses exact registered `1.0.0` EOS identities and requires no unadvertised feature. An array that is present but invalid is a failed probe. Unknown `@v0.1` IDs, unknown future versions and unverified package contributions never enter this fallback. This preserves existing legacy reads without allowing version strings to manufacture an actuator or browser route.

The bridge is a transport child: it reads the runtime socket and optional Vision stream, not the graph. IsOS checks its selected `vision-ws` token whenever the bridge child is enabled, but does not require graph/type arrays from it. The `mujoco-child-v2` runtime token describes the existing direct-child v2 socket composition and is required for `eos.process.mujoco@v0.1`, known `@v1.0`, and the legacy `eos.process.backend@v1.0` only when that node selects the verified `island/mujoco-sim@0.1.1` v2 child. R05 will separately define strict-socket readiness; this token must not be broadened to imply that later guarantee.

Implementation tests should compare the actual debug or release binaries' probes with setup identity, all 18 exact built-in IDs, the current feature arrays and the conditional MuJoCo addition. Stub probes exercise malformed, duplicate, missing, future and legacy-scalar cases. Boundary integration tests replace one selected binary at a time, test a new graph and a safe legacy graph, vary a verified sidecar and one required feature, and assert that no child starts and active PIDs remain unchanged on rejection. Full output belongs in `logs/test/<run-id>/`, with the selected binary paths and hashes, commands, and result summary. The [frozen fixture](../../../../tests/fixtures/reader_features/README.md) names the owner-side cases; IsOS owns the public diagnostic fixture.

Design baseline on 2026-11-01: `python3 scripts/check_doc_links.py --all` found zero broken links in 294 Markdown files; `python3 -m json.tool` accepted both frozen JSON files; `git diff --check` and `cargo fmt --all -- --check` passed. Commands and complete output are in ignored `logs/test/20261101-p05-eos-design/`. These checks qualify the contract draft, not binary feature implementation.

Independent design review found that the first draft omitted two actual launch boundaries. The corrected contract and 23-case fixture require `mujoco-child-v2` for both contributed MuJoCo process versions and the pinned legacy backend, and `vision-ws` for every enabled bridge. The same documentation, JSON, diff and format checks passed after correction; complete output is in ignored `logs/test/20261101-p05-eos-design-review/`.

EOS implementation evidence (2026-11-01): `cargo fmt --all -- --check`, `cargo clippy --workspace --all-targets -- -D warnings`, `cargo test --workspace` (126 passed, one existing ignored), `cargo build --workspace`, `python3 tests/reader_features_cli.py` (four passed), and `python3 scripts/check_doc_links.py --all` (294 files, zero broken links) passed. The binary replay compared all four real probes and setup identity to the frozen fixture, rejected a malformed setup request with no files, confirmed the three direct-child MuJoCo forms and enabled bridge feature claims, and validated safe `1.0.0` and `0.1.0` EOS graphs. Complete output and selected binary SHA-256 hashes are in ignored `logs/test/20261101-p05-eos-reader-features/`. IsOS owns the remaining graph-derived feature decisions and before-stop rejection replay.
