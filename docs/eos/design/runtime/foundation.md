# EOS runtime foundation

[中文](../../../../docs_cn/eos/design/runtime/foundation_cn.md) · [Node interface](../../interfaces/hardware.md) · [Process design](process.md) · [Dispatcher design](dispatcher.md)

This page describes the current Rust foundation and records dated verification. The later design section includes implemented graph, readiness, routing and stop behavior alongside remaining physical-adapter work; its contracts are owned by [hardware](../../interfaces/hardware.md), [node contributions](../../interfaces/node-contributions.md), [control](../../interfaces/control.md), and [gRPC](../../interfaces/grpc.md).

## Runtime ownership

The IsOS-authored graph is the source of truth. New graphs use `0.1.0` and registered `@v0.1` types; legacy `1.0.0` graphs remain readable. A registered node type determines a configured instance's core, layer, group, typed ports, settings, capabilities, and lifecycle. IsOS validates the whole graph before starting direct children, and EOS validates its owner projection before creating adapters. IsOS owns EOS, HTTP bridge, and config-server processes and resolves the verified simulator package. EOS owns the simulator as a direct child, its internal nodes, durable command journal, and the single dispatcher route to each actuator. Node profiles configure nodes; camera frames, observations, movement commands, health, and outcomes are distinct Rust data structures.

The default EOS build and public launchers use Rust. The CXX mock adapter and the MuJoCo framed Unix socket adapter are the admitted hardware targets. MuJoCo is the first end-to-end runtime target and Aether v2 package candidate. Its camera exposes RGB and declares depth unavailable; the base accepts bounded body velocity and relative movement; the manipulator accepts ordered joint positions or end-effector targets only when the type and profile advertise those modes. The C++ hardware and ROS 2 side chain remains opt-in and unlaunched. Unsupported physical adapters fail admission. The Rust runtime now loads verified host skill workers through a bounded broker; storage, arbitrary model-weight execution, graph-authored skill sequences and Workflow/ActionList execution remain outside 0.x.

## Boundaries and failure rules

- A node type owns schema and placement. A node instance owns identity and settings. Typed graph edges declare data flow; the dispatcher alone admits actuator commands and writes durable results.
- IsOS starts EOS, which starts its verified simulator child and waits for the simulator Unix socket before reporting EOS readiness. If the simulator fails, EOS stops; IsOS can restart the EOS component according to its bounded policy.
- EOS acquires the journal before binding its control socket. On restart it may unlink a stale socket only when the path is a Unix socket and no live peer accepts a connection. An uncertain released command is never automatically replayed.
- EOS sends stop to all admitted actuators on graceful shutdown. The simulator enforces a body velocity lease. A measured physical controller stop bound remains necessary before hardware deployment.
- The HTTP bridge and read-only config server bind loopback. The bridge has no adapter access; it forwards bounded requests to EOS.

## Completed slices and remaining work

The integration branch is `refactor(v2)/runtime-main`; tested `refactor(v2)/…` slices are squash merged. The foundation, registry, dispatcher/journal, process manager, services, MuJoCo adapter, graph editor, and Rust default launch are implemented. IsOS and IsosUI have their own integration branches. The old C++ executable and historical module guides are outside the default Rust launch path; the active skill SDK, published contracts and some C++ hardware callers remain. Apply the [Q02 last-caller contract](../../interfaces/cpp-last-caller.md) before deleting a component. Physical ROS 2/vendor adapters and hardware stop timing are separate later slices and are not admitted by this MVP.

## 0.x runtime design and remaining work

The graph writer emits `0.1.0` and `@v0.1` node types. IsOS validates the complete graph; EOS's setup reader projects and validates its `eos` core against exact package sidecars and registered descriptions before constructing an adapter. IsOS and EGIA validate their own cores, and IsOS checks cross-core edges. The EOS runtime and config server receive the validated revision-specific `eos/graph.json` projection through IsOS launch arguments; the saved full graph is not their profile path for `0.1.0`. Existing `1.0.0` setup reads retain whole-profile validation for compatibility. EOS never rewrites the IsOS-owned graph. The [connection scheduler](scheduler.md) describes live routed edges that enforce priority and frequency without introducing a second command path.

Startup proceeds as one barrier: acquire the journal, load and validate graph and package sidecars, resolve adapter factories, start the verified MuJoCo child, wait for its owner-only socket, construct camera/base/manipulator adapters, bind control and gRPC listeners, then report ready. A failure before ready stops constructed adapters and the child and leaves a single actionable event. EGIA may connect only after the gRPC health, discovery, resources, status, and capability services pass its existing typed checks. The Rust gateway maps those published messages to the same admitted registry and dispatcher, retaining protobuf field numbers, JSON names, and operation identity.

**Independently reviewed and scoped-qualified R05 implementation of that barrier:** a connectable MuJoCo socket is not sufficient. EOS launches its direct child with `--managed-strict-socket`, never with historical gRPC or benchmark listeners, and probes every declared device for a `2.0.0` health response containing exact `strict-socket-v1`, echoed request ID and positive `ok`/`accepted`. The backend-ready event, public ready line and gRPC health remain unavailable until this proof passes; failure terminates and reaps the unready child. See the [EOS MuJoCo contract](../../interfaces/mujoco.md). The direct-launch simulator outside EOS retains legacy behavior.

During operation, the runtime owns health and typed observations; the dispatcher owns deadline, bounds, deduplication, journaling, safety, and the only actuator route. A lost simulator socket or adapter host marks affected nodes unavailable. Released commands with uncertain outcomes are never retried automatically. The R06 owner path now enforces shutdown order under blocked work: stop intake and queued work, obtain independent base/arm stop acknowledgment or record uncertainty, then terminate and reap MuJoCo before closing listeners and the journal. Managed movement primitives are available only when both MuJoCo sockets prove `strict-stop-v1` for the same generation; R05 readiness alone does not prove a later physical safe stop.

R05 proves strict identity and same-child retransmission handling. R06 owner implementation supplies stop admission fencing, a preemptive bounded simulator lane, independent base/arm acknowledgment or durable unknown, and termination/reap after the stop attempt. Exact-head and final-negative cross-owner replays cover selected paths; full R06 qualification still needs the remaining live faults recorded in the [stop design](simulator-stop.md).

The internal adapter registry contains a MuJoCo factory and its socket client. IsOS still installs and pins the external `island/mujoco-sim@0.1.1` executable and assets; EOS receives verified paths and does not install packages or edit the graph. Physical ROS/vendor drivers are later narrow adapters, with measured stop behavior required before admission. See the [implementation roadmap](../../maintenance/todo.md).
