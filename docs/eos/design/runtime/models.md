# Models runtime

[Runtime overview](README.md) · [Internal model interfaces](../../develop/interfaces/external/models.md)

`src/eos/runtime/models/` owns private capability schemas, canonical validation, the bounded inference workers, HTTP and vision WebSocket transports, and health polling. Provider field mappings and response normalization live in `src/eos/ext/models/`, where deployments can add a custom adapter without adding provider names to the core runtime. The Agent-facing gateway exposes only the four typed one-shot VAD, human, human-pose, and face-recognition calls, not the generic model method or detailed model state.

Model entries, their exact IDs, enabled state, and provider adapters are admitted at startup. The runtime does not discover model packages, reload the catalog, start inference servers, or swap a running provider. Changing those definitions requires an EOS restart; dynamic model loading is roadmap work.

## Calls and private schemas

The runtime supports exact logical model IDs for audio VAD, transcription, synthesis, generic object detection, tracked humans, complete human pose, and face recognition. Their schemas live in `share/contracts/eos/external/models/schemas/`, outside the shared manifest. `Call(model_id, request)` validates the canonical request, invokes the configured HTTP or persistent vision WebSocket provider, normalizes the response, and validates the canonical result. WebSocket transport currently supports object detection, tracked-human, human-pose, and face recognition. Each configured WebSocket model retains one connection and one request/response exchange in flight; replace-latest camera workers provide bounded backpressure without requiring unsafe provider-side response multiplexing.

ASR, TTS, and VAD accept an optional `stream` flag. The current call path is buffered and supports `stream = false`; `true` fails explicitly. Incremental delivery will require a separate chunk/event API rather than pretending a buffered JSON result is a stream.

Human-pose calls may include a pixel-aligned, lossless depth image and a raw-unit-to-metre scale. The canonical `depth_input` object is encoded as the multipart `depth_file` field; `depth_scale` remains a scalar form field. Calls without depth retain the existing RGB-only wire format.

## Automatic hardware links

The folder also owns bounded orchestration modules. `CameraPosePump` publishes each captured source frame immediately, then calls the configured `vision.human` model. Human, pose, action, and face state advances independently through `pending`, `complete`, or `unavailable`, with its own sequence and source generation. Enabled enrichments use separate replace-latest workers, so no model delays source publication or another model's completed update. Late successful results remain associated with their original generation. The camera store accepts a registered face identity only when the provider marks it known with similarity at least `0.40`. It retains that identity across all newer empty, unknown, or lower-similarity face results as long as the same explicit track ID remains present and unique, regardless of bbox motion. A different track, duplicate ID, or disappearance clears the retained identity; a newer accepted identity replaces it immediately. The continuous human detector sends RGB only: aligned raw depth remains inside EOS, where a bounded centre-region median supplies each bbox's `distance_m`. The four retained exact frames keep aligned raw depth. Continuous pose enrichment remains RGB-only and derives optional metric joint depths locally from bounded pixel neighbourhoods. Exact-frame APIs may still encode depth as lossless PNG when explicitly requested. This removes full-resolution depth PNG compression, base64 transport, and provider decoding from the hot path without changing bbox coordinates or distance units. A sampled `camera_pose_throughput` event reports captured/submitted/replaced/completed and failed counts plus encoding, model, and end-to-end timing about once per second. It is emitted at debug level so routine measurements do not fill the launch log. The completed rate is the human-detection rate; resource publication sequence is not a frame-rate measurement. The pose-enrichment request carries only each detection's `track_id`, `bbox`, `confidence`, and optional `distance_m`; derived pose, action, face, and other normalized fields are not fed back to the provider. The `CameraObjectPump` independently calls the configured `vision.object_detection` model over HTTP or WebSocket. Its validated head-detection history is declared before the first result, and read, watch, or skill-subscription demand starts the shared pump lazily. `MicrophoneVadPump` accepts 16 kHz mono PCM windows, calls `audio.vad`, groups speech into an utterance, then attempts the exact model ID `asr`, and publishes successful VAD/ASR results through `MicrophoneVadStore`. The perception Reader observes these stores; neither pump creates a northbound transport or releases hardware commands. If the VAD pump drops buffered PCM, `microphone_audio_dropped` remains a warning and reports the lost duration, remaining backlog, and last VAD/ASR call times; these are operational measurements and contain no audio content. Model health warnings include the configured probe timeout and bounded failure message, so a slow probe can be distinguished from a refused connection. Each successful VAD call becomes one validated, bounded `vad.snapshot` retained at `robots/{robot}/world/vad/state`. Read and watch demand share the same `microphone_vad` producer used by the continuous stream. PCM, generated WAV, utterance audio, model segments, and provider metadata never enter that history.

Continuous links are enabled only by their `[perception.stream]` switch. Any of `human`, `human_pose`, or `face` starts the camera human producer; the latter two also enable their enrichment worker. Each enabled switch validates its configured role binding: `vad` uses `microphone_vad.model_id`, `human` uses `camera_pose.detection_model_id`, `human_pose` uses `camera_pose.model_id`, and `face` uses `camera_face.model_id`. All camera switches also validate the base `camera_pose.detection_model_id`; absent or false switches never fall back to legacy camera or VAD pumps. The optional `asr` follow-up is resolved at call time, so its absence does not prevent the VAD pump from starting. When log attachments are enabled, the exact merged WAV submitted to ASR is stored in the flat launch attachment directory as `asr-<uuid>.wav` and referenced by `microphone_asr_requested`; there is no `asr/` subdirectory. The older `save_audio` setting independently writes diagnostic utterance WAV files under the microphone VAD state directory.

The versioned face v1 schema retains legacy provider operation shapes. Typed northbound and skill inference APIs construct only `recognize`; of the other operations, EOS uses only registration. The dispatcher uses the separately validated internal `Runtime::RegisterFace` operation for the `face.register` primitive.

Skill one-shot vision inference does not require an enabled continuous stream. It may submit canonical inline `input` (and capability-supported depth/options) directly to the configured model, using the same request shape as the typed northbound API. Alternatively it may name an exact frame in the bounded camera store. The two modes are mutually exclusive; model request size, schema, response schema/invariants, and cancellation remain enforced by `Runtime::Call`.

Hardware bindings may also declare model-backed advanced primitives. Their `[[device.primitive]] model_id` selects one exact model; it is not a capability-wide lookup. Unlike optional perception pumps, an advanced primitive is part of the launched command surface, so its referenced model must exist, match the catalogued capability, and have `enabled = true` or EOS refuses startup. `speaker.speak@1.0.0` currently uses this mechanism with an `audio.synthesis` model. After its response passes the complete PCM WAV checks, the output is stored as `tts-<uuid>.<ext>` in the flat launch attachment directory and referenced by `tts_audio_generated` before release to the speaker backend.

## Health

A model may configure a separate HTTP `health_endpoint`; bounded `health_interval_ms` and `health_timeout_ms` control polling on a shared two-worker health scheduler independent of inference workers. One model never has overlapping probes, and shutdown cooperatively cancels active probes. A missing endpoint produces one configuration warning and unavailable health, but does not make optional inference configuration noisy.

Gemma's health probe allows 30 seconds because its provider may delay `/health` while serving an inference request. The probe timeout matches its inference timeout.

The generic `Runtime::Call` path does not reject a call from cached health alone. Consumers may impose a stronger rule: the advanced `speaker.speak` primitive requires its exact bound TTS model to report ready before synthesis. `GetStatus` exposes only aggregate total/ready/checking/degraded/unavailable counts for enabled models, never endpoints, credentials, headers, or provider metadata.

Tests use loopback providers for valid and malformed health, timeouts, mismatch, recovery, concurrency, clean shutdown, request/response normalization, bounds, and automatic-link input admission. External-adapter tests cover provider mappings independently.
