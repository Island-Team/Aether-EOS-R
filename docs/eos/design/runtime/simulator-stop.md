# R06 EOS simulator stop design

[中文](../../../../docs_cn/eos/design/runtime/simulator-stop_cn.md) · [Owner contract](../../interfaces/simulator-stop.md) · [Hardware](hardware.md) · [Dispatcher](dispatcher.md) · [Process supervision](process.md) · [Frozen cases](../../../../tests/fixtures/simulator_stop/README.md)

**EOS owner implementation merged; scoped cross-owner replay passed, while original R06 row and scoped M3 exit are qualified.** R06 closes the safety gap left by the R05 strict socket. Before this candidate, `StopGuard::stop` invoked `Dispatcher::emergency_stop` without a terminal physical receipt; `BackendChild::Drop` sent TERM, waits two seconds, then sends KILL to the process group and reaps; `Endpoint::stop` set a local flag and uses the ordinary socket; and `begin_release` dropped the journal lock after `Releasing` before calling an adapter. None of those facts proves an admitted movement was fenced before child termination. The [owner contract](../../interfaces/simulator-stop.md) defines the receipt and deadline; this page explains how to reach them.

## Single shutdown state and release fence

Use a run-scoped `Running → Closing → Stopping → Terminal` state shared by signal handling, private owner shutdown, backend-loss detection and normal unwind. The first transition to `Closing` is irreversible. It closes gRPC and private movement ingress, quiesces Dispatcher, seals skill/evidence publication, and snapshots every admitted base/manipulator path. A second stop joins the same state. The shutdown coordinator starts its absolute monotonic deadline before any blocking work; every child, socket and worker operation receives only the remaining time. It never waits for an ordinary capture, movement, skill, log or client worker to complete before scheduling the reserved stop request.

The Dispatcher release gate needs two distinct facts: a new command cannot cross after `Closing`, and a command that already persisted `Releasing` cannot reach the MuJoCo engine after the physical stop. For the latter, capture the shared adapter session's `(generation_id, stop_epoch)` before the durable `Releasing` transition and attach it to that exact command. Do not fetch a fresh epoch after a stalled journal update or queue wait. The MuJoCo engine checks this pair under its own short movement commit lock; its stop lane advances the epoch and overwrites both targets under the same lock. A delayed old release therefore returns a fenced or interrupted result. Dispatcher records that result against the original command ID and does not retry it. A lost result remains `OutcomeUnknown`, with the journal movement inhibit retained. An adapter response arriving after the stop fence cannot overwrite a terminal unknown/cancelled command with `Completed`; journal finalization compares the captured stop generation. This physical epoch fence must also cover the safety-estop path, which currently bypasses the writer-preferred release gate.

MuJoCo's companion stop is whole-robot. A single `ManagedMujocoStopCoordinator` belongs to the child generation, not to either per-device `Endpoint`. `robot.stop`, `safety.estop` and internal shutdown converge on it through Dispatcher. The coordinator registers a stop writer so later movements cannot enter, but does **not** call `wait_drained` before the physical request: an admitted movement may hold that permit while blocked in the ordinary socket. It reserves the companion safety lane, advances the engine epoch and obtains one base/arm result before waiting for any normal adapter return. Simultaneous stop IDs join that in-flight result; they retain distinct journal IDs and signatures, but cannot send duplicate physical frames. The authenticated stop registers a writer and starts its ID-keyed physical worker before it waits for the journal mutex. If an intent write fails or stalls past the physical deadline, the physical call still runs, while the operation and owner receipt remain unknown. The selected target set is marked `attempting` in each stop journal record before release; the one physical response is mapped by graph path and persisted in one update per joining record. No part is called sequentially. A failed part or terminal persistence leaves inhibit. A later stop after a new movement release needs a new physical request. A controlled `robot.stop` may publish a newer epoch for later movement only after dual proof and durable journal terminal result; it does not clear an estop latch. Shutdown never clears its admission fence. The published device-scoped `motion.stop` contract cannot be implemented by this whole-robot request, so MuJoCo omits that capability and rejects a valid Submit with `FAILED_PRECONDITION/terminal_device_stop_unavailable`. `has_terminal_stop_fence` becomes true for MuJoCo base/manipulator only after both main and companion health prove `strict-stop-v1` with the same generation; it is not by itself permission to advertise `motion.stop`. Camera remains read-only. A timeout leaves the shared epoch unadvanced from EOS's view, inhibits movement and reports unknown. Child loss invalidates the generation.

## Physical stop and child lifecycle

The child starts with the existing verified package, scene and graph binding; R06 also validates that `<main-socket>.stop` fits the Unix path limit and is owner-only. Before EOS ready it probes each declared actuator on the main socket and companion stop socket. GUI/render failure before the R05 camera readiness proof fails startup; a missing stop lane keeps managed movement and robot-level terminal stop hidden. A render worker blocked **after** ready cannot occupy the companion stop lane, so dual stop can still be confirmed if the engine answers. A live loss of stop-lane health degrades actuator availability and blocks new release. The shutdown coordinator sends the whole-robot stop once on the companion socket even if an ordinary request is blocked. It validates version, ID, generation, new epoch and base/arm statuses, then maps the full reply to the selected graph paths. The MuJoCo contract's bounded classification and execution are 500 ms and 1000 ms after successful connect and valid frame respectively; EOS's 3000 ms physical-stop budget also includes connect, write, read and local classification. A timeout or malformed partial reply never becomes confirmation.

Only after stop proof or explicit unknown classification may EOS terminate MuJoCo. The [R04 host worker broker](skills/host-rust.md) closes intake after Dispatcher quiesces; physical stop runs before EOS waits for host workers, and bounded worker shutdown completes or fails explicitly while MuJoCo is still alive. A host worker shutdown failure makes the managed terminal receipt unknown. MuJoCo starts in its own session; reaping its leader alone does not prove descendants left that group. The leader stays unreaped while EOS may still signal the pinned PGID, preventing PGID reuse. Replace `try_wait` liveness polling with `waitid(..., WNOWAIT)`; the current polling can reap the leader before stop. EOS records the leader PID, start ticks, PGID and session at spawn; before TERM or KILL it compares `/proc/<pid>/stat` with those values. It sends TERM to that exact held group, observes the leader without reaping, and scans `/proc` for any other member of the pinned PGID/session until none remains; scan errors or a nonempty group at deadline are unknown. EOS acts as a child subreaper to detect adopted descendants that escaped the group; any escaped or unaccounted survivor is unknown. A descendant cannot be ignored because the leader exited or because its stdout pipe reached EOF. A surviving member triggers identity-safe group KILL at the phase deadline, followed by bounded drain/reap polling, but forced KILL remains unknown even if it succeeds. Only after the group is drained and no later group signal is possible does EOS reap the leader and report `backend_group_drained:true,backend_reaped:true`. It never sends KILL after reaping the leader. At spawn, the child also receives `PR_SET_PDEATHSIG=SIGTERM` and checks its parent PID after `setsid`, so an EOS crash does not leave a deliberately managed simulator unattended; that signal is cleanup, not physical-stop proof, and IsOS still reports unknown. EOS explicitly redirects every child/helper stdio and sets close-on-exec on unrelated descriptors, preventing descendants from keeping its selected stdout receipt pipe open. It removes backend main and companion sockets and the private control socket before a confirmed receipt; `Drop` cleanup may still run for unknown paths but cannot upgrade them. Stuck log workers are detached from the safety deadline after their pipes close. The receipt is published only after final state classification, then one bounded stdout write and exit; P06 stderr events are diagnostic and cannot replace the selected pipe receipt.

The R06 deadline is 15 seconds from EOS's first stop transition `t0`: admission closure by `t0+1s`, physical stop classification by `t0+4s`, TERM/KILL/reap by `t0+10s`, socket cleanup and receipt write by `t0+13s`, and exit by `t0+15s`. The coordinator uses timer wakeups rather than relying on the ordinary accept loop to notice a signal. A missed phase is unknown and moves to cleanup; no phase extends the global deadline. IsOS defaults to 20 seconds of EOS grace inside its 30-second deployment stop deadline and reserves its last 2 seconds for forced group cleanup. A configured EOS grace shorter than the EOS bound is allowed only as an explicit owner choice and may return unknown; neither owner may call a timed-out stop confirmed. The EOS exit code is zero only for a confirmed receipt and clean termination. An unknown receipt exits nonzero. The receipt is one nonblocking stdout write of at most `PIPE_BUF` bytes; a full or closed pipe produces no usable receipt and is unknown to IsOS.

## Q04 backend descendant ownership correction

The post-spawn EOS direct-child census cannot establish backend ownership: host skill workers and adapter hosts may start after the backend. Stop may signal or reap only a process whose PID and start ticks match an observed member of the held backend PGID/session or a descendant whose live parent was already proven. This preserves identity after subreaper adoption. A newly adopted direct EOS child outside that proven set is ambiguous, so EOS leaves it untouched and reports `backend_group_unreaped` (unknown) rather than claiming drain. An escaped descendant observed only after its parent exits cannot be safely distinguished from an unrelated worker; it also stays unknown. The separate-session unrelated-child regression must show that stop neither signals nor reaps it. The escaped adopted-child test must show unknown, while original group members and previously observed descendants still receive bounded TERM/KILL handling.

For an ambiguous adoption, the owned group and known descendants can still drain. EOS then reaps the held backend leader without another group signal, but leaves `backend_group_drained=false` and `backend_group_unreaped` in the receipt; it does not report `backend_forced_kill`. The regression checks that exact reason, leader reap, and the unrelated child's continued ownership by its original caller. In the runtime startup order, adapter hosts are created before the backend baseline; managed host skill shutdown waits before backend termination. An unreaped host worker already makes the terminal receipt unknown, and the attribution uncertainty cannot turn it into confirmation.

## Q04 managed startup stop-proof correction

The clean public snapshot gate exposed a startup race: the simulator main socket could answer strict health before its companion stop listener bound, while EOS still emitted ready. Managed IsOS runs now require each declared base/manipulator to prove `strict-stop-v1` with one matching generation on both sockets before ready. Transient transport errors, including an unconnected startup socket, retry only within the existing absolute startup deadline; malformed proof or generation mismatch fails immediately. A standalone read-only R05 launch retains optional stop proof, and a camera-only graph remains read-only.

The process regression delays the companion listener and verifies ready comes afterward; a never-bound listener must time out with `eos_start_failed`, no ready output, and cleaned sockets.
