# Building and launching the Rust EOS v2 process set

[中文](../../../docs_cn/eos/develop/build-and-run_cn.md) · [Service map](services.md) · [Node graph](../interfaces/hardware.md)

Rust owns the default EOS build and the public `eosd`, `eos-north-http`, `eos-config`, and `eos-cli` launchers. These map to `aether-runtime`, `aether-http-bridge`, `aether-profile`, and `aether-tui`. `aether-config-server` is installed as its own read-only process. IsOS creates configuration with `isos init`, runs its manager with `isos serve`, applies a graph with `isos config apply <file>`, and starts the applied deployment with `isos run`. `isos deployment stop` stops only graph children; `isos stop` shuts down every IsOS-owned process, including the manager and UI. The `eos` wrapper forwards deployment lifecycle commands to these IsOS commands and opens `eos-cli` for `enter`. The legacy `island-launch` and `etc/runtime/stack.toml` are an unlaunched side chain and are not installed in a default v2 package.

The virtual Cargo workspace lives in top-level `crates/aether-*`, matching the crate layout used by `../Island`. All ten crate versions come from the workspace's `0.2.0` version. Rust executables use the `aether-` names; EOS launchers remain the product entry points. IsOS uses its configured `aether_bin_dir` or `ISOS_AETHER_BIN_DIR` to find `aether-profile` and the other core binaries. In a source checkout, `bin/aether-profile` resolves the release binary.

Run `./build.sh` for a source checkout, or configure and build with CMake using its default `ISLAND_BUILD_EOS=ON` and `ISLAND_BUILD_EOS_CPP=OFF`. The script places release binaries under `target/release`; CMake places them under its build tree's `cargo-target/release` and installs the five Rust executables to `libexec/island`. Source launchers use `target/release` unless `CARGO_TARGET_DIR` or `ISLAND_BUILD_DIR` names another location. The C++ runtime and hardware targets can be built explicitly with `./build.sh --cpp-side-chain` or `-DISLAND_BUILD_EOS_CPP=ON`; C++ process targets are never installed over Rust process names. The default install includes the mock and MuJoCo v2 node graphs under `etc/island/eos/graphs`.

For a local smoke run, use a private directory for the socket and journal, then start `bin/eosd --profile etc/eos/backends/mock-cxx.toml --journal-dir <private-dir>/journal --socket <private-dir>/eos.sock`. The process prints a `1.0.0` ready JSON line after admission. `bin/eos-north-http --socket <private-dir>/eos.sock --listen 127.0.0.1:16201` exposes the bounded control API; `bin/eos-cli --socket <private-dir>/eos.sock` opens the REPL. `bin/eos-config validate --file <graph>` checks the shared graph before IsOS applies it. `aether-config-server --profile <graph> --listen 127.0.0.1:16202` serves a validated read-only snapshot and type catalog. See [service behavior](services.md) for routes and bounds.

## Check the selected readers before Apply

IsOS selects exact executable files from its configured EOS binary directory. For a first-use inspection, run `<eos-bin-dir>/aether-profile --capabilities`, `<eos-bin-dir>/aether-runtime --capabilities`, and `<eos-bin-dir>/aether-config-server --capabilities`. Each prints supported graph/type versions and feature tokens without starting a device. The profile tool also answers `printf '%s\n' '{"schema_version":1,"op":"identity","core":"eos"}' | <eos-bin-dir>/aether-profile setup --json`. The [reader contract](../interfaces/reader-features.md) lists exact fields, built-in IDs and conditional features. A `0.1.0` graph needs readers that explicitly advertise `graph-0.1-reader`; any verified MuJoCo v2 child, including a legacy backend graph, additionally needs runtime `mujoco-child-v2`. An enabled HTTP bridge needs `vision-ws`. Product version alone does not establish compatibility. The HTTP bridge reports transport features, not graph-reader support. IsOS Validate and Apply compare the actual graph, verified package sidecars and selected binaries; Run and Restart recheck the selected generated snapshot before any child starts. If preflight rejects an unsupported type or feature, inspect the named binary and graph pointer, then use an exact verified compatible release or edit the graph and Apply again. Legacy `1.0.0` graphs remain readable only through their exact known identities.

The [MuJoCo IsOS graph fixture](../../../examples/v2/mujoco-isos.toml) records a historical `1.0.0` deployment with `@v1.0` types and `scene = "default"`; keep it read-only for legacy compatibility tests. For a new `0.1.1` deployment, choose the verified `sim-hardware` node set and `pick-place` or `navigation` scene in IsOS, then Validate and Apply the generated `0.1.0` graph. An existing graph needs explicit revision-checked migration. The merged R05 path starts the verified simulator child, connects to its Unix socket, and proves strict health for every declared device before announcing readiness: each reply must have protocol `2.0.0`, the echoed request ID, `ok:true`, `accepted:true`, and `features` containing `strict-socket-v1`. IsOS then starts dependent bridge and config processes. The simulator's v2 socket must match each MuJoCo adapter `socket_path` in the graph. IsOS stops dependents before EOS; EOS stops admitted actuators before terminating and reaping the simulator child.

The v2 default currently supports the CXX mock and MuJoCo adapters. It has no physical ROS 2 or vendor controller parity or measured hardware stop bound, so those nodes fail admission. Verified host skill workers are available through the bounded broker; arbitrary model weights, graph-authored skill sequences, Workflow/ActionList and storage orchestration are outside this 0.x target. Do not point an installed physical actuator at the C++ side chain and Rust dispatcher simultaneously. Legacy C++ sources remain reachable from the opt-in side chain and can be deleted only under the [last-caller contract](../interfaces/cpp-last-caller.md).
