# R02 gRPC first-use and verification

**R02 owner-stage record:** the R02 implementation passed local qualification and independent implementation review. The Rust runtime implements the eleven required R02 RPCs on a loopback gRPC listener and passes a selected EGIA typed-client replay against a mock profile. Test-injected producers and proof-capable adapters cover the positive resource and controlled-stop boundaries. At the R02 owner stage, production MuJoCo movement awaited R05 physical epoch fencing and R06 simulator stop/reap ordering. The subsequent [scoped M3 qualification](../../island/m3-qualification.md) closes the exit row on merged inputs.

1. Select the exact IsOS-applied graph and generated configuration. Start `eosd` with its verified profile, journal, private control socket, MuJoCo child and new loopback gRPC listener. Current startup fails before listener bind on an intentionally missing adapter or corrupt journal, with no ready event. If a future path binds before admission, health must remain `NOT_SERVING` and required RPCs must fail `UNAVAILABLE`.
2. After `SERVING`, run the selected EGIA typed client against the listener. It must finish health, `Discover`, `ListResources`, `GetStatus`, `ListCapabilities`, and optional `ListSkills` (`UNAVAILABLE` if not implemented). Compare robot identity, matching robot ID/name and nonempty status/version/start time, each actual device, exact primitive/capability pairs, resources and health against the saved graph and runtime projection. No empty world/detection/ASR resource may be invented. Reject an invalid candidate before publication and confirm the existing listener retains one immutable binding generation while live health degrades. Recheck after backend loss.
3. Read a declared resource, start `WatchResource`, change its validated product, and check a same-URI notification followed by a fresh `ReadResource`. Drop the stream and reconnect with a new watch plus read. Test cold, stale, unknown, slow-consumer and cancelled paths. Current EGIA does not auto-recover from slow-consumer `RESOURCE_EXHAUSTED`; record the caller error and explicitly rebuild the watch plus read. Request one and two camera frames; verify exact count, distinct JPEGs, dimensions, capture times, size cap, deadline and missing-frame behavior.
4. Submit one admitted primitive with a caller operation ID. Compare the resulting v2 `Operation` to the same Dispatcher command and durable journal record: ID, exact binding, admission, status and canonical `primitive.ack` must agree. Repeat the exact request concurrently and across a restart; there must be one adapter release. Reuse the ID with changed arguments or another advertised binding and expect `ALREADY_EXISTS`. Drop the Submit response and Watch stream, then query `GetOperation` with the same ID. Never retry uncertain movement automatically. Cancel only that command and use explicit stop to clamp motion. Separately verify journaled single-device `motion.stop`, whole-robot `robot.stop` without an emergency latch, and emergency-path `safety.estop`, including already-stopped, partial-failure, unconfirmed and duplicate-ID-after-restart cases. Crash `robot.stop` after one part confirms and before the second call; verify `OUTCOME_UNKNOWN`, known/unknown per-part results, no repeat call for either part under the same ID after restart, and no readiness with more than 64 stop-capable parts. Submit movement concurrently during fanout and verify rejection before adapter release. Pause an earlier movement after synced `Releasing` but before its adapter call, start RobotStop, and verify stop fanout cannot overtake the movement; repeat with an ambiguous in-flight movement and verify the inhibit remains through fenced/quiescent recovery. Inject pre-release and post-possible-release result overflow separately, expecting zero calls/`RESOURCE_EXHAUSTED` versus inhibited `OUTCOME_UNKNOWN`. After restart, use a newly authorized ID to stop the union of old and current targets, then verify durable inhibit clear without clearing an emergency latch. Inspect v2→v3 journal migration to confirm a typed robot target is used for whole-robot stops and recovered estop remains latched without re-release.
5. On shutdown, observe `NOT_SERVING` before new writes fail, bounded watches close, and Dispatcher stop before MuJoCo termination/reap. The latter physical ordering is an R06 qualification boundary; record the current R02 behavior without marking R06 passed.

The Rust listener samples adapter health and status on one bounded background worker per admitted projection. Discover, GetStatus, ListCapabilities and CaptureFrames read the retained snapshot without calling the HAL on a tonic request worker. A missing, failed or older-than-`min(health_timing.stale_after_ms, 1000 ms)` sample makes the affected device unavailable; CaptureFrames also needs its own frame no older than one second. A complete fresh projection attaches `eos-sample-age-ms` with the oldest health/status sample age to the first three responses. Fresh ReadResource and successful CaptureFrames attach the retained product/frame age. Missing or stale samples provide no age header and fail closed where a body is required. A probe is dated before its health and status calls, so a delayed status cannot make an old health result look fresh. The delayed-status network replay proves stale availability and absent age after the late result, then fresh recovery on the next complete probe. The sampler stops publishing on shutdown and never waits for a blocked adapter before Dispatcher safety stop. Movement has sixteen worker permits; controlled stop and emergency stop each have a separate reserved permit, so queued movement cannot consume the stop paths.

A pending `WatchOperation` sends its current state and then one terminal update if it arrives before the caller deadline. At the caller deadline (five seconds by default), it sends `DEADLINE_EXCEEDED` rather than silently ending; the client then uses the same ID with `GetOperation`. A lost Submit response, watch cancellation, or deadline does not authorize a new physical release.
