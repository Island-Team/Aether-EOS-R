# EOS v2 Vision interface

[中文](../../../docs_cn/eos/interfaces/vision_cn.md) · [Package node IDL](node-contributions.md) · [Owner first-use guide](../develop/vision-provenance.md)

The legacy built-in `eos.interface.camera_gate@v1.0` is a software node at `eos/interface/gate`. Its required `frame:camera_frame` input must refer to a registered camera's `frame` output. Its `preview:vision_frame` output is a read-only stream. The built-in `isos.ui.vision@v1.0` is a software node at `isos/ui/panel`; its optional `preview:vision_frame` input selects an initial gate. A viewer may choose any active compatible gate. The former `isosui.system.vision@v1.0` is accepted only as an import alias and is emitted as the IsOS-owned type. Neither node admits actuator commands. The legacy `isos.ui.vision@v1.0` node is not a `0.1.0` Vision destination, and its preview is not the Q01 EGIA service binding.

## Data and rate contract

`vision_frame` uses codec `vision_frame_jpeg_v1`, media type `image/jpeg`, and an 8 MiB JPEG payload limit. The logical `VisionFrame` fields are `gate_path` (string, canonical gate path), `sequence` (optional unsigned integer, source frame count), `timestamp_unix_ms` (optional signed integer, Unix milliseconds), `width_px` and `height_px` (positive integer, pixels), `source_rate_hz` (finite positive number, hertz), and `jpeg` (JPEG bytes). The binary WebSocket payload carries metadata separately from JPEG bytes.

The gate captures its camera at the declared observation rate up to a hard 60 Hz limit. One latest frame is retained per camera output; slower viewers drop older frames. The Vision node's optional `target_fps` (positive integer, frames per second, at most 60), `max_width_px` (positive integer, pixels, at most 4096), and `jpeg_quality` (integer 1–100) tune a viewer. WebSocket subscription defaults are the source declared rate capped at 60, 1280 pixels, and quality 85. The current direct runtime capture request defaults to quality 80 when omitted; clients seeking identical JPEG output must send the quality explicitly. JPEG encoding maintains aspect ratio and uses source RGB bytes. When the camera supplies a JPEG preview at the requested quality and full width, Vision reuses those validated bytes. A frame is available only while the camera is ready and healthy.

## Read-only browser API

`GET /api/eos/v2/vision/gates` returns `{"revision":"<graph-hash>","gates":[{"path":"<gate-path>","label":"Front camera","output_port":"preview","source_path":"<camera-path>","source_rate_hz":30.0}]}`. `revision` is the lowercase SHA256 hex digest of the loaded graph bytes. The list includes active gates only. `path` and `source_path` are canonical graph paths, `label` is a display string, `output_port` is `preview`, and `source_rate_hz` is hertz.

Connect to `WS /api/eos/v2/vision/ws` and send one masked text frame first:

```json
{"op":"subscribe","gate_path":"eos/interface/gate/front","revision":"<graph-hash>","target_fps":30,"max_width_px":1280,"jpeg_quality":80}
```

`op`, `gate_path`, and `revision` are required strings. The three numeric options are optional and use the bounds above. The server sends `{"type":"subscribed"}` or `{"type":"error","message":"..."}` as text. Each binary frame is `u32` little-endian metadata JSON byte length, then that many UTF-8 metadata JSON bytes, then JPEG bytes. Metadata includes `gate_path`, `width_px`, `height_px`, and `source_rate_hz`; `sequence` and `timestamp_unix_ms` appear when present. The subscription is rejected if the graph revision changed or the gate is inactive. One WebSocket connection carries one subscription. Frames are bounded to 8 MiB JPEG plus 4 KiB metadata. Browser origin restrictions from the HTTP bridge still apply.

EOS captures and encodes in its runtime; the HTTP bridge only relays validated read-only frames. No browser endpoint accepts raw camera control or actuator commands.

## Q01 gate provenance extension — implementation candidate

This additive extension is specified for the [Q01 milestone](../../island/implementation-todo.md). The direct gRPC `CaptureFrames` remains a source snapshot and cannot prove receipt of a gate-delivered frame by EGIA. The owner WebSocket described below carries that provenance when an IsOS-selected binding is active. The extension applies only to `eos.interface.camera_gate@v0.1` deliveries on an IsOS-selected active graph. It does not turn `vision.snapshot`, a resource, or the legacy `@v1.0` preview into gate evidence.

EOS assigns each successful gate-slot publication an immutable **delivery identity** `(graph_revision, runtime_stream_id, gate_path, gate_generation)`. `graph_revision` is the IsOS-managed active revision: lowercase SHA-256 of the saved whole-graph bytes, distinct from the existing Vision `revision` (SHA-256 of the loaded EOS projection bytes). EOS accepts it only from verified managed launch metadata. Standalone EOS cannot claim Q01 managed provenance. `runtime_stream_id` is a random UUID generated once on each EOS runtime start, changed on every child restart even within one IsOS deployment run, and never supplied by a camera. `gate_generation` is a positive unsigned 64-bit counter, strictly increasing within one stream and gate; zero is reserved. At the maximum value EOS stops publication for that gate with `generation_exhausted` and requires a new runtime stream. A graph change requires a new runtime and stream. A shutdown, health loss, or revision change clears the delivered slot before any new read; an old JPEG is never replayed as current. Health invalidation advances a source epoch. A delivery staged before that advance cannot commit, even if health recovers before the next read; only a fresh capture in the new epoch can publish.

The captured source receives `source_frame_id`, a nonblank EOS-issued opaque ID unique within `(runtime_stream_id, source_path)`, even when the camera provides no sequence or capture timestamp. EOS freezes the canonical `source_path`, optional source `sequence` and `timestamp_unix_ms`, dimensions, and source bytes with that ID before gate delivery. Camera-reported sequence and time remain diagnostic and never substitute for the EOS ID or the delivery identity. The gate snapshot holds the source and delivery identity together; the HTTP bridge must not assemble metadata from a later status read.

Each binary WebSocket frame retains the existing `u32` little-endian metadata-length prefix and 8 MiB JPEG bound. The metadata JSON must be at most **4096 UTF-8 bytes**, measured before the JPEG; length zero, length above 4096, truncated JSON, non-object JSON, or an absent JPEG is invalid. The extension adds the following required fields to the same metadata object. Existing fields keep their meanings.

| Field | Type / unit | Purpose, absence and validation |
|---|---|---|
| `graph_revision` | string / — | Required 64 lowercase hex digits, exact IsOS active saved-graph digest; old frames without it cannot be Q01 evidence. |
| `projection_revision` | string / — | Required 64 lowercase hex digits of the loaded EOS projection; equals the existing Vision catalog/subscription `revision`. |
| `runtime_stream_id` | UUID string / — | Required EOS-start ID; never reused after restart. |
| `source_path` | canonical graph path / — | Required camera source of the delivered gate, matched to the selected graph edge. |
| `source_frame_id` | nonblank opaque string / — | Required EOS capture ID; max 128 UTF-8 bytes; unique for this source and stream. |
| `gate_generation` | unsigned 64-bit integer / deliveries | Required, positive, strictly increasing per gate and stream; no wrap or reuse. |
| `render` | object / pixels and quality 1–100 | Required `{ "max_width_px": 1280, "jpeg_quality": 80 }`, the validated subscription parameters used for this rendition. |
| `jpeg_sha256` | string / — | Required lowercase SHA-256 hex of the **exact JPEG bytes after metadata**; computed by EOS after encoding, before the immutable frame is queued. |

For example, the metadata portion of one frame is:

```json
{"gate_path":"eos/interface/gate/front","graph_revision":"0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef","projection_revision":"aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa","runtime_stream_id":"8b4e9b70-5481-4d88-9bd6-4f07cb466ae4","source_path":"eos/hardware/camera/front","source_frame_id":"cam-41","gate_generation":7,"width_px":1280,"height_px":720,"source_rate_hz":30.0,"render":{"max_width_px":1280,"jpeg_quality":80},"jpeg_sha256":"c8f1b57ba3b319e7c5ddce3dac7f09c729d8d4bce2259c4f03d68cdbb7f69f0d"}
```

The illustrative digest above is a shape example, not a digest of an omitted JPEG. A receiver verifies `jpeg_sha256` over the received bytes. Different subscriptions may render the same delivery at different widths or qualities, so delivery identity can match while JPEG digests differ. A Q01 replay that claims byte equality must select identical render parameters and compare each verified digest and binary payload length; otherwise it compares the delivery identity and reports both rendition digests separately. For Q01, EOS encodes the fixed 1280-pixel/quality-80 rendition once from the committed gate snapshot, retains those immutable bytes with the latest slot, and serves those same bytes to the browser and owner listeners when both request that render. It computes the digest once over that JPEG; replacing or clearing the slot drops the bytes. Other render choices have separate bytes and digests. A rendition never changes the delivery identity or gate cap counters.

The subscription's `revision` remains mandatory and denotes `projection_revision`; it does not replace the selected IsOS `graph_revision`. A wrong or no longer active revision or gate gets a text error and no binary frame. A reconnect first receives an attested `subscribed` response containing `graph_revision`, `projection_revision`, `runtime_stream_id`, `gate_path`, `source_path`, and current `gate_generation`; EOS derives these atomically from the verified static route and live health before the first frame, or from the active gate snapshot after delivery. A caller-supplied `after_generation`, when present, is an unsigned 64-bit cursor and requires `after_runtime_stream_id` equal to the attested stream; EOS binds both to the selected gate. EOS emits only a generation **greater** than that cursor. An older cursor may receive the current newer delivery; an equal cursor waits for the next publication, and a cursor above the current generation waits rather than causing replay. A cursor from a different stream is invalid with `cursor_stale` and requires a fresh subscription without a cursor. There is no rollover. The cursor is optional for existing browser clients and carries no command authority.

IsOS selects the endpoint and grants owner-local read-only access to EGIA for one deployment run; EOS accepts only that selected grant on the owner transport. The `deployment_run_id` and grant rotate on every IsOS deployment run, while `runtime_stream_id` rotates on every EOS child start. Browser Origin and a loopback address are not owner authentication. EOS binds the grant to the selected endpoint, graph revision, gate and source; metadata alone cannot authorize a subscriber. The browser path remains subject to its existing Origin rule. EOS stops new publications and clears pending/latest gate frames before stopping admitted actuators and terminating MuJoCo; `safety.estop` and Stop keep their existing priority and never wait on a Vision subscriber. After stop, a subscriber receives a close or unavailable result, never a cached success frame.

The target reason codes are `invalid_metadata`, `jpeg_invalid`, `jpeg_too_large`, `revision_mismatch`, `gate_inactive`, `source_mismatch`, `stream_mismatch`, `cursor_stale`, `generation_exhausted`, `owner_grant_denied`, and `stopped`. Errors carry no JPEG or secret grant. `route_status` remains the owner of `cap_wait_count`, `replaced_count`, and `gap_count`; those counters describe the EOS gate queue, not EGIA ingress. A selected MuJoCo case must prove an exact delivered gate frame and route counters without claiming a positive replacement count unless induced and observed. The existing FIFO `overflow_count` evidence remains synthetic until a live FIFO graph route exists.

### Frozen 0.x owner transport and handshake

The existing `aether-http-bridge` keeps `--listen <loopback-host:port>` and the public browser `GET /api/eos/v2/vision/gates` and `WS /api/eos/v2/vision/ws` on its TCP listener. A selected Q01 run additionally starts that same bridge process with `--owner-vision-socket <absolute-path>`, its existing `--socket <EOS-private-runtime-socket>`, and `--run-id <IsOS-run-id>`. The new owner listener is a Unix socket named `eos-vision-owner.sock` in the IsOS-selected private Vision endpoint directory, which can be shorter than the control-grant run directory. The endpoint directory has mode 0700 and matching UID; the socket has mode 0600. Its mode-0600 verifier is in that same directory. IsOS checks both Vision socket paths against the Unix pathname limit before launch. The listener accepts only `GET /api/eos/v2/vision/owner-ws` with `Host: localhost`, no `Origin` or `Sec-Fetch-*`, no query credentials, and `Authorization: Bearer <64-lowercase-hex>`. It never routes to public gates, control, result or browser Vision paths. The bridge obtains the verifier path only from `AETHER_BRIDGE_VISION_VERIFIER_FILE`, not a command argument; it fails startup if the verifier is absent or unsafe. The selected EOS runtime must advertise `vision-provenance-v1` and the selected bridge `vision-owner-uds-v1` in `--capabilities`; the focused EOS implementation advertises these tokens; selected IsOS must still pin and verify the exact candidate bytes.

IsOS creates a fresh 32-byte random `egia-vision` grant per deployment run, stored as 64 lowercase hex digits plus newline in a mode-0600 regular file. The separate mode-0600 verifier JSON has exact `schema_version:1`, `run_id`, `active_revision` (saved whole graph), `projection_revision` (EOS projection), `source_path`, `gate_path`, and `egia_vision_sha256` (SHA-256 of decoded grant bytes), with no secret. The bridge checks its `--run-id`, verifier owner/mode and every verifier field against an EOS runtime `vision_attest` private-socket response before binding owner readiness. That response is constructed atomically from verified managed launch metadata and the admitted gate route and contains `run_id`, `active_revision`, `projection_revision`, `runtime_stream_id`, `source_path`, `gate_path`, `gate_generation`, and `ready`. It returns generation `0` before the first delivery, using validated static gate/source identity and live health; there is no JPEG. A missing or unhealthy gate is unavailable. The bridge checks same-UID `SO_PEERCRED`, hashes the bearer bytes and compares with the verifier digest in constant time before WebSocket upgrade. It rejects a missing/malformed/wrong bearer with HTTP 403 `{"ok":false,"error":"owner_grant_denied"}`, stale run/revision/source/gate with HTTP 409 `{"ok":false,"error":"owner_binding_stale"}`, or unavailable EOS/health with HTTP 503 `{"ok":false,"error":"vision_unavailable"}`. Stop revokes the run grant, closes the owner listener and active sockets, clears queued frames, and unlinks its socket. Every bounded owner poll rechecks the private verifier and `ready:true` attestation; revocation or unready health closes an active socket with 1012 before another JPEG. A `changed:true` IPC generation must be strictly greater than the prior cursor or the bridge closes with 1008 and sends no JPEG. A bridge or EOS child restart in the same run rechecks the verifier; EOS rotates `runtime_stream_id`. A new IsOS run gets a different grant and run ID. No owner grant is accepted on the public TCP listener.

After valid HTTP 101 upgrade, the first masked text frame arrives within five seconds, is at most 4096 bytes, and has the existing `op:"subscribe"`, bound `gate_path`, EOS `revision` (= `projection_revision`), and fixed render/rate options. Optional `after_generation` and `after_runtime_stream_id` are **both fields of this subscribe JSON** and must be present together; the former is an unsigned 64-bit integer and the latter the previously attested UUID. EOS validates the subscription against a fresh `vision_attest` before any binary frame. The text reply is `{"type":"subscribed","graph_revision":"0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef","projection_revision":"aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa","runtime_stream_id":"8b4e9b70-5481-4d88-9bd6-4f07cb466ae4","source_path":"eos/hardware/camera/front","gate_path":"eos/interface/gate/front","gate_generation":0}` when no frame has yet been delivered; its generation may be positive after delivery. Static identity and stream are frozen atomically before this reply. An invalid first message, wrong gate/revision/render, missing cursor pair or stale stream sends a bounded text error, for example `{"type":"error","reason_code":"cursor_stale"}` for an old stream; other cases use `revision_mismatch`, `gate_inactive`, or `invalid_metadata` as appropriate, and closes with WebSocket 1008; EOS shutdown closes with 1012. No binary payload precedes `subscribed`. The browser TCP path may emit the additive attestation without owner authorization, but remains governed by its existing Origin/Host checks and never accepts the owner grant.

The frozen [EOS Q01 cases](../../../tests/fixtures/q01_vision_provenance/README.md) bind pre-frame generation `0`, exact 4096-byte metadata and 8-MiB JPEG limits, cursor pairs, old stream, wrong projection, public-path grant denial and stop behavior. They are design expectations, not implemented test results.
