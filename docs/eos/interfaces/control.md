# EOS v2 graph control

[中文](../../../docs_cn/eos/interfaces/control_cn.md) · [Hardware graph](hardware.md)

The IsOS-authored `1.0.0` graph admits manual controls, reusable primitives, and bounded skill sequences as EOS `v1.0` node types. EOS executes commands through its single dispatcher and never treats a node profile as a movement payload. IsOS owns graph edits and package resolution; EOS reads the applied graph without changing it.

New graphs may use [versioned primitive binding nodes](primitive-bindings.md) under `eos/dispatcher/<device class>` with an explicit output edge to one generic hardware device. The older `eos.control.primitive@v1.0` route on this page remains compatible for imported graphs.

## Node definitions

| Node type and placement | Setting | Type and unit | Purpose and validation |
| --- | --- | --- | --- |
| `eos.control.manual@v1.0` at `eos/control/manual` | `target` | `String`, canonical hardware path | Selects one base or manipulator. Its `references` must be exactly the target and EOS dispatcher paths. |
| `eos.control.primitive@v1.0` at `eos/control/primitive` | `target` | `String`, canonical hardware path | Selects one base or manipulator; exact target and dispatcher references required. |
| `eos.control.primitive@v1.0` | `movement_type` | `String`, mode ID | One of `body_velocity`, `relative_pose`, `joint_positions`, or `end_effector_pose`, and must be advertised by the target's movement modes. |
| `eos.control.skill@v1.0` at `eos/control/skill` | `steps` | `StringArray`, canonical primitive paths | Ordered sequence of 1–16 existing primitive nodes. References must be exactly those primitive paths and the EOS dispatcher. Repeated paths are allowed in the sequence. |

Manual and primitive nodes require `inputs.status` from dispatcher `status`, plus exactly one typed observation input from their target: `base_observation` (`BaseObservation`) or `manipulator_observation` (`ManipulatorObservation`). Both expose `request: ControlRequest` and `outcome: CommandOutcome`. Skill nodes require `inputs.status` from dispatcher `status` and expose `outcome: SkillOutcome`. These typed edges show the configured data relationship; movement is still released only by the dispatcher. Each node's `id`, `label`, `description`, `capabilities`, `references`, `inputs`, and settings retain the common field rules in the [hardware graph interface](hardware.md). Capabilities are `manual_control`, `primitive_control`, and `skill_sequence` respectively.

## Loopback API

The EOS-panel primitive binding demo uses this loopback bridge with `op: "primitive_typed"`; its exact header and payload are defined in [primitive bindings](primitive-bindings.md#bounded-runtime-command). A browser never calls a raw Dispatcher or a new `eos/gateway/primitives` route. The bridge forwards to private EOS IPC, where the active binding and target are checked before Dispatcher admission. EGIA's published gRPC `CapabilityService` is a separate ingress that converges on the same Dispatcher. The EOS [R03 managed admission](grpc.md#r03-governed-actuator-admission-target-contract) requires the IsOS saved active revision and a server-verified caller grant at that common boundary. The merged EOS bridge injects its private operator grant without exposing it to the browser; the merged IsosUI consumer follows the authorized result by command ID. The full per-binding U04 workbench remains a separate milestone.

The HTTP bridge listens at `127.0.0.1:16020` and forwards bounded JSON to EOS over its private Unix socket. Requests use `POST /api/eos/v2/control` with `Content-Type: application/json`; bodies are limited to 64 KiB. Browser calls require an approved `Origin`: `http://127.0.0.1:<ISOSUI_PORT>` and `http://localhost:<ISOSUI_PORT>` (default 16001), `http://127.0.0.1:<ISOS_HTTP_PORT>` (default 16000), `https://www.os-island.com`, or `https://os-island.com`. The bridge answers approved CORS/private-network preflights. The bridge allowlist excludes raw actuator, result and shutdown routes for browser and local HTTP callers. The EOS R03 private socket also rejects raw `manual`, `primitive`, `skill_execute`, `skill_result`, `dispatch`, `stop`, `manual_stop`, `cancel`, `result` and `skill_cancel` routes; internal owner-only `shutdown` remains. Every request must use the loopback bridge address.

For public `primitive_typed`, the browser supplies `header.payload_length_bytes` as a positive 1–16,384 byte compact UTF-8 payload length. The bridge parses the bounded public JSON, requires that field and a payload, rejects a declared or parsed payload length outside 1–16,384, then replaces the private header length with `serde_json`'s compact serialization length of the parsed payload before Unix IPC. The public declaration is a bounded hint rather than byte-exact proof across serializers; the private header is authoritative. The private runtime still requires an exact match with its own parsed-payload serialization and rejects malformed typed commands before Dispatcher. This bridge normalization is necessary because JavaScript and Rust render some finite JSON numbers differently, such as `0.000001` versus `1e-6`; the browser cannot use a wall-clock or string-character count to infer the private bytes. A missing, noninteger or out-of-range public length, or an absent payload, returns HTTP 400 with `{"ok":false,"error":"invalid typed request"}` before reading the grant. The bridge does not change typed payload values, graph binding, target, revision, command ID, deadline or grant checks.

## R07 managed browser submission

**R07 scoped implementation merged and qualified; [evidence is recorded in the shared TODO](../../island/implementation-todo.md).** For a managed, authorized `primitive_typed` request, EOS returns a correlated `DispatchResult` with `InProgress` only after the Dispatcher has durably reserved that exact command and accepted one bounded execution slot. No new public field or operation is added. The bridge's existing two-second private I/O bound and the browser's four-second timeout apply to this acknowledgement, not to the later physical call. EOS may return a terminal result instead if validation, admission or execution finishes before the reply; the browser must honor that exact status. A transport timeout or lost acknowledgement is **submission outcome unavailable**, never an invitation to resend movement. The browser retains the generated ID and may make only the authorized, read-only `result` request under the same current IsOS run and active revision. An `InProgress` acknowledgement proves durable reservation, not actuator release or physical completion.

EOS admits at most eight managed browser movement submissions that have returned or may return `InProgress`, counting workers waiting for the release gate and workers inside an adapter call. This limit is separate from private-socket client and safety-stop capacity; a busy movement lane cannot consume the safety path. For a new ID, EOS checks the exact active binding, target, typed payload limits, grant, run, revision and current deadline before reservation, obtains a slot, and durably writes `Prepared` before acknowledging `InProgress`. It rechecks live admission at the Dispatcher release gate, durably writes `Releasing` before one adapter call, and persists one terminal `Completed`, `Failed`, `Cancelled`, `Rejected` or `OutcomeUnknown` result before releasing the slot. If all eight slots are occupied, EOS records a terminal `Rejected` result for a valid new ID **in one atomic journal insert** containing the full command signature and managed identity, `phase:Terminal`, and `accepted:false`; there is no intermediate `Prepared` record, no worker and no adapter call. The Dispatcher implements this distinct crash-safe transition as `Journal::insert_terminal_rejection`, separate from the `Prepared` insert. If it cannot persist that rejection, EOS returns `{"ok":false,"error":"movement capacity unavailable"}` without acknowledging or releasing the command. An expired deadline or invalid admission is rejected before physical release. This asynchronous path still enters the existing Dispatcher; it does not create a second actuator route or change gRPC movement semantics.

For an already reserved ID, EOS compares the complete durable managed identity, including the submitted monotonic deadline, and exact typed arguments under the journal lock before capacity accounting. An identical request returns the current retained `InProgress` or terminal result without starting another worker or adapter call; changed identity or arguments return `Rejected` without release. A duplicate must still pass the current grant, run, revision and active-binding authorization checks. Worker creation failure after reservation checks the current journal phase under the same lock: it seals a still-`Prepared` entry as terminal `Rejected` before any acknowledgement, but returns an already-terminal `Cancelled` if Stop won the race and never overwrites it. If the required terminal write fails, EOS returns an unavailable error, inhibits movement and preserves the journal for recovery. A worker slot remains owned by this generation until durable terminal persistence, or until shutdown has fenced any later release and classified the unresolved call; a detached worker retains the old journal and adapter ownership while it exists and cannot enter a new generation.

On IsOS Stop, EOS enters R06 `Closing`: it closes new movement admission, registers the stop writer and starts the preemptive physical stop before waiting for ordinary movement workers or their journal lock. The browser worker checks this closure and its journal phase under the journal lock immediately before the durable `Prepared` → `Releasing` transition; a worker that passed that check before `Closing` retains its captured R06 generation/stop-epoch token and cannot use a fresh token afterward. Once the preemptive stop is scheduled, EOS may seal a still-`Prepared` command as durable terminal `Cancelled` under the same journal lock; a worker encountering that terminal record cannot call an adapter. A command already in `Releasing` is not reported `Completed` merely because Stop was requested. A confirmed MuJoCo dual-part stop advances the R06 generation/stop-epoch fence and blocks old-token release; the admitted mock adapter uses its latching stop. If MuJoCo stop is lost or unknown, the epoch may not advance and an already-in-flight old worker may still reach the old child until termination: EOS keeps admission closed, retains the unknown receipt, terminates and reaps that child within the R06 deadline. The worker retains only the old EOS process's adapter/session and captured generation; it cannot reconnect with a fresh generation, and the new IsOS run starts a distinct EOS process and child. Child termination is cleanup, not proof of a confirmed physical stop or movement outcome. A blocked worker never delays the R06 physical stop lane or the bounded child cleanup. On crash or restart, durable `Prepared` recovers as `Cancelled`, durable `Releasing` as `OutcomeUnknown` with movement inhibited, and neither is replayed. A new IsOS run rotates the grant and makes the old ID opaque to the browser even if its terminal journal record remains. The UI follows `InProgress` only through the authorized `result` route while fresh IsOS status proves the captured run and revision are still active; Stop, restart, an old run or a stale revision ends that follow-up without inventing completion.

If a physical release may have occurred but its terminal journal write fails, EOS latches movement inhibit, keeps the worker slot until durable sealing or generation exit, retains old journal/adapter ownership while the physical call remains live, and marks that ID's browser read **result unavailable** rather than returning stale `InProgress` or an unpersisted terminal guess. No new movement may be admitted. A later same-run duplicate cannot start another worker and receives the same unavailable classification. EOS may durably seal the original `Releasing` record as `OutcomeUnknown` only after the old physical call has returned, a confirmed stop epoch has fenced it, or an unknown-stop cleanup has reaped its old child; successful sealing makes authorized reads return that durable unknown terminal. If sealing still fails, live reads remain unavailable and shutdown reports the R06 stop result from its independent physical proof, never a fabricated movement success. On process restart, the existing durable `Releasing` recovery writes terminal `OutcomeUnknown` and retains movement inhibit before readiness; an unclean recovery write fails startup. Fault-injection tests must cover the terminal write failure both before and after physical release, the read and slot behavior, the late adapter response, and recovery without replay.

If a queued worker decides **before** `Releasing` that its deadline expired, health failed or `Closing` began, but writing the terminal result fails, the durable record remains `Prepared`. EOS fences that ID against `Releasing` and every adapter call, latches movement inhibit for the live generation, keeps its slot until a durable seal or generation exit, and makes authorized result reads and identical duplicate submissions return `{"ok":false,"error":"result unavailable"}` instead of stale `InProgress`; a duplicate never creates a worker. It retries a durable terminal `Rejected` for expiry or health rejection, or `Cancelled` for Stop, under the journal lock, with Stop's `Cancelled` winning a race. A successful seal releases the slot and makes that terminal result readable. If the generation exits before sealing, normal journal recovery converts durable `Prepared` to terminal `Cancelled` without release before readiness; failure to persist recovery fails startup. Inject the pre-release terminal-write fault at deadline, health and Stop rejection, then test stale-read opacity, duplicate nonrelease, slot retention, durable retry and restart recovery.

## R07 authorized browser result

**Q01 target design — not implemented:** Browser `primitive_typed` and public `result` keep their published 1–128 UTF-8 byte `command_id` contract. The selected bridge will emit a sanitized [browser command event](events.md#q01-browser-command-correlation--eos-producer-implemented) after checking a valid matching private result. Safe 1–64 byte ASCII IDs outside the reserved `h_` prefix appear exactly as P06/P07 `correlation_id`; other valid IDs map to the documented deterministic opaque token. The bridge does not reject a previously valid ID or copy arbitrary text into the log.

R07 extends the existing `POST /api/eos/v2/control` route with one read-only public `op: "result"` follow-up for a `primitive_typed` command. After checking the exact public fields below, the bridge rewrites that operation to private `op: "primitive_result"` and injects its current private `operator-control` grant. The owner socket continues to reject historical raw `op: "result"` with `operation has no governed managed route`; a browser cannot select `primitive_result` directly. The bridge keeps the existing 64 KiB body and two-second I/O bounds and applies the same Host and approved-Origin checks used for `primitive_typed`. Browser JSON containing `authority_grant`, an arbitrary target or a raw dispatcher operation remains forbidden. The bridge does not store results or invent terminal status.

| Request field | Type | Unit | Purpose, default and validation |
| --- | --- | --- | --- |
| `op` | string | — | Required exact `result`; no default. |
| `command_id` | string | command identity | Required 1–128 UTF-8 bytes, matching the submitted typed header; no default. |
| `active_revision` | string | saved graph SHA-256 | Required 64 lowercase hex digits equal to EOS's current IsOS active revision; no default. |

```json
{"op":"result","command_id":"move-1","active_revision":"aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa"}
```

The private `primitive_result` request has exactly `op`, `command_id`, `active_revision` and `authority_grant`. The first three retain the public field constraints, except private `op` must equal `primitive_result`; `authority_grant` is a required 64-character lowercase hex bearer string supplied only by the bridge, with no browser default. The private runtime verifies it as `OperatorControl`, checks the active revision, and uses a journal lookup that atomically checks the current run, stored active revision, role, `Movement` kind, and `PrivateBridge` ingress before returning `DispatchResult`. The existing `gateway_operation_authorized` helper checks run and role but does not expose ingress; R07 adds an explicit private-binding result lookup rather than inferring provenance from the primitive name. An absent ID, another role or run, a gRPC movement, a legacy record, or a stop ID yields the same bounded `{"ok":false,"error":"unknown command ID"}` without disclosing which condition applied. No lookup calls an adapter or replays a command.

```json
{"ok":true,"result":{"command_id":"move-1","status":"InProgress","reason":null}}
```

A successful result has the existing `DispatchResult` shape: `command_id` is the same bounded identity, `status` is exactly `Completed`, `Failed`, `Cancelled`, `Rejected`, `InProgress`, or `OutcomeUnknown`, and `reason` is null or a UTF-8 string. The read path rejects a reason exceeding 512 UTF-8 bytes and rejects the full serialized `{"ok":true,"result":...}` response exceeding 4 KiB; it never truncates or alters the durable journal entry. Both return `{"ok":false,"error":"result unavailable"}`. The bridge also refuses any private result response over 4 KiB with HTTP `502` and the same fixed error. `InProgress` remains nonterminal; `Failed` is a terminal failure; `OutcomeUnknown` is never converted to success. After a new IsOS run rotates grants, an old command is opaque. The UI may poll only while its saved and active revisions agree; a bridge outage or stopped runtime remains visibly unavailable, while deployment Stop stays on its existing IsOS governed path. R06 separately qualifies physical stop before MuJoCo movement becomes visible.

The public result route returns HTTP `400` with `{"ok":false,"error":"invalid result request"}` for malformed or extra public keys, and HTTP `403` with the existing bridge error for a forged `authority_grant`, invalid Host or disallowed Origin. Missing or unreadable bridge grant returns HTTP `503` with `{"ok":false,"error":"operator control unavailable"}` before IPC. A private grant rejected by EOS returns HTTP `200` with `{"ok":false,"error":"operator control grant required"}`; a stale revision returns HTTP `200` with `{"ok":false,"error":"stale active revision"}`; opaque IDs return HTTP `200` with `{"ok":false,"error":"unknown command ID"}`. The bridge returns HTTP `502` with `{"ok":false,"error":"runtime unavailable"}` for private IPC transport failure. These result-route errors are bounded fixed strings; no private grant or journal data is echoed.

The following historical manual/primitive examples are retained to read legacy graphs; the EOS R03 deployed private socket rejects these operations. A manual or primitive request had `op: string` (`manual` or `primitive`), `node_path: string` (canonical admitted control node), `command_id: string` (unique 1–120 byte dispatcher ID), `deadline_monotonic_ns: u64` (EOS monotonic nanoseconds), and `movement: object` (one specific typed movement shape defined in [hardware v2](hardware.md)). EOS replaces any client target with the node's configured target, checks a primitive's movement type, then asks the dispatcher to enforce health, limits, deadline, journaling, and stop. The response is `{"ok":true,"result":{"command_id":"move-1","status":"OutcomeUnknown","reason":null}}` or `{"ok":false,"error":"..."}`. `OutcomeUnknown` means transport acceptance did not establish physical completion.

```json
{"op":"primitive","node_path":"cores/eos/layers/control/groups/primitive/nodes/base_velocity_0","command_id":"move-1","deadline_monotonic_ns":5000000000,"movement":{"type":"body_velocity","x_m_s":0.1,"y_m_s":0.0,"yaw_rad_s":0.0,"valid_for_ms":100}}
```

`manual_stop` takes only `op` and the admitted manual `node_path`; EOS stops its configured target and responds with `{"ok":true}` or an error. It does not accept a hardware path supplied by the browser.

Read-only `status` takes `{"op":"status","node_path":"<canonical hardware path>"}` and returns `{"ok":true,"status":{"state":"stopped","active_command_id":null}}`. `state` is one of `starting`, `ready`, `stopped`, or `faulted`; `active_command_id` is a string or null. This reports adapter lifecycle independently of `health`. After `manual_stop` or `stop`, fresh typed base and manipulator observations remain available while the adapter is healthy, but movement stays latched off until EOS restarts and rebuilds the adapter. A stale or invalid observation still fails and degrades health. Browsers may call `status`, `observe`, and `health` without receiving a raw actuator route.

A skill execution request has `op: "skill_execute"`, `node_path: string` (admitted skill), `execution_id: string` (unique 1–64 ASCII letters, digits, period, dash, or underscore), and `steps: array` of 1–16 objects containing only `movement`. The array length and each movement type must match the graph's ordered primitive list before any step starts. Each step receives a five-second monotonic deadline and a derived command ID `<execution_id>:<index>`. The request returns immediately with `{"ok":true,"execution":{"execution_id":"demo-1","status":"queued","results":[],"reason":null}}`; status may already be `running`. A step continues only after a confirmed `Completed` outcome. A rejected or uncertain outcome ends the skill and stops that step's target.

```json
{"op":"skill_execute","node_path":"cores/eos/layers/control/groups/skill/nodes/demo_0","execution_id":"demo-1","steps":[{"movement":{"type":"body_velocity","x_m_s":0.1,"y_m_s":0.0,"yaw_rad_s":0.0,"valid_for_ms":100}},{"movement":{"type":"joint_positions","joint_names":["joint1","joint2","joint3","joint4","joint5","joint6"],"joint_positions_rad":[0,0,0,0,0,0],"max_speed_rad_s":0.2}}]}
```

`skill_result` and `skill_cancel` take `{"op":"skill_result","execution_id":"demo-1"}` or the same body with `skill_cancel`. They return the same `execution` shape. `status` is `queued`, `running`, `completed`, `failed`, or `cancelled`; `results` is an ordered array of dispatcher `DispatchResult` records, and `reason` is `null` or a bounded failure explanation. Cancellation requests a physical stop for the active primitive. At most eight skills run concurrently; the latest 128 results are retained, evicting the oldest terminal result on capacity. EOS cancels and joins active skills before simulator shutdown.
