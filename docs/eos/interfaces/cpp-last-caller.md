# C++ last-caller contract for EOS 0.x

[中文](../../../docs_cn/eos/interfaces/cpp-last-caller_cn.md) · [Interface catalog](README.md) · [Q02 design](../design/runtime/cpp-last-caller.md) · [Last-caller inventory](../maintenance/cpp-last-caller-inventory.md)

Q02 may remove an old `adapters/eos-cxx/` component only after its final compiled, installed, runtime, test and documented caller is identified, equivalent Rust tests pass, and the reduced opt-in C++ side chain still builds. A deliberately excluded engine, such as WorkflowService, ActionList or model-weight execution, has no claimed Rust parity and therefore remains while it has a component-level contract or any active caller. A no-caller implementation detail without a component-level contract may be removed only after the inventory proves that status and independent review explicitly approves the exception. A physical driver with a remaining caller stays. No directory-level deletion is allowed until every contained target, source, test and install reference has an individual recorded disposition.

The default EOS package installs the five Rust executables behind the public `eosd`, `eos-config`, `eos-north-http`, `eos-cli` and `eos-repl` launchers. The active `crates/aether-hal/cxx` mock and `aether_adapter_v1` C ABI remain part of Rust. The C/C++ host skill ABI headers, `eos_skill_sdk`, `EOS::SkillABI`, `EOS::SkillCpp`, `EOS::SkillSDK`, CMake package files and exported symbols remain available to skill authors and the Rust verified worker. The old C++ hardware and ROS/vendor side chain remains opt-in until hardware-backed parity exists.

When the SDK build fetches nlohmann JSON, its install includes those headers and defines the imported dependency target for consumers from the same install prefix. When it uses a system package, `EOSSkillConfig.cmake` resolves that system dependency. The installed SDK consumer test must use the installed prefix without separately staging a fetched dependency. Installed `docs/` and `docs_cn/` retain their sibling layout so authored bilingual relative links resolve.

The EOS protobuf sources, generated schemas, contract manifest and HTTP OpenAPI descriptions remain available to Rust and EGIA. The old north HTTP server's published `/v1/eos/*` and `/v2/eos/*` REST, SSE and WebSocket routes are a distinct opt-in interface: retain its implementation while supported unless equivalent route-level implementation and tests pass, or an explicit contract deprecation decision updates the English/Chinese HTTP contract, install and launcher expectations, OpenAPI status and tests. The Rust browser bridge's `/api/eos/v2/*` routes do not prove that parity. Q02 changes no protobuf package, service, method, field number, ProtoJSON name, socket protocol identity, skill ABI layout or symbol. A source filename can change only after every code, test, script, install and bilingual documentation reference is updated. The historical `examples/v2/mujoco-isos.toml` must remain a byte-identical read-only `1.0.0` compatibility fixture, even if it gains a topic-named alias.

For every deletion, the [inventory](../maintenance/cpp-last-caller-inventory.md) records the individual target, last caller, Rust parity or reviewed no-contract exception, required command and result, and disposition. Missing parity evidence, an active caller or an unreviewed exception blocks deletion. A clean temporary-prefix install must include real paired English/Chinese guide files and required contract resources. Correct stale ownership and readiness statements in `docs/eos/develop/README.md`, `docs/eos/develop/build-and-run.md`, `docs/eos/design/runtime/foundation.md` and their Chinese counterparts before Q02 closes; date historical claims, check route terminology and validate links. The install, SDK, schema, ABI and EGIA import gates must fail when required resources are missing or changed.
