# EOS reader features and identities

[中文](../../../docs_cn/eos/interfaces/reader-features_cn.md) · [Node profile](hardware.md) · [Setup adapter](setup-v1.md) · [Cross-repository P05 task](../../island/implementation-todo.md)

**P05 owner contract — EOS probe slice implemented.** IsOS owns the saved graph, verified package pins, deployment preflight and public rejection. EOS owns what its selected executables can actually read. The local probes below run before any EOS child starts; they report reader support, not live health or permission to actuate. The exact built-in `supported_node_types`, setup identity reader fields and `mujoco-child-v2` are implemented here; graph-derived admission and diagnostics remain IsOS work in P05.

## Probes and fields

IsOS executes the exact selected `aether-profile`, `aether-runtime` and `aether-config-server` binaries with `--capabilities`, a bounded timeout, bounded stdout, no shell and no graph input. Each writes one JSON object and exits zero without opening a socket or device. `aether-profile setup --json` also accepts the existing schema-1 identity request `{"schema_version":1,"op":"identity","core":"eos"}` on stdin; it returns the same reader sets for that binary in its `identity` object. The HTTP bridge only relays control and Vision data. Its `--capabilities` is queried for transport features when that child is selected, but its graph/type scalar fields are historical metadata and it is not a graph reader.

```json
{"product_version":"0.2.0","graph_version":"1.0.0","node_type_version":"1.0","supported_graph_versions":["1.0.0","0.1.0"],"supported_node_type_versions":["1.0","0.1"],"supported_node_types":["eos.control.manual@v1.0","eos.control.primitive@v1.0","eos.control.skill@v1.0","eos.dispatcher.control@v0.1","eos.dispatcher.control@v1.0","eos.dispatcher.primitive_base@v0.1","eos.dispatcher.primitive_base@v1.0","eos.dispatcher.primitive_manipulator@v0.1","eos.dispatcher.primitive_manipulator@v1.0","eos.hardware.base@v0.1","eos.hardware.base@v1.0","eos.hardware.camera@v0.1","eos.hardware.camera@v1.0","eos.hardware.manipulator@v0.1","eos.hardware.manipulator@v1.0","eos.interface.camera_gate@v0.1","eos.interface.camera_gate@v1.0","eos.process.backend@v1.0"],"binary":"aether-profile","features":["short-paths","node-types","data-idl","primitive-binding","catalog","setup-v1","graph-0.1-reader"]}
```

The example is illustrative JSON; the `supported_node_types` wire array is sorted lexicographically by complete ID. The frozen fixture contains the exact sorted arrays for each reader. `aether-profile` setup identity wraps these same fields with `core:"eos"` and `setup_schema_version:1` inside the existing `{"schema_version":1,"ok":true,"diagnostics":[],"files":[],"identity":{...}}` reply. A malformed identity request keeps the existing schema-1 `ok:false` diagnostic with `path`, `code` and `message`; it returns no files.

| Field | Type and unit | Purpose, absence and validation | Compatibility |
| --- | --- | --- | --- |
| `binary` | exact executable basename / — | Identifies which selected file answered; must equal the name IsOS invoked. | Setup identity uses `core:"eos"` instead. |
| `product_version` | semantic version string / — | Build identity for display and evidence; must be nonblank. | IsOS does not require one exact EOS product version. |
| `graph_version`, `node_type_version` | string / graph version and suffix version | Historical scalar aliases, presently `1.0.0` and `1.0`; never broaden an authoritative array. | Only a known legacy reader with no corresponding array may use the scalar fallback below. |
| `supported_graph_versions` | unique string array / exact graph versions | Reader's admitted envelopes, exactly `1.0.0` and `0.1.0` in this slice. Empty, malformed or duplicate arrays fail preflight. | An array, when present, is authoritative. It does not admit unknown future graph versions. |
| `supported_node_type_versions` | unique string array / exact `@v` suffix versions | Registry suffixes, exactly `1.0` and `0.1` in this slice; a suffix never grants an unlisted type. | An array, when present, is authoritative. |
| `supported_node_types` | unique sorted string array / exact EOS IDs | The 18 built-in EOS registrations listed below; no IsOS, EGIA or package-contributed ID is claimed. | New P05 field. Missing on a known legacy executable permits only the exact legacy fallback, not `@v0.1` admission. |
| `features` | unique string array / tokens | Implemented protocol and launch behaviors for that binary; no implied feature from product version. Unknown required token fails preflight. | An absent array is not a feature set; known legacy fallback is narrow. |
| `setup_schema_version` | positive integer / schema version | Present only in setup identity, currently `1`; identifies the existing setup request/reply envelope. | Preserve schema 1 and existing diagnostics. |

The 11 legacy built-ins are `eos.hardware.camera@v1.0`, `eos.hardware.base@v1.0`, `eos.hardware.manipulator@v1.0`, `eos.dispatcher.control@v1.0`, `eos.dispatcher.primitive_base@v1.0`, `eos.dispatcher.primitive_manipulator@v1.0`, `eos.control.manual@v1.0`, `eos.control.primitive@v1.0`, `eos.control.skill@v1.0`, `eos.process.backend@v1.0` and `eos.interface.camera_gate@v1.0`. The seven new built-ins are `eos.hardware.camera@v0.1`, `eos.hardware.base@v0.1`, `eos.hardware.manipulator@v0.1`, `eos.dispatcher.control@v0.1`, `eos.dispatcher.primitive_base@v0.1`, `eos.dispatcher.primitive_manipulator@v0.1` and `eos.interface.camera_gate@v0.1`. `eos.process.mujoco@v0.1` and historical MuJoCo-specific types are contributed by a package and are absent from the static list. IsOS passes a P01-verified sidecar path with `--node-types <path>` to the selected profile binary, then requests `setup catalog`; that exact result checks contributed IDs, placement and settings. A version suffix or an unverified sidecar is never enough.

## Required features by selected graph

The executable probes retain their current feature tokens. `aether-profile` advertises `short-paths`, `node-types`, `data-idl`, `primitive-binding`, `catalog`, `setup-v1`, `graph-0.1-reader`. `aether-runtime` advertises `short-paths`, `node-types`, `data-idl`, `primitive-binding`, `log-dir`, `vision-gate`, `graph-0.1-reader`, `mujoco-child-v2`, and `managed-control-grants`. `aether-config-server` advertises `short-paths`, `node-types`, `data-idl`, `primitive-binding`, `catalog`, `graph-0.1-reader`. `aether-http-bridge` advertises `short-paths`, `node-types`, `data-idl`, `primitive-binding`, `vision-ws`; it does not advertise `graph-0.1-reader` because it never parses the graph. Keep the order shown for wire compatibility, but consumers compare sets.

For a `0.1.0` EOS projection, IsOS requires `graph-0.1-reader`, `node-types` and `data-idl` on the profile tool and on each selected graph-reading child: runtime and config server. It also requires `setup-v1` and `catalog` on the profile tool. For a selected `0.1.0` managed EOS runtime, IsOS additionally requires exact `managed-control-grants` on that runtime at its process `/node_type`; a missing feature is `reader_feature_unsupported` before active-child stop or grant issuance. The token confirms EOS can verify the selected schema-2 generation and run-scoped grants; it does not itself grant movement or imply EGIA, bridge or simulator support. A selected runtime launch with `--log-dir` additionally requires `log-dir`. A graph containing either EOS primitive-binding type requires `primitive-binding` on runtime; one containing the camera gate requires `vision-gate` on runtime.

For either graph version, a graph launching a verified v2 MuJoCo child through `eos.process.mujoco@v0.1`, `eos.process.mujoco@v1.0`, or the legacy built-in `eos.process.backend@v1.0` pinned by `settings.package:"island/mujoco-sim"` and `settings.version:"0.1.1"` requires runtime `mujoco-child-v2`. This token confirms the existing direct-child v2 socket path and does not claim R05 strict-socket behavior. Every enabled `aether-http-bridge` child requires `vision-ws`, even without a camera-gate node; a disabled bridge creates no requirement. Required features follow actual selected nodes and launch arguments; an absent optional child or node creates no feature requirement.

For a known `1.0.0` graph, use the exact legacy type registry and package sidecars. A reader without arrays may use its scalar `1.0.0`/`1.0` identity only for a graph whose EOS IDs are known legacy identities and whose required feature set is empty under this contract. A bridge with only scalar fields is acceptable because it does not read the graph; every enabled bridge still needs `vision-ws` for either graph version. A malformed array cannot fall back to a scalar. Unknown future graph envelopes, IDs, type suffixes, malformed probes and missing required features fail before launch. This fallback neither rewrites saved bytes nor admits graph-authored skill sequence execution. IsOS's existing fixed `short-paths` process check remains in force separately from this derived feature set.

IsOS checks the saved graph and P01 verified pins first, then the exact selected binary probes and EOS catalog with verified sidecars, then owner Validate/Render and generated snapshot verification, all before stopping active children or spawning replacements. Run and Restart recheck the selected binary hashes and advertised sets against the immutable P04 generation; a changed executable requires explicit Apply to select a new generation. IsOS owns public `{code,path,stage}` diagnostics that identify the executable, node JSON Pointer, unsupported type or feature and supported set. EOS setup retains its schema-1 `{path,code,message}` diagnostics and never emits raw graph, local paths, secret values or package contents. An upgrade recommendation names a release only if IsOS has an exact verified compatible release; otherwise report the required support without guessing a product version.

The [frozen P05 fixture](../../../tests/fixtures/reader_features/README.md) covers identities, feature derivation, known legacy fallback, exact contributed types and negative preflight paths. Implementation must compare the real selected binaries, not a mock version string, and replay one `0.1.0` and one safe `1.0.0` graph before the P05 gate closes.

**Q01 target design — not implemented:** When IsOS selects `vision_evidence.gate_path`, it additionally requires exact `vision-provenance-v1` from the selected `aether-runtime` and `vision-owner-uds-v1` from the selected `aether-http-bridge`. The former attests atomic `vision_attest`, saved/projection revisions, stream and frame metadata; the latter attests the distinct owner-only UDS listener, run-scoped bearer verification and public/owner route separation. Existing `vision-gate` and `vision-ws` do not imply either feature. Missing features produce `reader_feature_unsupported` at the respective selected process `/node_type` before grant issuance or active child replacement. The current binaries do not advertise these Q01 tokens.
