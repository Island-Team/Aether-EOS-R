The EOS R03 managed-admission code below merged through [PR #315](https://github.com/Island-Team/Island-eos/pull/315), and the IsOS grant handoff merged through [PR #52](../../island/retired-repository-references.md#ref-aee8e4a3d593). Their post-merge clean-home replay qualified R03; R05/R06 and the scoped M3 exit were subsequently qualified; see the [M3 record](../../island/m3-qualification.md). The published protobuf contract and opt-in C++ server remain historical compatibility surfaces. EGIA's current Python client requires health, Gateway discovery/resources/status, and CapabilityService capability discovery before it can report ready.

The sections through **Assigned listener ports** describe the published C++ service and HTTP projection as a compatibility reference. They do not imply that the Rust runtime or current HTTP bridge implements every historical RPC or REST/SSE route. The final section specifies the implemented Rust subset and its lifecycle.

## Transport ownership

The published EOS process-facing protobuf services are v1 `GatewayService`, `SkillService`, and `WorkflowService`, plus v2 `CapabilityService`. The opt-in C++ server exposes all four on one historical gRPC listener; the Rust listener serves only the R02 subset below. The separate historical `eos-north-http` contract projects supported v1 REST operations and v2 capability REST and SSE operations, including `/v2/eos` capability routes:

- native gRPC on `[gateway].grpc_port`, owned by `eosd`;
- HTTP/1.1 and SSE on `[north_http].port`, owned by `eos-north-http`.

The north HTTP process calls only the public gRPC services; it does not link or bypass into EOS domain services. Typed protobuf envelope fields use their ProtoJSON names, such as `deviceId`, `frameCount`, and `absoluteFrame`. Schema-owned values carried in `google.protobuf.Struct` retain their documented JSON keys, including `schema_version` and primitive argument snake_case names. ProtoJSON base64-encodes protobuf `bytes`, including camera JPEG pictures.

The domain pages document the native protobuf/gRPC services. The HTTP page documents strict ProtoJSON routes and the SSE projections of `WatchResource`, `WatchExecution`, `FollowExecutionJournal`, and `MonitorExecutions`.

Native clients use packages `island.eos.v1` and `island.eos.v2` from the generated contracts under `share/eos/contracts/eos/`. Unary and streaming calls accept optional `x-request-id` metadata for correlation. Clients must set deadlines, cancel streams they no longer consume, preserve `uint64` sequence/revision values, and branch on gRPC status codes rather than diagnostic message text. Domain rejection and terminal failure are normally successful RPC responses carrying typed status fields; malformed, missing, conflicting, or unavailable requests use canonical gRPC statuses documented by each service page. The v2 [capability operations](capabilities.md) use the Dispatcher command ID as `operation_id`; their watch is a current-state and terminal stream without a cursor. Workflow clients bootstrap ActionList/fact state with `GetRuntimeSnapshot.action_list_cursor`, then resume the manager-wide `WatchActionListEvents` stream with the last durably applied `{epoch, sequence}`. Epoch mismatch, future cursor, and retention expiry require a new snapshot as documented by the [WorkflowService recovery algorithm](workflow.md#resnapshot-and-resume-algorithm). The standalone simulator retains its separately documented JSON and binary formats. The gateway binds loopback TCP by default and may also bind an optional owner-controlled Unix domain socket as documented by the [northbound runtime](../design/runtime/northbound.md). The inherited IPC descriptor used by supervised external skills is a separate private interface and is not the EOS gRPC listener.

See the [north HTTP contract](external/http.md) for every route, error mapping, SSE cursor rule, CORS behavior, request ID, and browser security boundary.


## Read, compute, and write admission

The gRPC server is an adapter over EOS-owned domain services. Read RPCs use EOS projections and retained stores: discovery, status, resource/history reads, watches, navigation reads, and skill/workflow queries do not synchronously query a hardware driver. Hardware-backed body data is sampled by EOS on its runtime cadence. A read requiring such a sample fails when it is missing, unhealthy, or more than one second old. Successful body reads expose the age in milliseconds as initial gRPC metadata `eos-sample-age-ms`; the HTTP adapter forwards it as `Eos-Sample-Age-Ms`. This leaves resource JSON schemas unchanged. Reads still check resource identity, freshness, bounds, and response size.

**R04 implementation slice:** the default Rust listener adds a seven-method [SkillService subset](skills.md#r04-default-rust-subset--implementation-slice) over an IsOS-selected native host catalog. It reuses R03 `authorization` and `x-eos-active-revision` metadata on Start/Terminate, does not change `skills.proto`, and routes declared primitive calls through the same Dispatcher. The advertised `host-skill-abi-v2` feature means primitive-only descriptors with required Rust worker/broker enforcement; descriptors declaring resource, source, inference, SIGNAL or community callbacks are rejected until those owners exist. Other published SkillService methods and WorkflowService remain unavailable.

Camera capture and perception inference are bounded compute calls. They may use a validated snapshot and call a model provider; they have deadlines, cancellation, and capacity limits. They are not treated as unrestricted cache reads.

Capability submissions and cancellation, waypoint changes, skill execution and signals, and workflow submissions are writes. Their gRPC handlers call the owning admission path, which checks schemas, capabilities, target, safety policy, idempotency, and queues before state changes. Handlers do not call the hardware HAL directly. A transport request ID correlates logs; operation-specific command and request IDs retain their documented replay rules.

EOS treats clients reaching its configured local listener as trusted under deployment policy. Loopback TCP does not distinguish local users. For same-host clients, prefer the optional owner-controlled Unix socket. Per-client grants require a separate access-control design; there is no permissive security placeholder in the write path.

## Assigned listener ports

EOS-owned listeners are contiguous and must remain so:

| Port | Owner | Protocol |
| --- | --- | --- |
| `16200` | `eosd` | EOS gRPC |
| `16201` | `eos-north-http` | browser REST/SSE |

Ports in model-provider or test fixtures are not EOS listeners and are outside this allocation.

Unknown methods, resources, schemas, versions, fields forbidden by a schema, enum values, targets, and primitive names fail closed. Validation happens before admission or provider work. Empty and optional values retain the meaning defined by their schema; transports must not turn absence into a default unless the contract explicitly defines one. Size, deadline, cancellation, ordering, and degraded-dependency behavior are defined by the focused interface page and the owning runtime module.

See the [contract catalog](contracts.md), the [runtime overview](../design/runtime/README.md), and the [extension overview](../develop/ext/README.md) for loading, execution, and device-side dataflow.

## Rust 0.x gateway — merged R02 subset

The Rust gateway uses the existing generated `island.eos.v1` and `island.eos.v2` packages. It serves standard gRPC health and the eleven RPCs listed below. For EGIA startup, Gateway `Discover`, `ListResources`, `GetStatus`, and CapabilityService `ListCapabilities` are available before advertising `SERVING`. Responses project one admitted graph generation, robot identity, node descriptions, health, and exact primitive bindings; they never fabricate a missing device or capability. Capability operations map to the durable Dispatcher command ID and its accepted, rejected, terminal, or uncertain outcomes. Other published services remain documented here but are not advertised ready until their Rust handlers pass parity tests.

Bind only after graph, adapter, and journal admission. Publish one complete immutable discovery generation per runtime start. A rejected candidate cannot replace a serving listener's generation; live health may degrade without changing binding identity. A missing simulator, stale observation, unknown binding, incompatible schema, or expired deadline produces the documented typed status or canonical gRPC error before actuator release. Shutdown changes health to `NOT_SERVING`, stops new writes, finishes or cancels bounded work, invokes Dispatcher stop, and closes streams. Retain existing protobuf field numbers, ProtoJSON names, method names, and service package IDs. Additive optional fields require old-client fixture tests.

### R02 frozen Rust subset

The [R02 design](../design/runtime/grpc-gateway.md), [first-use replay](../develop/grpc-gateway.md), and [machine cases](../../../tests/fixtures/r02_grpc_gateway/README.md) define this slice. The authoritative wire files remain `gateway.proto`, `capabilities.proto`, `robot/{descriptor,primitive}.proto`, `system/resource.proto`, and `perception/camera.proto` under `share/eos/contracts/eos/`; R02 changes no package, service, method, field number, or ProtoJSON identity. The Rust listener implements gRPC health `Check` for the aggregate empty service name, `island.eos.v1.GatewayService/{Discover,ListResources,GetStatus,ReadResource,WatchResource,CaptureFrames}`, and `island.eos.v2.CapabilityService/{ListCapabilities,SubmitOperation,WatchOperation,GetOperation,CancelOperation}`. The listener binds loopback by default; an optional owner-permissioned Unix socket is a separate configuration. It never exposes the private MuJoCo socket. Other published methods fail `UNIMPLEMENTED` until implemented, except `SkillService.ListSkills`: while the Rust skill catalog is unavailable it returns `UNAVAILABLE`, which the existing EGIA client explicitly treats as an optional empty skill set. Health for an unavailable service name is `NOT_SERVING`.

The required method and message identities are fixed by the published protos:

| RPC | Request → response | EGIA use and R02 result |
| --- | --- | --- |
| health `Check` | `HealthCheckRequest` → `HealthCheckResponse` | Empty service must be `SERVING` only after complete discovery. |
| `Discover` | `Empty` → `DiscoverResponse` | Parses robot, device and inline primitive bindings. |
| `ListResources` | `Empty` → `ListValue` | Parses `{uri, class}` entries; an empty list is valid. |
| `GetStatus` | `Empty` → `Struct` | Requires matching `robot_id`/`robot_name`, nonempty `status`/`version`/`started_at`; reports current health. |
| `ReadResource` | `ResourceRequest` → `Struct` | Reads one listed, validated URI. |
| `WatchResource` | `ResourceRequest` → stream `ResourceChanged` | Uses URI notifications, then re-reads. |
| `CaptureFrames` | `CaptureFramesRequest` → `CaptureFramesResponse` | Validates one/two distinct JPEG frames. |
| `ListCapabilities` | `ListCapabilitiesRequest` → `ListCapabilitiesResponse` | Joins exact capability names to Discover bindings. |
| `SubmitOperation` | `SubmitOperationRequest` → `Operation` | Owns one Dispatcher command ID. |
| `WatchOperation` | `OperationRequest` → stream `Operation` | Follows current then terminal state. |
| `GetOperation` | `OperationRequest` → `Operation` | Recovers a lost Submit/watch response by ID. |
| `CancelOperation` | `OperationRequest` → `Operation` | Cancels only the named command. |

A minimal camera-only admission can return `Discover` as `{"robot":{"id":"demo","name":"demo-0","model":"eos-runtime","state":"idle","health":"ready","estop":false,"description":"EOS graph runtime demo-0"},"devices":[{"id":"front","class":"camera","part":"front","state":"idle","health":"ready","description":"Front camera"}]}`, `ListResources` as `[]`, `GetStatus` as `{"robot_id":"demo","robot_name":"demo-0","version":"0.2.0","started_at":"2026-11-01T00:00:00Z","status":"ready"}`, and `ListCapabilities` as `{"capabilities":[]}`. These are ProtoJSON examples of a complete discovery without an invented actuator or semantic resource. A `CaptureFrames` request uses `{"robotName":"demo-0","deviceId":"front","frameCount":1}`; a cold camera returns gRPC `UNAVAILABLE`, not an empty `vision.snapshot`.

The aggregate health entry stays `NOT_SERVING` until profile, exact graph revision, node registry, direct child and adapters, durable Dispatcher journal, and one complete discovery projection are admitted. Current startup fails incomplete admission before listener bind and emits no ready event; a future pre-admission bind must answer `NOT_SERVING` and reject required RPCs with `UNAVAILABLE`. An open port, a live process, or a simulator socket is insufficient. `Discover`, `ListResources`, `GetStatus`, and `ListCapabilities` project the same immutable admitted generation. R02 does not hot-swap an applied graph: an invalid candidate is rejected before publication, while the existing listener retains its last complete generation; live health can degrade independently. The graph supplies robot `id` and `name`; until the graph has physical model metadata, `model` is the literal `eos-runtime` and `description` identifies an EOS graph runtime, never a hardware model claim. `GetStatus` includes `robot_id` and `robot_name` equal to Discover, nonempty `status` and `version` (`0.2.0`), and RFC 3339 `started_at` for EGIA. EGIA compares `robot_name` during rediscovery; omitting it is an invalid projection. Device IDs, classes, parts, descriptions and primitive bindings come only from admitted profile nodes and verified type metadata. A device with no actionable binding remains discoverable with its actual health. `ListCapabilities` carries the exact same admitted robot/device primitive targets and availability; no capability name may point at an absent or different binding. A current unhealthy device may make a capability unavailable without changing identity.

`ListResources` returns a `google.protobuf.ListValue` of bounded `{uri, class}` descriptors in deterministic URI order. A URI begins `robots/{robot.name}/` and is listed only when its producer and schema are admitted. In particular, no empty `world.snapshot`, detection, or ASR value is invented to satisfy EGIA. `ReadResource(ResourceRequest.uri)` returns the latest validated `google.protobuf.Struct` for a listed URI; an unknown URI is `NOT_FOUND`, and a declared URI with no healthy fresh product is `UNAVAILABLE`. A hardware-backed sample older than one second is stale. `WatchResource` accepts the same exact URI, sends a bounded URI-only `ResourceChanged` notification after a changed retained product, and never treats the notification as the product. A reconnecting client starts a new watch and re-reads the resource; the server supplies no cursor or lossless replay. A slow watcher is closed with `RESOURCE_EXHAUSTED`. The selected EGIA client currently auto-rediscovers only on `NOT_FOUND` or `UNAVAILABLE`; for `RESOURCE_EXHAUSTED` it raises an error to its caller. R02 does not claim automatic EGIA recovery from that code. The caller must explicitly restart the stream and read again, or a separately reviewed EGIA client change must add this retry. Cancellation releases its subscription.

`CaptureFrames` requires the exact admitted `robot_name`, a discovered healthy camera `device_id`, and `frame_count` equal to 1 or 2. It returns `type=vision.snapshot`, `schema_version=1.0`, that same device ID, and exactly that many **distinct**, complete JPEG frames with nonzero dimensions and nonempty RFC 3339 capture times. Acquisition uses the EOS-owned bounded camera cache and a deadline; the response is capped at 16 MiB, each JPEG at 8 MiB, and at most two frames are retained per camera. Invalid counts or names are `INVALID_ARGUMENT` or `NOT_FOUND`; missing, stale, unhealthy or insufficient distinct frames are `UNAVAILABLE`; capacity exhaustion is `RESOURCE_EXHAUSTED`. It does not start an unbounded camera stream.

Capability names use the canonical hardware/runtime forms in [CapabilityService](capabilities.md). `SubmitOperation` requires one catalog name, a present object `arguments` and a caller-owned 1–128 byte `operation_id`. R02 extends the current journal's 120-byte ID ceiling to this public limit. It validates the exact binding, primitive schema, numeric limits, health and deadline before any adapter release, and uses the same Dispatcher reservation and physical release path as other EOS entry points. R03 adds graph-revision/authority policy and broader actuator admission tests; R02 does not claim those gates. The journal durably stores enough immutable primitive/version/target/admission metadata to reconstruct the canonical `primitive.ack` after restart; it is not a second operation store. Same ID plus identical canonical request returns the retained state, including across restart; conflicting reuse is `ALREADY_EXISTS` and never releases again. Unsupported primitive conversions remain unavailable rather than being advertised or routed around Dispatcher. `Operation.operation_id` always equals the submitted command ID. Pending has no acknowledgement; terminal has `accepted` present and a matching acknowledgement `command_id`, primitive, version and status. Existing movement Dispatcher `Completed`, `Cancelled`, `Rejected`, `InProgress`, and `OutcomeUnknown` project to `SUCCEEDED`, `CANCELLED`, `REJECTED`, `PENDING`, and `OUTCOME_UNKNOWN` respectively. R02 stop commands also produce `FAILED` when a terminal stop failure is confirmed; R03 adds broader distinguishable movement failure and timeout causes. A pre-admission rejection is `accepted=false`; a failure after admission is `accepted=true`. An uncertain released motion remains `OUTCOME_UNKNOWN` after restart and is never automatically replayed.

Stop operations use a distinct Dispatcher request kind and the same durable Prepared → Releasing → Terminal phases and operation ID rules; they are **not** ordinary `Movement` values or graph control edges. The journal stores a typed hardware-node or robot target, never a fake hardware path for whole-robot stop. A recovered uncertain estop retains its safety latch without re-releasing the physical request. `motion.stop` requires one admitted device ID, invokes only its stop-capable adapter, and succeeds after terminal stopped confirmation; an already stopped device succeeds without another physical effect. `robot.stop` uses an empty device ID and durably snapshots at most 64 admitted stop-capable actuator paths in canonical order before one logical release. A separate durable movement inhibit blocks new movement from before Releasing until verified completion or recovery; it calls each snapshotted part at most once, waits for terminal stop boundaries, and reports at most 64 per-part results with sanitized reasons of at most 256 bytes in `acknowledgement.result.parts`; any unconfirmed part makes the whole operation `FAILED` or `OUTCOME_UNKNOWN` according to whether the failure is known. It does not latch emergency stop. `safety.estop` also uses an empty device ID, durably records the request, then engages the configured emergency-stop path and process latch; success requires terminal confirmation, and no reset is offered. For any stop, a lost response or crash after release is uncertain and is never replayed under the same ID. A crash after partial `robot.stop` fanout yields `OUTCOME_UNKNOWN`: only durably confirmed part results remain known, all other parts are unknown, and none is automatically called again for that ID. More than 64 stop-capable parts prevents gateway readiness; a per-part result overflow detected before release is `RESOURCE_EXHAUSTED`, while one after possible release remains `OUTCOME_UNKNOWN`. The existing unjournaled `stop_node` and `emergency_stop` methods are insufficient as public operation implementations until wrapped by these distinct journaled Dispatcher paths and terminal-confirmation semantics. Shutdown may still invoke emergency stop independently for safety. An adapter that cannot confirm its terminal stop boundary cannot produce `SUCCEEDED`.

The RobotStop movement inhibit is journal control state, separate from the `safety.estop` latch. It is synced before Releasing and checked by every Dispatcher movement release, including concurrent requests. A fully confirmed terminal `robot.stop` clears it durably; a known partial failure, uncertain result, crash, or failure to persist the clear leaves it set. After restart with a partial-fanout `OUTCOME_UNKNOWN`, the same operation ID remains query-only. A **new, locally authorized** operation ID may submit `robot.stop` while movement is inhibited; it must snapshot the union of the unresolved prior targets and currently admitted stop-capable actuators and confirm every terminal stopped boundary before a durable clear. If any former target cannot be verified stopped, movement remains inhibited pending explicit authorized maintenance with equivalent per-target stop evidence; there is no automatic clear or replay. During inhibit, the complete gRPC discovery surface may remain `SERVING` so the stop recovery path is reachable, but `GetStatus.status` and robot health are `degraded`, ordinary movement capability `available` is false, and Submit movement is rejected before release. Stop capabilities remain available. The normal ready event attests a safe responding runtime, not permission to move; clients must inspect current health and capability availability. Clearing this inhibit never clears an emergency-stop latch.

The Dispatcher release coordinator closes the gap between a synced `Releasing` record and the physical adapter call. A movement obtains a release permit under the coordinator, checks inhibit and deadline, persists `Releasing`, and retains the permit through its physical call; this permit is its release linearization point, so a paused movement that has persisted `Releasing` still owns it. RobotStop first closes new movement permits, then syncs the inhibit before its own `Releasing`, and waits for all prior movement permits to drain or for the adapter to fence their physical effects before stop fanout. `motion.stop` uses the same ordering for its target device. A movement with an ambiguous or delayed physical result is unresolved until the adapter proves quiescence or rejects its old release generation at the physical write boundary; merely returning from a call or observing a stopped sample is insufficient. If that proof cannot be obtained within the bounded stop deadline, RobotStop remains `OUTCOME_UNKNOWN` with inhibit set, makes no success claim, and requires a new authorized ID or equivalent maintenance recovery. The coordinator never waits for an adapter while holding the journal mutex; the independent latched `safety.estop` path can preempt a blocked movement. After a process restart, any old `Releasing` movement is sealed against new movement release until adapter epoch fencing or equivalent physical quiescence is verified; health is degraded and movement unavailable during this recovery. No RobotStop inhibit can clear before that proof and all target stop confirmations. This ordering prevents an earlier movement paused before its adapter call from actuating after a confirmed RobotStop.

`GetOperation` returns the current retained state. `WatchOperation` first sends it and, if pending, at most one terminal update; it has no cursor. On a broken watch, clients call `GetOperation` with the same ID before any decision to submit again. `CancelOperation` targets only that command through Dispatcher; a terminal ID returns its retained result, a missing ID is `NOT_FOUND`, and a non-cancellable command is `FAILED_PRECONDITION`. An explicit stop capability is required to clamp motion. Request cancellation or a lost reply does not imply physical cancellation. During shutdown aggregate health changes to `NOT_SERVING`, new submissions fail `UNAVAILABLE`, watchers close, and Dispatcher stop precedes simulator termination and reap (R06 exit evidence).

Malformed/empty IDs, missing object arguments, invalid enum or frame counts and oversized requests return `INVALID_ARGUMENT`; unknown admitted names, URIs, camera IDs or operation IDs return `NOT_FOUND`; conflicting command identity returns `ALREADY_EXISTS`; bounded queue/stream/frame capacity returns `RESOURCE_EXHAUSTED`; unavailable or stale dependencies return `UNAVAILABLE`; expired transport deadlines return `DEADLINE_EXCEEDED`. An admitted semantic rejection is an OK RPC with terminal `REJECTED`, not a transport error. `INTERNAL` is reserved for a server invariant or durable-store failure before release; if release may have happened, preserve `OUTCOME_UNKNOWN`. On the historical unmanaged lookup path, a legacy journal ID lacking canonical acknowledgement metadata returns `DATA_LOSS` and is not re-released; managed lookup uses the uniform `NOT_FOUND` policy below. Bound unary requests to 64 KiB except the 16 MiB frame response, subscriptions to 16 per method, and server work by the caller deadline with a five-second default when absent. Transport `x-request-id` is correlation only and cannot replace operation identity.

## R03 governed actuator admission target contract

**R03 qualified on merged EOS and IsOS owners.** The [R03 design](../design/runtime/admission-revision.md), [first-use replay](../develop/admission-revision.md), and [frozen cases](../../../tests/fixtures/r03_admission_revision/README.md) define the managed EOS admission slice. The selected `aether-runtime --capabilities` probe advertises exact feature `managed-control-grants`. IsOS P05 must require this token on the selected runtime for a `0.1.0` managed graph and reject an older runtime at its process `/node_type` before stopping an active child or issuing grants. This adds metadata and private launch inputs without changing published protobuf packages, methods, field numbers or ProtoJSON names. IsOS owns the saved whole-graph SHA-256 `active_revision`; EOS's `projection_sha256` is the digest of the generated EOS projection bytes and never substitutes for it. The selected IsOS schema-2 leaf is `data/generated/<deployment>/v2/<revision>/<generation>/`, with `manifest.json` at that leaf and `eos/graph.json` below it. IsOS verifies that leaf before spawn. EOS requires `manifest.schema_version:2` and its selected profile to be exactly the listed regular `eos/graph.json`, rejects symlinks and path escape, verifies its just-read bytes against the single manifest entry, validates the 64-digit lowercase `manifest.revision`, and fixes both identities for its process lifetime. Managed mode requires both `EOS_CONTROL_GRANTS_FILE` and a selected profile path with the IsOS `/v2/<revision>/<generation>/eos/graph.json` layout. Either input alone fails startup before listener bind, ready event or adapter construction. With both inputs, an absent, malformed or mismatched schema-2 manifest or verifier also fails startup, and EOS requires its effective `--run-id` to equal the verifier `run_id`. The optional public `--run-id` alone is only a correlation value and never selects managed mode. With neither input, a standalone profile may serve complete read-only discovery with movement capability `available=false`; it never claims a saved active revision and Submit returns `UNAVAILABLE`, even when `--run-id` is supplied. IsOS still reads and explicitly migrates legacy `1.0.0` saved graphs without launching this managed actuator path.

IsOS creates two independent 32-byte grants from the OS cryptographic RNG per deployment run: `egia-control` and `operator-control`. Each mode-0600 regular grant file below its mode-0700 runtime directory contains exactly 64 lowercase hex digits and one newline; the decoded 32 bytes are the secret. A separate mode-0600 verifier JSON file contains `schema_version:1`, exact `run_id`, saved `active_revision`, and SHA-256 digests of the decoded grants under `egia_control_sha256` and `operator_control_sha256`; it contains no secret. IsOS passes the verifier path only to EOS as `EOS_CONTROL_GRANTS_FILE`, the EGIA grant path only to supervised EGIA as `EGIA_EOS_CONTROL_GRANT_FILE`, and the operator grant path only to the supervised HTTP bridge as `AETHER_BRIDGE_CONTROL_GRANT_FILE`. EOS checks run and revision against its admitted generation, then compares a presented decoded grant digest to the role's verifier in constant time. Files with unsafe ownership, mode, path or contents fail before write readiness. Grants are never stored in graph bytes, generated config, logs, descriptors or public metadata. IsOS grant issuance and launch delivery are being implemented in its separate owner branch; EOS fixture-injected grants prove only the EOS behavior until the cross-repository replay passes. The trust boundary is the local OS user, not isolation from another process with the same UID. The grant lifetime is one IsOS deployment `run_id`: an EOS child restart within that run reuses the run-scoped verifier and grants for journal recovery; a new deployment run mints new grants and invalidates the old files before new write readiness. Grant bytes never enter the immutable generated snapshot. EOS rejects an old verifier `run_id` even when the saved graph revision is unchanged.

For gRPC actuator writes and operation lookup, watch and cancellation, `authorization: Bearer <64-lowercase-hex-grant>` is required. `x-eos-active-revision: <64-lowercase-hex>` is required for movement, `motion.stop` and `robot.stop` and compared again at the final Dispatcher release gate after queue wait. Complete discovery adds response metadata `eos-active-revision` and `eos-projection-sha256` so clients can bind subsequent writes to the inspected generation without changing response messages. A read-only legacy client continues health, discovery, resources and capability listing without new metadata; its write with no grant or revision fails before release. Both grants may invoke `safety.estop` while the revision is missing or stale, through its reserved lane. Internal shutdown has an independent private safety seam. A fresh-ID `robot.stop` during the durable movement inhibit may set `StopRequest.authorized_recovery` only for `operator-control` with explicit `x-eos-stop-recovery: true`; EOS snapshots the union of unresolved old targets and current admitted stop-capable actuators, and keeps inhibit until every target is terminally proven stopped. `egia-control` and an operator request without that marker cannot recover the inhibit. `robot.stop` is robot-scoped; `motion.stop` is bound to one exact admitted device. Neither recovery nor a controlled stop clears the emergency latch. The `egia-control` role may submit movement only over governed gRPC. The `operator-control` role may submit movement only through the private `primitive_typed` bridge path; its gRPC movement Submit is `PERMISSION_DENIED`. Both roles may use authenticated gRPC stop according to the matrix below. EOS does not infer an EGIA safety-stage pass from the grant alone. The private `primitive_typed` header adds `active_revision`; the supervised bridge sends its grant as outer owner-socket `authority_grant`, never as browser payload. A02 adds EGIA's managed write metadata. The merged EOS bridge injects its private operator grant for `primitive_typed`; R07 still owns UI revision display, authorized result follow-up and full browser-path qualification.

| Role and ingress | Movement | Controlled stop | `safety.estop` | Operation Get/Watch/Cancel |
| --- | --- | --- | --- | --- |
| `egia-control` gRPC | Exact active binding | `motion.stop` for exact device, normal `robot.stop`; no inhibit recovery | Yes, even with stale/missing revision | Only its recorded role/scope and current run |
| `operator-control` gRPC | Denied | Exact-device `motion.stop`, normal `robot.stop`, and explicit fresh-ID inhibit recovery | Yes, even with stale/missing revision | Only its recorded role/scope and current run |

For example, a managed `SubmitOperation` retains the existing ProtoJSON body `{"capabilityName":"robots/demo-0/devices/drive/primitives/base.velocity","operationId":"cmd-17","arguments":{"x_m_s":0.1,"y_m_s":0,"yaw_rad_s":0,"valid_for_ms":100}}` and adds the two request metadata fields. A missing grant yields gRPC `UNAUTHENTICATED` with no `Operation` and zero adapter calls. An authenticated stale revision yields `FAILED_PRECONDITION` with no new reservation or adapter call. `GetOperation`, `WatchOperation` and `CancelOperation` require a valid grant of the same durable role/scope that submitted the ID; no current revision is required to query an old result. For a managed listener, an unauthorized role, wrong run, sealed legacy ID and absent ID all return the same `NOT_FOUND` on Get, Watch and Cancel, without revealing a result or changing cancellation state. A historical unmanaged in-process lookup retains `DATA_LOSS` for a legacy record lacking admission identity; it does not authorize a managed write. This role is the owner unit within the documented same-UID boundary, including after token rotation. An authorized `GetOperation` recovers a lost response and never calls the adapter; a fresh command cannot use the old revision. An EOS child restart within the same IsOS deployment run retains the run ID and grants, so exact lost-reply recovery still works. An explicit new IsOS deployment run rotates grants and run ID; old grants fail, old-run Get/Watch/Cancel with a new grant return the same `NOT_FOUND` as an absent ID, and reuse of an old ID returns `ALREADY_EXISTS` without returning its prior success or releasing a new command. Conflicting same-ID role, revision, binding, target or typed arguments yield `ALREADY_EXISTS` and never release. The durable signature includes stable role/scope, server-attested ingress, IsOS `run_id` and saved revision but excludes credential bytes, transport `x-request-id` and per-attempt deadline; stop records also persist their `MotionStop`/`RobotStop`/`SafetyEstop` kind, exact device or robot target, role, run ID, saved revision (nullable only for estop) and recovery marker. A same-ID cross-role or changed-marker stop conflicts rather than replaying a prior stop result; every new attempt still must have a live deadline before release.

All deployed public and private actuator writes converge on Dispatcher governed admission; movement and stop have distinct coordinated methods and reserved stop lanes. The current owner-socket `manual`, `primitive`, `skill_execute`, `skill_result`, raw `dispatch`, unjournaled `stop` and `manual_stop`, and raw `cancel`, `result` and `skill_cancel` operations must cease being production actuator routes; local in-process helpers and historical graph types do not confer deployment authority. Before adapter release Dispatcher checks exact admitted binding and target, role, active revision, healthy lifecycle and health, fresh typed observation, finite numerical limits, monotonic deadline, durable ID and safety state. An admitted semantic rejection remains terminal `REJECTED` with matching command ID. Failed durable persistence before release calls no adapter; possible release with lost terminal persistence becomes `OUTCOME_UNKNOWN` and is never retried under that ID. R01 evidence queue caps cannot touch command or fixed safety routes. R02 stop kinds and reserved capacity remain distinct. Physical MuJoCo epoch fencing and simulator stop/reap ordering remain R05/R06 gates.
