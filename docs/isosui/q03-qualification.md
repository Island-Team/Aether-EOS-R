# Q03 IsosUI qualification design

[中文](../../docs_cn/isosui/q03-qualification_cn.md)

**Status:** design reviewed; selected installed browser evidence passed in the sealed Q03 final-17 replay, and the merged-head Q04 final-5 replay passed independent archive review. IsosUI `v0.1.0` was later published; the [approved published-asset run-7](https://github.com/Island-Team/Island-eos/blob/refactor%28v2%29/runtime-main/docs/island/q04-merged-qualification.md) completed the Q04/M5 cross-owner release gate for its stated scope. Live public HTTPS browser first use remains open. IsosUI presents owner-reported graph, status, logs, Vision, and primitive results. IsOS owns graph Apply and current-run events; EOS owns command admission. The editor must not execute a graph wire as a browser command.

## Source and static gates

Create the topic branch from fetched IsosUI `master`, then build and qualify the exact reviewed code/contract topic HEAD; record both the master base and selected candidate SHA, plus the other four owner commits, Node 22/npm 10, lockfile SHA-256 and built manifest/asset hashes. `scripts/verify-bundles.mjs` must report that exact code/contract HEAD as `source_commit`; never substitute the older master base. Commit numeric benchmark evidence on a separate documentation topic based on the qualified code commit so the selected bundle and code topic HEAD retain the same identity. Recheck remote master before the PR, and requalify the merged SHA in Q04. Run `npm ci --no-audit --no-fund`, `npm run typecheck`, `npm test`, `npm run build`, both bundle manifest checks and `git diff --check`. Confirm local `/` and hosted `/isosui/` asset bases, `source_commit`, version `0.1.0`, schema and target. Run the browser-result and Q01 Vision fixture checkers plus focused catalog, edge, panel, log cursor, primitive deadline/result/Stop, and Vision provenance tests. Include stale graph revision, unsupported graph/type, unavailable selector, old-run response, wrong stream/gate/source, malformed frame and owner outage negatives. Save every command, exit code and complete output under ignored `logs/test/<run-id>/`.

## Installed first use

Serve the selected local bundle from a fresh IsOS home with a verified `island/mujoco-sim@0.1.1` package. In a real browser, visit `/en/isos` and `/cn/isos`, choose scene/devices, Validate and revision-check Apply, inspect saved/active revisions and readiness, type/instance descriptions and edge diagnostics. Exercise independent Graph, Control, Monitor, Vision and Logs panels, focus and keyboard operation, 44 px touch targets, narrow viewport, both themes, persisted layout and Stop visibility during an EOS outage. Choose one active base or arm binding, verify exact target and SI field help, invoke once, and retain command ID across Sending, InProgress and terminal/OutcomeUnknown states. Correlate the result with current-run logs; inject failure/restart and prove no command replay. Check stale revision, bridge outage, frame rejection and confirmed/unknown Stop. Test explicit legacy migration and unsupported graph read-only behavior. Capture screenshots or DOM assertions with owner HTTP/event transcripts, sanitized of grants, prompts and media.

For the hosted check, map `/en/isos` and `/cn/isos` to the exact `dist/hosted/index.html`, serve only hosted assets under `/isosui/`, and reject fallback to `dist/local`. In the actual browser assert that the loaded manifest and every observed JS/CSS response SHA-256 match the selected hosted files, including lazy chunks loaded during Graph and Control interactions; retain the complete observed digest map and reject a late substituted chunk. Then verify the same editor URLs and loopback API policy. The selected Q01 verifier must confirm IsOS `vision_evidence` and EOS `subscribed` attestation for one run, revisions, gate/source, render settings and stream; compare accepted JPEG digest and generation with EGIA where specified. UI delivered FPS and skipped generations are browser observations, not EOS queue metrics. Unit fixtures alone do not close this installed gate.

## Browser baseline

Each of the three repetitions starts a fresh Firefox and geckodriver session, verifies the selected production bundle again, and records its browser version, session ID, driver process ID and observed asset hashes. The 100 warm-ups and 1,000 measured operations per case, 2 s interaction deadline and fail-fast checkpoint apply independently to every session. Browser startup, prior-session teardown and asset verification failures also write a checkpoint with the completed cases before the run can be published. A failed warm-up remains a failure; a later passing retry does not turn an incomplete run into baseline evidence. The earlier long-lived-session local and hosted attempts are retained under `logs/test/20261103-q03-ui-fecafe9/` as diagnostics because each stalled before an EOS submit during a later Control interaction.

Before measurement, commit `tests/fixtures/q03_browser_benchmark/v1/` containing an exact 19-node, 10-input-wire graph derived from the sanitized Q01 selected graph, one active base binding, stub JSON bodies and a manifest of each body's SHA-256 and byte length. The fixture fixes a 5 ms stub response delay, a two-step `InProgress` → `Completed` result for a synthetic command ID, a 2 s per-interaction timeout and a 1280×800 browser viewport. Because the production Control result exists only after Invoke, the browser may send exactly one synthetic `primitive_typed` POST per sample **only to the isolated benchmark EOS stub**. The runner must acquire the fixed IsOS, UI and EOS loopback ports before opening the browser, reject any preoccupied port, verify target/revision/payload, and assert unique command IDs and no retry. Count a Control sample only when the submitted POST ID, every authorized result-read ID and the visible terminal ID are equal, and the active revision and IsOS run identity match that sample; reject stale or old-run results. It may never route a request to a live owner or physical actuator. For each pinned production local and hosted bundle, perform 100 warm-ups and 1,000 serial Graph-open/catalog-render operations plus 1,000 serial Control Invoke/result-display operations. Graph timing starts immediately before navigating to `?page=graph` and ends only after the selected revision and 19 nodes/10 wires are visibly stable across two animation frames. Control timing starts immediately before navigating to `?page=eos` and ends only after the same-run binding and terminal result are visibly stable across two frames. Reset to the prior page and wait for its selected revision and visible content before starting the measured interval. Accept a terminal Control result only after this sample's Invoke has produced its synthetic POST ID; a prior card result cannot complete a new sample. On a correlation or post-count failure, stop immediately and retain the attempted outcomes and requests, plus completed cases in that repetition, in a failure checkpoint. Measure with the browser monotonic clock; retain every latency, outcome, actual response size and measured wall duration. Focused harness tests must prove accounting, rejected/failed response and timeout behavior. Run three repetitions per bundle and report completed operations/s, midpoint median and nearest-rank p99 in milliseconds, failures and run order, each run and pooled. Record browser, OS/CPU, bundle hashes and graph size. Keep stub browser latency distinct from live MuJoCo or dispatcher latency. No threshold is set before the baseline. An independent design review precedes harness implementation, and independent implementation/evidence review precedes a PR to IsosUI `master`.
