# U04 node information and primitive control

[中文](../../../docs_cn/isosui/interfaces/primitive-control_cn.md) · [Design](../design-primitive-control.md) · [First use](../usage.md)

IsOS owns graph bytes, the saved and active SHA-256 revision, run ID and deployment Stop. EOS owns the active binding, target admission, live adapter status, journal and terminal result. IsosUI reads these owners and sends an operator-clicked command only through `POST /api/eos/v2/control`. A graph wire declares the binding; it does not execute a command.

## Graph card

A pointer pause of about 550 ms, keyboard focus, or the touch information button opens one nonmodal card in a body portal above overlapping nodes. Clicking or dragging a node raises that node above its neighbors; the old below-node detail card is removed. It is viewport-clamped (8 px margin; 340 px nominal maximum width/height), Escape/close dismisses it, and its button uses React Flow `nodrag`/`nowheel` so node dragging and wire handles remain usable. The card shows catalog type description, separate instance description, input/output names, exact data type IDs, schema `x-unit` annotations when supplied, transport and port help. A missing catalog description is marked as a compatibility fallback. For an EOS hardware node, live adapter `status` and `health` are read only while IsOS reports a running, saved==active revision and an unedited graph; failed reads do not fabricate health. While open and visible, owner status/health refresh every two seconds; a failed read or a sample older than five seconds is labeled unavailable or stale. Graph drafts never get inferred live status.

## Active binding and request

IsosUI reads `GET /node-types/selected` with the saved graph and requires its `graph_revision` to match the graph's saved-byte revision before checking all EOS and EGIA types. A changed revision gets one bounded graph/catalog reread; a second mismatch or unavailable owner catalog leaves Graph, EOS control and inspection read-only. The global `GET /node-types` catalog remains available for package discovery, while selected owner types and data schemas describe the applied graph. IsOS's `read_only` verdict also fences controls.

The EOS workbench refreshes owner graph/catalog and process status while visible. Its five-second timer starts at most one read at a time; a slow read remains eligible to publish even if later timer ticks occur. A new saved revision or run ID clears the previous run's discovery and health before the new status is shown. Operator **Refresh** closes Invoke immediately. If a read is underway, repeated clicks queue one immediate follow-up and discard that older result; Invoke reopens only after the follow-up's matching saved graph, selected catalog, process status and EOS discovery complete. Owner failure or revision mismatch leaves controls read-only. Unmount discards late replies.

One control card is rendered for each exact `eos.dispatcher.primitive_base@v0.1` or `eos.dispatcher.primitive_manipulator@v0.1` binding with one exact `command` edge to a matching `eos.hardware.base@v0.1` or `eos.hardware.manipulator@v0.1` target. Supported pairs are `base.velocity`/`body_velocity`, `base.navigate`/`relative_pose`, `arm.movej`/`joint_positions`, and `arm.movel`/`end_effector_pose`, each primitive version `1.0.0`. Other, malformed, missing, ambiguous, or legacy bindings are unavailable in this U04 control. The target is displayed as a fixed graph-resolved path; changing it requires Graph edit and Apply. The card shows binding and target type/instance descriptions, primitive and mode, and SI field units. `movementValid` checks finite numbers, available target modes, configured bounds, frame IDs, joint names and normalized quaternion before enabling Invoke. A fresh EOS `status:ready` plus `health:healthy` is required.

Before a send, IsosUI requires IsOS `run_id_state:known`, nonempty run ID, `state:running`, a 64-hex saved revision equal to the active revision and displayed graph revision, no draft edits or compatibility read-only state. It re-reads the saved graph and process status, verifies the same exact binding and target, and finishes the final IsOS run/revision fence before reading EOS process-local monotonic time. Immediately after that time read, it rechecks the latest local run, revision, binding, Stop, edit and abort state, then sends at most one `primitive_typed` POST with a fresh command ID. The four-second deadline starts from the last blocking owner read; an unavailable or expired send is never replayed with that ID. The header carries `data_type_id` (`base_movement` or `manipulator_movement`), `data_type_version:1.0`, exact primitive name/version, canonical binding/target paths, active revision, fresh 1–128-byte command ID, positive sequence, four-second monotonic deadline, UTF-8 JSON payload byte length (1–16384), and `codec:json_v1`. The payload is the validated typed movement object. The browser never supplies a grant or a private IPC operation.

The browser displays local `Sending`, then only an EOS response with the same command ID can establish `Completed`, `Failed`, `Cancelled`, `Rejected`, `InProgress`, or `OutcomeUnknown`. A lost submit response does not trigger a second submit. `InProgress` uses only `{op:"result",command_id,active_revision}` on the same public bridge, with IsOS run/revision checks before and after each read. The result reader is bounded to twelve attempts or one minute, then offers manual refresh. Run rotation, stale revision, unavailable IsOS identity, Stop, binding change or unmount fences old reads and late replies. Transport errors remain unavailable, never success. The IsOS Stop button stays visible and callable even when EOS Invoke is disabled or the bridge is down. Its click sets a run-scoped fence in the EOS workbench before awaiting the Stop response; every binding card disables Invoke immediately. Pending, unknown or unavailable Stop and failed status refresh keep that run fenced. It also aborts each sibling card's pending result read, seals its record for that run, and ignores a late terminal reply. A newly observed run ID has a separate fence.
