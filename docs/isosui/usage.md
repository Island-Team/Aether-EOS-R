## Current path

1. Install Node.js 22 and npm 10, then run `npm ci` and `npm run build` in this repository. Select the resulting `dist/local` build in IsOS. Alternatively, `npm run dev` starts the standalone frontend on `127.0.0.1:16001`; the IsOS and EOS loopback APIs must be running for graph and live controls.
2. Start IsOS with `isos serve` and open `/en/isos` or `/cn/isos`. Home shows manager setup, installed package receipts, core readiness, process state, and all-source logs. An offline API is an explicit blocked state, not an empty graph.
3. Install or link the exact `island/mujoco-sim@0.1.1` package in IsOS. In Graph, choose the installed `sim-hardware` node set, preview its additions, and select a scene. In Graph, browse **core → layer → group → node type**. Select a scene from the searchable `/node-options` group for `eos/process/mujoco/simulator` and choose each generic camera/base/manipulator device from its own exact `node_path` group. The device choice writes `adapter.settings.device_id` and `adapter.settings.simulator_node` together.
4. Select each node to read the registered type description separately from the editable instance description and configure its type-defined fields. Search owner-provided selector labels and descriptions, and inspect unavailable saved IDs and repair reasons. Wait for the current draft options to load before applying; changing the scene or package refreshes dependent device options. Connect compatible output and input ports, then choose **Check graph** under Advanced. If a wire is highlighted, select it: the inspector shows source and destination type IDs, IDL field units, and any IsOS rejection code, path and reason for that input. The Diagnostics section retains the full server result. Correct the port or node setting and check the graph again; a draft edit makes the previous result stale. The inspector's deployment state is separate from live node health, which opens in the EOS monitor. Use the primary Graph action to save and run only after the check is clear. The server validates and applies the graph; a browser draft alone does not control EOS.
5. Wait for Home readiness, then open EOS controls and monitor. Controls appear only for declared nodes in the active graph. The workspace toolbar opens control, monitor, Vision and logs independently; the Graph View menu opens the same persistent EOS control panel. EGIA still uses its Graph core window.
6. To find a failure before launch, open Home Logs. Its pinned manager-session anchor shows the first package or Apply failure even when detail filters hide that source. After launch, the panel pins the run's first ready or failure event. Filter later detail rows by source, level, node path or correlation ID; the anchor remains visible. Copy the run ID and correlation ID into the EOS or EGIA investigation. Home status supplies live readiness and the saved/active revision; a stale active revision blocks live control.
7. Stop the deployment with IsOS. For an upgrade, install a new exact package version, preview its nodes, check the graph, apply a new revision, and restart. Retain the previous graph and package receipt for recovery.

If EOS controls are still loading while the owner catalog is slow, wait for the current refresh to finish. The five-second background timer does not cancel an active read. Click the workbench **Refresh** to request a new owner snapshot; Invoke stays disabled until the fresh saved graph, selected catalog, process status and discovery agree. An unavailable or mismatched selected catalog leaves the control read-only with a visible reason.

The root [README](../../ui/README.md) gives the actual development commands, API origins and build outputs. IsOS owns package installation and process operations.

## P07 log navigation

Open Home Logs after a package or Apply failure. The panel asks IsOS for `view=current` and shows the manager-session first package/Apply failure above the source, level, node and correlation filters. While no such event has arrived, it says the anchor is pending; an empty list is not evidence of success. After IsOS admits a deployment run, the panel switches to that run's first ready or failure event, then shows later detail rows. It keeps that run selected after Stop, process exit or manager restart until IsOS admits another run. Use Home status for live readiness and the saved/active revision; the log event explains what happened at its own time.

Pause Follow to inspect a row's safe source, core, event code, run ID, correlation ID and graph node pointer. Narrow the detail rows only after seeing the pinned first event. If retention or rotation lost entries, the panel displays a gap notice and resumes in the same run; if the collector is unavailable, it retains the last rows and cursor and displays an error until recovery. A new admitted run gets a visible boundary and its own anchor. Browser console diagnostics remain separate from IsOS events. The P07 panel displays owner-reported event identity and preserves a legacy compatibility view when IsOS lacks the opt-in response. See the [P07 UI contract](interfaces/log-cursors.md).

An empty filtered page with an advancing cursor and no diagnostic means no matching detail row yet; it is not a gap. If status reports `run_id_state:unavailable` or current logs return `log_scope_unavailable`, keep prior rows marked stale and use live status while IsOS recovers the run identity. A `log_scope_publish_failed` Run error means no child was spawned, but the durable run record may have survived; refresh status and current logs before interpreting the scope. Neither condition authorizes the UI to choose a manager session or declare readiness.

### R07 first use with a managed mock base

Apply an IsOS graph with one `base.velocity` primitive binding connected to one `mock-cxx` base, then Run it. Open EOS and wait for the base status and health to be ready. Check the displayed binding and target paths and the SI limits. Enter a bounded velocity and lease, then click **Invoke** once. The card keeps its command ID, shows the exact EOS status and follows `InProgress` only while IsOS confirms the same run and revision. Use **Refresh result** if automatic reads pause. Click **Stop deployment** through IsOS, then open **Current run logs**. The log view opens without a command-ID filter; the command ID stays on the card for comparison.

In the managed mock replay, the first command returned `OutcomeUnknown`; after Stop and restart, the card must keep that owner status and ID with **Unavailable for this run**. A fresh click in the new run returned EOS `Rejected` because movement remained inhibited after the uncertain release. Inspect the new command's result and current-run logs; do not retry the old movement or treat the mock Stop response as physical MuJoCo stop proof. The EOS checkout records the exact graph, revisions, response bodies and commands in ignored `logs/test/20261102-r07-cross-owner-live/SUMMARY.md`.

On **Stop deployment**, expect **Stopping…** until IsOS replies. Check the Stop line separately from the live state: **Stop confirmed** requires the same run ID and `terminal.outcome:"confirmed"`; **Stop outcome unknown** includes a fixed reason code and needs investigation in current-run logs. **Stop unconfirmed** means the terminal reply is missing, null, malformed or belongs to another run. A never-run home with `run_id_state:none` reports no managed run to stop. **Stop response unavailable** means the reply was lost; inspect refreshed IsOS status and logs before another operator action. A failed status refresh does not change the displayed Stop result. The previous EOS command result stays fenced after the click, including if a late reply arrives.

If IsOS explicitly rejects Stop, the alert says **Stop rejected by IsOS** and shows its owner message. A null terminal with reaped children is still unconfirmed; duplicate child outcomes cannot confirm Stop.

## Current M4 workbench interaction

U01–U04 are merged on IsosUI `master` ([owner status](todo.md)). The steps below describe the implemented UI. The [historical M4 affected-boundary replay](https://github.com/Island-Team/Island-eos/blob/master/docs/island/m4-affected-replay.md) proved a supervised mission and distinct browser command, but not EGIA child replacement within that same run. The later [Q03 final-17 and Q04 final-5 replays](q03-evidence.md) use separate pinned inputs. The IsosUI tag and hosted archive are published and pinned by Island-web; the later [approved published-asset run-7](https://github.com/Island-Team/Island-eos/blob/master/docs/island/q04-merged-qualification.md) completed the scoped cross-owner release replay; live public HTTPS first use remains open.

On a saved `0.1.0` graph, wait for the selected owner catalog and matching `graph_revision` before editing or invoking EOS. The global catalog lists installable package types; the selected catalog supplies the EGIA stages and settings for this exact saved graph. If the owner catalog is unavailable or its revision changes twice while reading, inspect the raw graph read-only and retry after the owner is available. See the [catalog contract](catalog/README.md).

Graph can display its saved revision while process status, readiness or package node sets are still loading. Use **Reload saved graph** to request a new selected snapshot; the current canvas stays visible until the reply passes revision checks. Home polls process status every five seconds; use **Refresh** after an external package or graph change to reload the full owner view. See the [graph loading contract](interfaces/graph-loading.md).

Graph starts with a searchable registered type library. A selected type shows its nonblank **type description**, placement, capabilities, port contract and setting help; a selected instance shows its own editable description. The configuration form renders settings from catalog metadata. A selector searches verified options for that **node and setting**; scene and device options are supported here. Model-weight assets are an extension point, without EGIA tensor execution in this release. The selector header shows the exact package/version pin; each option row shows stable ID, human label, description, availability and reason. Keep an unavailable saved value visible with its reason; never silently replace it. Check graph remains available and reports unresolved or invalid choices; Apply is blocked until they are corrected. Package paths stay private to IsOS; the graph saves stable IDs and exact package pins.

Pause the pointer over a node for about half a second to open its floating info card beside the pointer. Keyboard focus or the information button opens it immediately; clicking or dragging brings the selected node above neighboring nodes. Show registered type description and instance description separately, plus placement, ports and units; show live health only when reported by its owning core. Clamp the card inside the viewport, make it available on touch, and keep dragging and wire editing usable.

Each wire exposes `priority` (nice `-20..19`, default `0`) and optional `frequency_hz` (positive finite delivery cap). The inspector edits them against an IsOS validation result. Labels show both values at normal zoom and in keyboard focus text; the legend explains priority and frequency separately from transport and payload type. A wire without an active runtime route is explicitly **design only**. Priority affects scheduling, never dispatcher safety admission.

The workspace docks or floats **control**, **monitor**, **Vision**, and **logs** independently. A floating panel has a drag handle, resize handle, focus order, close/dock action, bounded viewport, and local layout persistence. When reopening, clamp saved geometry to the viewport. On a narrow screen, stack panels and preserve the Stop action and significant connection or revision warnings. Routine messages appear briefly and remain in the browser section of Logs. Work pages use compact aligned rows and transparent or lightly translucent surfaces; visual overview pages may use wider spacing. Both share Island-web-inspired tokens, restrained borders, visible keyboard focus, 28–30 px desktop controls and at least 44×44 px touch targets.

For the full U04 primitive demo, inspect a node, check and apply its graph, then wait for EOS readiness. In the EOS control panel select one active primitive binding and inspect its single graph-resolved target; changing that target requires a graph edit and Apply. The panel shows both node descriptions and the typed primitive fields from the owner contract. Invoke through the existing loopback `primitive_typed` bridge. Show browser-local sending, then the exact `Completed`, `Failed`, `Cancelled`, `Rejected`, `InProgress` or `OutcomeUnknown` status from the correlated response; `InProgress` stays open until the authorized result read confirms an outcome. Show the current-run log and live health separately; filter logs by correlation only when an EOS owner event supplies a valid matching ID. A graph edge alone never means the command ran. Stop through IsOS. The [Q03/Q04 replay record](q03-evidence.md) documents selected clean-home and merged-head paths; the later [approved published-asset run-7](https://github.com/Island-Team/Island-eos/blob/master/docs/island/q04-merged-qualification.md) completed the Q04/M5 release gate for its stated scope.

### Edge QoS inspector

Select a wire, then choose **Check graph**. The inspector uses IsOS’s exact source pointer and shows its declared route class. Only an IsOS admitted, routed, QoS eligible, nonfixed edge offers editable controls. Nice priority is an integer from -20 (highest) to 19 (lowest), with effective weight `20 − priority`; an empty frequency cap means unlimited. The producer expected rate is a separate hint. Enter a value and press Enter or leave the field to commit it to the draft. Each edit clears the prior route authority; choose **Check graph** again before another QoS edit. Invalid values block Save and Save/Run. The editor validates the exact draft again before Apply; if IsOS rejects it or the draft changes while validation is pending, no Apply request is sent. A design only or fixed edge remains viewable without QoS controls.

## U04 node card and primitive controls

Pause over a Graph node, focus it with the keyboard, or tap its information button to inspect separate catalog type and instance descriptions, typed ports and any EOS owner-reported health. Escape or Close dismisses the clamped card. In EOS, each supported active `@v0.1` base or manipulator binding has its own control card. Check its one graph-resolved target, primitive, units and bounds; edit and Apply the graph to change that target. Wait for a known IsOS run, equal saved/active revisions and EOS ready/healthy status. Click Invoke once. Keep the displayed command ID while the browser shows Sending, then the exact EOS status. An `InProgress` result is followed by the authorized public result read for the same ID; a lost reply never resubmits. Stop deployment remains available through IsOS even if EOS control fails. See the [U04 contract](interfaces/primitive-control.md).

## U03 first use: workspace panels

Open Graph, then use the workspace toolbar to show Control, Monitor, Vision and Logs. Each panel can dock, float, collapse or close independently. Drag a floating title to move it; use its corner handle or arrow keys on that focused handle to resize. On narrow screens the panels stack. The Stop deployment button, IsOS connection state and active revision stay in the fixed strip above them. Stop is available when EOS or a panel is unavailable. A Stop click fences Invoke and result follow-up for that run immediately; an unknown Stop outcome remains an unknown outcome until IsOS confirms another run.

The control panel keeps each command ID and owner result while you switch pages, dock or collapse it. Closing Control hides it without creating a second client; reopen it from the toolbar. Monitor polling and Vision streaming pause when their panels are closed or collapsed. The Logs panel keeps its current-run cursor while docking or collapsing, pauses Follow while hidden, and starts a fresh status and scope check after closing and reopening. Panel geometry is stored locally for this robot and is clamped to the current viewport. See the [workspace contract](interfaces/workspace-panels.md). The selected Q03 R06/A03 recovery and merged-head Q04 final-5 replays passed on their separately pinned inputs; the later [approved published-asset run-7](https://github.com/Island-Team/Island-eos/blob/master/docs/island/q04-merged-qualification.md) completed the scoped cross-owner release replay.

For selected Vision evidence, open the Vision panel only after Home reports the current run ready. The panel uses IsOS's selected gate and source, subscribes to the public EOS bridge, and shows the run, gate generation, stream, JPEG digest, delivered FPS, and locally skipped generations. `No new frame` means the attested stream is ready but has not delivered an image; `Frame rejected` names a frame that failed local provenance or digest checks. Stop, a changed run or revision, or hiding the panel removes the image. See the [Vision provenance contract](interfaces/vision-provenance.md). The selected Q03 camera and merged-head Q04 final-5 Vision replays passed; final-5 used a simulated hosted Origin on loopback.
