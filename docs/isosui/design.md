# Editor and dockable workbench design

[中文](../../docs_cn/isosui/design_cn.md) · [First use](usage.md) · [TODO](todo.md)

**Target:** IsosUI `0.1.0` with IsOS `0.1.0` and EOS `0.2.0`. The current editor supports `0.1.0` graphs and registered `@v0.1` types with safe legacy `1.0.0` reads, type-specific node forms, node-set previews, frequency patterns derived from configured edge caps, independent EOS control/monitor/Vision/log panels, an EGIA core window, and the edge inspector described below. Everything identified as **target** still needs implementation. Product versions, graph versions, node IDs, HTTP routes and simulator socket versions are separate identities.

## Ownership and data flow

IsOS owns the saved graph, type catalog, package receipts, `/api/isos/v1/node-options`, validation, revisions, Apply, manager status and unified log cursor. EOS owns live adapter status, observation, control and admission. EGIA owns agent-stage state. IsosUI keeps only a draft graph, server revision, transient option results and browser-local panel geometry. It must never infer a verified package path, command authority or live status from the draft. Read the owner contracts in IsOS `interfaces/node-graph.md` and `interfaces/releases.md` and EOS `interfaces/hardware.md` and `interfaces/control.md`; this page defines their UI projection only. The [graph loading contract](interfaces/graph-loading.md) specifies snapshot and background status request ordering.

The target UI state is `{saved_revision, draft, validation, active_revision, catalog, options, readiness, panels}`. Edits update the draft and mark validation stale. `Check graph` asks IsOS to validate without writing. `Apply` sends the exact saved revision and draft; on a conflict, keep both the local draft and server revision visible for explicit reconciliation. The editor keeps additive fields that it does not edit and never rewrites saved bytes merely because it displayed a graph. IsOS's additive `read_only` and `diagnostics` graph response is authoritative: read-only disables editing, validation, Apply, scene changes, node-set preview, Run, Restart, and EOS control submission while leaving inspection, Refresh, logs, and emergency Stop available. When an older IsOS omits `read_only`, an unknown graph version or a node type missing from its catalog also forces read-only; the version or type diagnostic remains visible. A saved graph is never treated as an active control binding unless its revision matches EOS's active revision. UI version `0.1.0` does not assert graph `1.0.0` stability.

## Type-driven configuration and selector

The registered type supplies placement, a nonblank description, fields and typed ports. The instance supplies ID, label, description, settings, package pin and input references. An old type sidecar without `description` receives the IsOS compatibility fallback; the UI labels it as catalog fallback rather than inventing a device description. Every visible field has label, type, unit where relevant, purpose, default and validation/help text from its owning contract. Empty required values and invalid units are inline errors.

**Target node info card.** Pointer hover and keyboard focus open the same small, nonmodal card beside the pointer on hover, or beside the node on keyboard focus. It shows label, type ID, the registered type description and the instance description as separate rows, declared ports with type and unit help, and live status only if EOS supplied it for the active node. The card floats above neighboring nodes in a canvas portal, stays within the viewport, and does not cover the pointer's drag start or wire handles; entering it keeps the card open for reading. Focus moves into its content only on request, Escape closes it, and touch users open it from the node's info button. Missing old type descriptions are labeled as compatibility fallbacks. A draft node never gets fabricated live health.

The target selector descriptor on a setting identifies an IsOS option source; this release selects one stable value per setting. `POST /node-options` receives the current draft; the response groups options by node path and setting name. Every option has stable value, label, description, availability and an unavailable reason. The UI search matches label, stable value and description, with keyboard arrows, Enter, Escape, typeahead and a screen-reader count. The selected value is stored by stable ID; display labels never become graph values. Re-query when the package pin, dependent setting or draft graph changes. Ignore stale responses with a request generation counter. If the selected ID disappears or becomes unavailable, keep it in the form with a warning, and block Apply until the operator selects a valid option. The first concrete selectors are MuJoCo scene and device; the same mechanism later handles package assets such as model weights. Arbitrary filesystem entry is not a substitute for a verified registry option.

## Wire projection and editing

**Implemented edge inspector.** The current Graph inspector compares the source and destination's exact declared port type IDs and displays both IDLs, including payload field `x-unit` annotations. A missing catalog descriptor is shown as unavailable metadata, not as a rejected edge. After `Check graph`, the editor maps its four-segment wire target to IsOS's expanded diagnostic pointer and attaches `/inputs/<port>/<source-index>` only to that wire with its code, path and message; a port-wide diagnostic for a multi-source input stays in the full Diagnostics section. A rejected wire receives a visible stroke and accessible text. Editing, undoing, redoing or refreshing the draft clears that validation result and any route authority, so another QoS edit requires Check graph, and a late response for an older edit is ignored. The inspector labels this as a **draft check**. It shows IsOS deployment state separately and opens the EOS monitor for live node health; the Graph wire itself does not yet display a live per-node health badge. Exact type identity remains the edge compatibility rule: the UI does not convert payload units. The inspector now edits priority and an optional frequency cap only after a matching IsOS `Validate.edges` source pointer declares `routed:true`, `qos_eligible:true`, and `fixed:false`. General asset selectors remain later work; U03 supplies independent control/monitor/Vision/log panels.

An edge is the source reference attached to an input. Target optional `priority` is a signed integer from `-20` (highest) to `19` (lowest), default `0`; optional `frequency_hz` is finite and positive, absent for no edge cap. The producer port's `expected_rate_hz` remains a hint, never a saved edge cap. Render actual configured values first; where no edge cap exists, show `unlimited` and optionally the producer hint separately. For an old source reference, display priority `0` and `unlimited` without mutating the graph. Edit only the selected edge, preserve all unknown compatible fields, validate locally for immediate feedback and ask IsOS to validate before Apply.

Transport anchor shape, exact payload-type color, layer/group node marks, runtime fault outline and wire priority/frequency indicators remain distinct. Target line pattern expresses the configured cap; a solid line means no cap, not a measured high rate. A text label such as `nice 0 · ≤ 20 Hz` accompanies the line and appears in the inspector and accessible edge name. Use a consistent priority marker or stroke tier independent of color, with a legend and focus/hover details. The wire pattern now uses the saved edge cap; the producer `expected_rate_hz` appears only as a separate hint. Priority changes stroke width independently of color, and the accessible label carries nice and cap values. Design-only edges show a `design only` badge until a runtime route is confirmed, and do not imply active delivery.

## Primitive controls — implemented

**Current primitive controls.** The EOS control panel lists each active `eos.dispatcher.primitive_base` or `eos.dispatcher.primitive_manipulator` binding separately, even when two bindings use the same primitive name. Selection shows the binding's type/instance descriptions, the single target resolved from the active graph, declared primitive/version/mode, argument units and bounds, and EOS-reported target health. The Invoke action is disabled for a stale active revision, missing or ambiguous target, unavailable EOS, invalid arguments or unhealthy target. It obtains EOS monotonic time, builds the existing `primitive_typed` header/payload, and sends it through `/api/eos/v2/control`; EOS checks the active binding and Dispatcher admits any physical release. The selected Graph node shows `sending` after invocation, then the exact correlated `Completed`, `Failed`, `Cancelled`, `Rejected`, `InProgress` or `OutcomeUnknown` result. `InProgress` remains nonterminal; a later outcome requires the authorized result read through the bridge. A pulse is tied to a correlated response or runtime event, never to a design-only wire or a browser assumption of success. The panel keeps IsOS Stop and the command ID visible. The [R07 client design](design-browser-results.md) defines run/revision fencing, typed follow-up and unavailable states; the full primitive form is implemented in U04. EGIA's gRPC CapabilityService is a separate ingress to the same Dispatcher, not a browser API.

The R07 qualification first proved one operator-clicked, active `base.velocity` binding with a bounded `body_velocity` form, typed send, `InProgress` follow-up and IsOS Stop against a mock adapter; real MuJoCo movement remains closed until R06 stop qualification. U04 added one control for every supported active base and arm binding and the graph node information card; see [U04 design](design-primitive-control.md).

## Panels and page kinds

Home, Graph and configuration are **work pages**: dense, aligned, scannable rows, bounded scrolling and persistent status context. Overview or explanatory landing content is a **visual page** with more spacing and imagery. Both share existing SCSS theme tokens, Island-web typography and transparent or lightly translucent surfaces; solid fill is reserved for legibility. Desktop controls are approximately 28–30 px high and touch hit targets at least 44×44 px. All controls expose focus-visible, disabled and error states; status never depends on color alone.

Implemented U03 workspace panels (`control`, `monitor`, `vision`, `logs`) each have `{open, docked, collapsed, x, y, width, height}` in browser-local storage, keyed by UI layout version and robot ID. Dragging or resizing modifies only geometry. Persist locally per robot and version; on load, reject malformed data, clamp to viewport and restore a safe default. Docking preserves panel content and subscriptions. Closing Vision disconnects its stream; hiding log follow pauses polling; monitor polling is bounded and stops when inactive. A stale active revision or lost API connection disables commands and remains visible even when panels overlap. Focus order follows the last active panel; Esc exits resize/drag without changing the graph. At narrow widths, force a stacked layout with all critical status and Stop controls visible.

## First-use observability algorithm

On opening Home, fetch IsOS status for live readiness and the opt-in `view=current` log scope for history. Before any admitted run, pin the manager-session first package/Apply failure; after launch, pin the persisted deployment run's first ready or failure event before detail filters. While the anchor is pending, display waiting and no detail rows. Stop, PID loss, cleared active revision and manager restart do not replace the last-run scope. A log row presents timestamp, level, source, core, optional `node_path`, `event_code`, `run_id`, optional `correlation_id` and message when IsOS provides them. Browser-only errors remain separate from server provenance. Cursor polling follows IsOS's same-run rebase diagnostics, shows rotation gaps and a new-run boundary, and never concatenates unrelated runs. The [P07 log design](design-log-cursors.md) owns the detailed state machine; the first-use guide teaches package → graph → Apply → readiness → control → logs → stop in that order.
