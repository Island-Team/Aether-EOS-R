**R07 merged and mock-base qualified.** `EosWorkbench.tsx` mounts `PrimitiveBaseCard`, which renders one active base binding and owns the typed sender, correlated result reader and state model. Legacy movement controls are no longer rendered; U04 later expands the complete per-binding UI. The legacy controls cannot become an alternate movement route. The [EOS owner R07 contract](https://github.com/Island-Team/Island-eos/blob/refactor%28v2%29/runtime-main/docs/eos/interfaces/control.md#r07-authorized-browser-result) fixes the wire and errors; IsOS owns revision/run/Stop.

## Client and state boundary

`src/services/eos/primitive-command.ts` sends narrow `base.velocity` commands, and `src/services/eos/primitive-result.ts` performs guarded reads; both use the validated loopback origin and request options. The sender takes an active resolved binding, its one graph-edge target, active revision, checked `body_velocity` arguments, EOS monotonic time, positive sequence and fresh command ID; it produces exactly the public `primitive_typed` envelope, computes `payload_length_bytes` with `TextEncoder` over compact JSON, and rejects non-safe clock/deadline numbers. It never accepts a free-form target or private grant. The result client accepts only `{commandId, activeRevision}`, produces exactly the three public JSON keys `op`, `command_id`, `active_revision`, parses the six-status `DispatchResult`, verifies the returned command ID, and maps bounded transport/owner/protocol errors to a discriminated result. Both clients use one decoder so the initial send and follow-up have identical status semantics. Components use these services rather than calling `fetch` directly. A rejected HTTP or `ok:false` envelope is an error; it is never coerced to a `Rejected` command status. A service timeout or malformed success is unavailable, not `OutcomeUnknown`, because only EOS can assign that command status.

`src/components/isos/primitive-result-state.ts` supplies the pure transition model consumed by `PrimitiveBaseCard`. A record contains the captured IsOS `runId`, `activeRevision`, active binding path, generated `commandId`, last owner `DispatchResult` or null, browser phase (`sending`, `following`, `terminal`, `paused`, `unavailable`), last safe error and request generation. The only transition into `terminal` comes from a correlated EOS status in `Completed`, `Failed`, `Cancelled`, `Rejected` or `OutcomeUnknown`; `InProgress` remains `following` or `paused`. The model keeps `Failed` separate from `Rejected` and transport errors, preserves the command ID across errors, and never starts a second `primitive_typed` send after a timeout or uncertain result.

R07 renders one minimal active base binding card with its graph-resolved target and four bounded SI fields; the operator clicks Invoke. The qualified card remains restricted to the mock adapter while R06 gates MuJoCo movement. Before sending it resolves the exact active graph binding and target, checks `saved_revision === graph.revision === active_revision`, `run_id_state:known`, `state:running`, clean draft, EOS readiness and owner-reported target movement availability. It captures the run/revision/binding/ID once, obtains EOS monotonic time, rechecks the IsOS fence immediately before send, then submits once. The result state model re-reads IsOS `process-status` immediately before each follow-up and after a page becomes visible; it compares current `run_id` and revision with the captured values. An IsOS status error or `run_id_state:unavailable` pauses follow-up as unavailable. A stopped run, changed run or changed revision aborts the pending read and seals that record as old-run/unavailable. A browser request generation and `AbortController` prevent a late reply after selection, Stop, unmount or run change from updating the current card. A fresh command gets a fresh record even if the same binding is selected. The UI takes the active revision from IsOS, never from a draft or command response.

The result poll is one read at a time, with the 1-second initial delay, 10-second maximum error backoff, 60-second/12-attempt bound and hidden-tab pause in the UI contract. `InProgress` remains visible when the bound expires; manual Refresh rechecks IsOS before one read. A terminal status stops reads. If the first send response is lost, the UI may perform only this guarded result read using the generated ID, accepting `unknown command ID` as opaque unavailability. The service never retries `primitive_typed`. Vision keeps its separate read-only WebSocket and revision fence. The result card shows command ID, active revision, binding path, exact owner status or unavailable explanation and last update. It links to unfiltered current-run logs unless an EOS owner event supplies a valid matching `correlation_id`; then it may prefill that filter. It never assumes the command ID is a log correlation ID or uses a Graph edge animation as proof of release.

## Integration with the existing workbench

`EosWorkbench` refreshes IsOS status every five seconds for visible revision warnings; `PrimitiveBaseCard` obtains fresh process status before each result read, then checks it again after the read. The typed clients classify owner, transport and protocol errors while retaining the validated origin, CORS mode and no credentials. The command card stays mounted and shows unavailability when the bridge fails; background refresh does not clear its command record. The six statuses have English and Chinese text with `role=status` or `role=alert` as appropriate. `Failed`, `Rejected`, `OutcomeUnknown`, an opaque old ID, and bridge outage need distinct text; color alone cannot carry meaning. The R07 card calls IsOS `stopProcesses()` beside Invoke, independently of the EOS bridge, graph editability and result polling. It decodes the typed `{stopped,terminal}` reply and shows the run-matched Stop outcome; R06 owns physical stop receipt. The full active-binding list, rich typed argument forms, info card and floating panel layout remain U04/U03 work.

## Stop terminal display correction

The R07 live replay found that the EOS card read `result.state` from an IsOS Stop `{stopped,terminal}` reply and that the workbench stored the reply as `ProcessStatus`. The separate `stopProcesses()` service type now prevents that mixup. A shared runtime decoder validates the whole terminal record, its fixed reason codes and the captured run ID before displaying confirmation. Home, Graph and EOS show the same pending, confirmed, unknown, unconfirmed and unavailable meanings. The EOS card fences pending result reads on click; each Stop path reads fresh `/process-status` after the reply without replacing the Stop outcome when status refresh fails. Component tests cover EOS outage and stale revision, late result reads, unknown and transport outcomes; pure tests cover null, missing, malformed and mismatched terminal evidence. Full gate commands and output are recorded in ignored `logs/test/20261102-stop-terminal-display/`.

Independent review also required duplicate terminal process IDs to fail closed, a null terminal with nonempty `stopped` to remain unconfirmed, and explicit `IsosApiError` rejections to retain their owner identity. These cases have negative tests in the shared decoder and mounted EOS card; all three Stop entry points use the same failure projection.
