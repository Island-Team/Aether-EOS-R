# Build and run EI in IsOS

[中文](../../../docs_cn/ei/develop/build-and-run.md) · [Architecture](../design/architecture.md) · [Setup interface](../interfaces/isos-config.md) · [TODO](../todo.md)

**Current unified checkout (0.2.1 source, unreleased):** From `ei/`, run `uv sync --extra dev --extra vec --python 3.12`, `./bin/islandctl validate`, then `./bin/ei --no-tui` for standalone EI. EOS binaries and contracts live at the repository root; IsOS manager source is under `crates/isos/`, and IsosUI under `ui/`. Managed IsOS graph `0.2.0` has one `isos` core; IsOS projects its `ei_*` layers to `ei-config setup --json` using setup schema 2 and the selected source revision. The old `egia` command, setup role, configuration directory, and wire identities remain compatibility inputs. The dated qualifications below record the earlier separate-repository development state.

This guide follows the order a first-time operator encounters the system. **Current** standalone commands work in this checkout against a compatible externally running EOS gRPC service. The IsOS stage reader now recognizes the seven exact EGIA stage types and can generate the managed stage overlay; the selected end-to-end deployment remains a qualification gate in the 0.x TODO. Python remains the EGIA runtime for `0.1.0`.

## 1. Prepare the runtime

Install Python 3.12 and `uv`; use an EOS implementation of Gateway discovery and CapabilityService, plus a configured OpenAI-compatible model endpoint. From this repository, run `uv sync --python 3.12` and `./egia-build.sh`. `./bin/islandctl validate` checks the checkout's shared resources and configured launcher paths. The current README pins a development EOS commit for standalone compatibility; a public paired release needs a tagged EOS and a real-process compatibility test. The Rust EOS gRPC gateway is available on its selected gRPC endpoint; its HTTP control/catalog ports are separate.

## 2. Configure without leaking secrets

Copy `.env.example` to `.env` and set only the model binding's named `api_key_env`. Set `etc/egia/models.toml` to the actual model endpoint and keep distinct fast-controller and slow-reasoner bindings. Select the EOS connection in `etc/egia/profiles/<mode>.toml`; `etc/egia/modes.toml` selects the default mode. `etc/egia/egia.toml` controls listener, model selection, stage policy, and logging; `prompts.toml` and `safety/gate.toml` remain required. Validate before launch with `./bin/islandctl validate`, `uv run python scripts/print_prompt.py`, and, if the model endpoint is running, `uv run python scripts/test_model.py`.

For the **target managed path**, IsOS stores the authored `0.1.0` graph under its private config root, resolves exact package pins and EOS gRPC endpoint, seeds complete EGIA defaults, and writes revision-bound generated config to an immutable deployment revision directory. The graph stores stable IDs, not secrets or resolved executable/model/scene paths. IsOS invokes `egia-config setup --json` for identity, catalog, validate, and render; a missing `eos_gateway`, unsupported graph/type version, or unresolved model binding blocks Apply/Run with a field-level diagnostic. Existing `1.0.0` graphs remain readable and are migrated only through explicit revision-checked Apply.

**Current EGIA reader check:** Send `{"schema_version":1,"op":"identity","core":"egia"}` to `./bin/egia-config setup --json`. The reply lists graph envelopes `0.1.0` and `1.0.0`, the four legacy common design IDs, and seven exact `@v0.1` stage IDs. A complete new graph validates and renders `egia/stages.json`; a partial graph, conflicting EOS gateway, authored command route, or unknown type fails at its graph path. IsOS's merged A01 reader admits those exact stage IDs for Apply/Run. This local identity check does not launch EGIA or change saved graph bytes; use the [setup contract](../interfaces/isos-config.md) for its fixture and diagnostics.

**Current EGIA P05 reader check:** Query the same selected installation's `egia-config` identity and `egia --capabilities`; compare the advertised exact ID set and feature sets in the [reader contract](../interfaces/reader-features.md). For a checkout, run `printf '%s' '{"schema_version":1,"op":"identity","core":"egia"}' | ./bin/egia-config setup --json` and `./bin/egia --capabilities`. The runtime probe neither bootstraps a virtual environment nor starts EGIA. If the selected interpreter is missing, it exits `127`; install the environment or set `EGIA_PYTHON` to the intended interpreter. IsOS P05 will report an unsupported exact node or feature with its saved-graph path and selected reader; restore a verified compatible installation or correct the graph, then Apply. A successful probe alone does not establish EOS gRPC readiness.

## 3. Start in dependency order

For **current standalone** EGIA, start compatible EOS and the model service first, then run `./egia-launch.sh --no-tui` or `./bin/egia --no-tui --mode <mode>`. The `--etc` option selects a different EGIA config root; `--island-config` selects shared resources. The northbound listener defaults to `127.0.0.1:16060`. If EOS discovery or a required schema fails, treat EGIA as unavailable even if the TCP listener opened.

For the **target managed** deployment, run `isos version check`, `isos config validate <graph.json>`, `isos config apply <graph.json>`, then `isos run` or use IsosUI Save and Run. IsOS starts its workbench, resolves packages, starts EOS and its MuJoCo child, verifies EOS gRPC readiness, then launches EGIA with `EGIA_ETC=<generated-root> --mode isos --managed --no-tui --state-root <isos-data-root>/state/<deployment>`. The IsOS data root is `<ISOS_HOME>/data` when `ISOS_HOME` is set and `${XDG_DATA_HOME:-~/.local/share}/isos` otherwise. IsOS supplies this deployment-scoped mutable root across Run/Stop/Restart; EGIA owns its files under the `egia/` child. The root is separate from the graph and revision-bound generated configuration. IsOS owns restart and reverse-order stop. `isos deployment stop` stops the deployment while leaving the workbench available. An IsOS model service remains a separate service, shown with deployment status and logs rather than as an EGIA graph node.

**A02 managed control check:** IsOS also passes `EGIA_EOS_CONTROL_GRANT_FILE` as an absolute path to the run-scoped, mode-`0600` EGIA grant. Do not copy its bytes to a graph, log, or command line. The selected `egia/stages.json` must carry IsOS's saved graph revision as a lowercase 64-digit SHA-256. EGIA accepts EOS write readiness only when Discover, GetStatus, and ListCapabilities return the same `eos-active-revision` and `eos-projection-sha256`; the former must equal that selected overlay revision. If discovery is mixed, consistently describes a different graph, or the grant is unsafe, inspect the selected run and restart from IsOS after fixing its owner inputs. A lost Submit/Watch response is reconciled by GetOperation with the same ID and grant. If no matching terminal acknowledgement is found, treat the physical outcome as unknown and use the owner status/stop flow; never mint a new ID for the same movement.


**A03 recovery and local reset:** Each admitted primitive receives a validated operation ID, durably reserved before Submit. On restart EGIA queries only `GetOperation` with that ID; a missing receipt remains unresolved and blocks safety reset. The fleet latch is fsynced before emergency egress and survives EOS and EGIA restarts. After external EOS estop remediation, stop EGIA and use a same-UID local terminal: `./bin/egia safety reset --state-root <isos-data-root>/state/<deployment> --episode <episode-id> --graph-revision <selected-sha256>` for an IsOS-managed deployment. Replace `<isos-data-root>` with the active IsOS data root defined above and pass the exact containing state root used by that deployment, not its `egia/` child; a direct launch instead uses the root it was started with. The command requires the runtime to be stopped and the exact affected alias set; it writes one authorization. Start EGIA once: it consumes the authorization, performs two fresh complete selected-revision EOS checks for every persisted alias and robot identity, and clears the latch only if estop is false, status is safe, and no operation remains unresolved. Failed checks leave the latch engaged. There is no manager, HTTP or WebSocket reset route.

## 4. Read status and logs in causal order

Run `isos status --json` and open IsosUI's workbench log panel in the target integration. Read the first run in this order: package/version compatibility → graph/config revision → EOS child and gRPC readiness → EGIA discovery generation → EGIA ready → mission/proposal/gate/operation result → stop. Filter by `run_id`, then `correlation_id`, then `node_path`. A listener or process PID is evidence of process start, not proof that discovery and safety initialization succeeded. If an action is rejected, the gate event code and exact missing/stale binding are the starting point; do not retry blindly.

The [EGIA event contract](../interfaces/events.md) fixes the shared JSONL envelope and 24 allowed `egia` codes. IsOS passes a deployment `ISOS_RUN_ID=r...`; managed EGIA validates it before writing a shared record. A missing or malformed binding fails before an EGIA event; IsOS reports the selected child exit. Standalone EGIA mints a local `l...` ID. Managed stderr carries only sanitized JSONL; native stderr writes are discarded. The rotating private owner replay (32 MiB, five backups) is under the selected state root at `egia/egia.jsonl`; human diagnostics use EGIA's resolved log root. Direct source launches retain their existing `var/lib/egia` and `var/log/egia` defaults. Read `egia_ready` only after complete EOS discovery, model binding and safety initialization. A lost EOS Submit response may already represent admitted movement: follow `egia_operation_unknown` and `egia_recovery_required` by status/receipt lookup and reconciliation, never by replaying movement. A collector outage cannot block stop or replace the owner replay; repeated noncritical diagnostics are counted, while first failure and terminal events bypass suppression. The IsOS selected-child boundary replay remains a separate integration gate.

## 5. Recover and stop

On version mismatch, inspect `isos version check`, the saved graph version, type IDs, and exact package pins. On config failure, correct the field reported by `egia-config`; do not edit generated files. On EOS discovery failure, inspect the gRPC endpoint and EOS node status; EOS HTTP 16020/16021 is not gRPC. On model failure, check the named binding, secret environment variable, endpoint, and decision event. On gate rejection, inspect capability identity and safety policy before a new attempt. On emergency latch, use the authorized reset flow only after EOS and the scene are safe.

Stop the target deployment with `isos deployment stop` or Ctrl+C in the attached `isos run` terminal; use `isos stop` for the whole workbench. Standalone EGIA is stopped with its foreground terminal interrupt. A clean stop rejects new proposals, ends or cancels in-flight work according to EOS terminal operation state, checkpoints mission outcomes, closes link, and emits one terminal run event. Do not interpret a timeout, process exit, or socket closure as physical success.
