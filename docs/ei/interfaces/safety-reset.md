# EGIA local safety reset and operation recovery

[中文](../../../docs_cn/ei/interfaces/safety-reset.md) · [Events](events.md) · [First use](../develop/build-and-run.md)

EGIA owns the emergency latch and its durable operation checkpoints. No IsOS manager, HTTP, WebSocket, graph edge or model route can reset the latch. The only operator entry is `./bin/egia safety reset --state-root <island-state-root> --episode <episode-id> --graph-revision <selected-sha256>` on the same host and UID after EGIA has stopped and EOS estop has been remediated externally. The CLI requires an interactive terminal and the exact phrase `RESET EGIA SAFETY`. It holds the runtime's exclusive `safety.lock` and writes one authorization; it does not clear the latch itself. For an IsOS-managed deployment, substitute `<isos-data-root>/state/<deployment>` for `<island-state-root>`; use the exact containing root passed to EGIA at launch, not its `egia/` child.

## Owner-only state

Files live below `<island-state-root>/egia/safety/`; operation checkpoints live below `<island-state-root>/egia/operations/`. IsOS supplies the deployment-scoped containing root `<isos-data-root>/state/<deployment>` with `--state-root` for a selected `0.1.0` managed launch, and keeps that root across Run/Stop/Restart of the same deployment. Here `<isos-data-root>` is `<ISOS_HOME>/data` when `ISOS_HOME` is set; otherwise it is `${XDG_DATA_HOME:-~/.local/share}/isos`. EGIA owns the bytes beneath `egia/`; they are not graph fields or immutable generated configuration. Directories are mode `0700`, regular files mode `0600`, with same-directory temporary write, file fsync, atomic replace and directory fsync. Symlinks, wrong ownership, wrong mode, malformed JSON, oversized records and unknown schemas fail closed. A direct EGIA launch keeps its existing layout or explicit `--state-root` semantics.

| Field | Type / unit | Purpose and validation |
| --- | --- | --- |
| `schema` | exact string / none | `egia-safety-history-v1`, `egia-safety-latch-v1`, `egia-safety-reset-v1`, `egia-operations-history-v1`, `egia-operation-index-v1` or `egia-operation-v1`; unknown versions fail. |
| `identities` | object alias → EOS robot ID / none | Nonempty affected alias set, keys 1–64 `[A-Za-z0-9_-]`, robot ID string at most 128 bytes; empty ID means unknown and cannot pass reset. |
| `episode_id` | 32 lowercase hex characters / latch episode | New for each engagement; durable marker, latch and one-shot authorization must match exactly. |
| `graph_revision` | lowercase 64-digit SHA-256 / selected graph | Binds latch and authorization to the selected IsOS graph; standalone latch tests use the all-zero sentinel. Operation checkpoints retain the selected revision or the `standalone` literal. |
| `nonce` | 32 lowercase hex characters / none | One-shot reset request identity; consumed on next startup and never reused. |
| `reserved_count`, `sequence` | positive 64-bit integers / reservation order | Monotonic history count and unique one-based index sequence; the index set must be complete and contiguous. |
| `operation_id` | string / EOS idempotency key | 1–64 `[A-Za-z0-9_-]`; created or validated before gate egress, persisted before Submit. |
| `alias`, `primitive`, `device_id`, `mission_id` | strings / owner identities | Exact recovery target; `mission_id` may be null. Primitive and device strings are at most 128 bytes; alias and mission ID use the opaque ID grammar. |
| `eos_robot_id` | nonempty string / EOS identity | Captured before operation submission; recovery lookup requires the same complete EOS robot identity. |
| `state`, `outcome` | closed strings / none | Operation `pending` or `terminal`; terminal outcome is `succeeded`, `failed`, `cancelled` or `rejected` and requires a matching EOS receipt. |

On restart EGIA loads every pending operation and calls only EOS `GetOperation` with its saved ID. Missing, malformed, nonterminal or mismatched receipts remain unresolved; no new Submit may represent that old physical action. A corrupt checkpoint prevents normal startup rather than silently discarding uncertainty.

The owner process restart test keeps one stub EOS operation map, grant, selected revision and synthetic run ID across two Python interpreters. It reserves an operation before Submit, exits after the stub stores a terminal receipt but before EGIA settlement, then starts the production EGIA pending-checkpoint path in a new interpreter. Complete discovery precedes `GetOperation` on the saved ID; the checkpoint settles without a second Submit. Its missing-receipt case retains the pending ID and latch and refuses a later reset. This tests EGIA's owner process boundary; IsOS R06 currently stops a deployment after a selected EGIA child fault, so it does not establish supervised same-run child replacement.

The private test-only `A03_EVIDENCE_DIR` hook copies raw owner state after each worker has exited, at `positive-before`, `positive-after`, `negative-before`, `negative-after`, and `negative-refused`. Each fresh snapshot directory is mode `0700`; copied files and its deterministic hash/length/mode manifest are mode `0600`. The exact inventory is `operations-history.json`, the selected operation's `.index` and `.json`, and, only for the two later negative snapshots, `safety-history.json` and `safety-latch.json`. The `negative-after` copy happens before reset authorization. The hook rejects missing, symlinked, wrong-type, wrong-owner or wrong-mode source files and never copies `safety-reset.json`, grant bytes or unrelated owner state. With the environment variable unset it creates no evidence directory and has no runtime effect.

The reset request is consumed once. EGIA requires exact selected alias coverage and the persisted EOS robot ID for each alias, no unresolved operation, and two fresh complete EOS Discover/GetStatus/ListCapabilities generations matching the selected saved graph revision. Both checks require `Discover.robot.estop=false`, ready health and safe live status. Any failed check preserves the latch. A new EOS or EGIA process identity never authorizes unlatch by itself.

Durable `safety-history.json` records prior engagement and the active episode. A missing latch file after an engaged marker fails startup closed. `operations-history.json` retains a monotonic `reserved_count`; it precedes each ID `.index` with its unique one-based `sequence` and payload. Indexes remain after terminal settlement. A missing checkpoint or index fails startup even when other operations remain. A terminal checkpoint cannot be rewritten. One-shot authorization is consumed immediately after the runtime lock, before config, discovery or mission checkpoint reads, even when that startup fails early. Managed launches restore valid mission checkpoints or fail closed even with `mission_preload=false`; prior incomplete work is never cleared.

Read `episode_id` from the owner-only `safety-history.json` and obtain the current selected revision from the IsOS applied graph before invoking the local reset CLI. A changed revision or a new latch episode requires a new operator authorization; neither reuses the old request.
