## Milestone delivery cycle (development agents)

Use this cycle for **one M1–M5 milestone at a time**. It directs contributors and review agents; it does not define a deployed node, WorkflowService, or ActionList. Repeat the design-to-review steps for each substantial slice within a milestone.

1. **Plan with agents.** Give planning agents distinct owner or boundary questions. Have them inspect current code, owning contracts, dependencies and the milestone row above. Reconcile their findings into an ordered slice plan with scope, non-goals, responsible owners, compatibility risks and the row's exit evidence. Record the slice plan and resolved decisions in the detailed TODO or linked owner design before implementation.
2. **Design the contract and first use.** Each owner updates its authoritative `interfaces/` contract, relevant design and algorithm pages, fixtures, and English/Chinese usage steps. State current behavior separately from the target. Follow setup → Apply → readiness → control → causal logs → stop order in operator guidance.
3. **Check the design independently.** An agent who did not author each changed design compares it with its owner contract, schemas, current consumers and the adjacent layer data flow. Check version compatibility, field validation, failure, restart and safe stop. Record findings and dispositions in the design or PR; resolve findings and request a recheck before calling the design ready.
4. **Implement in slices.** Assign each slice to an implementing agent on a focused `refactor(v2)/<topic>` branch under the repository agent guide. Implement against the reviewed contract; keep behavior-changing code, contract updates and focused unit/mock/negative tests together in each implementation PR. A docs-only planning PR may precede implementation, but does not complete its TODO box.
5. **Run integrated evidence.** After focused checks, exercise the milestone's affected installed boundary with a stub or simulator as needed; M5 runs the full IsOS → EOS → MuJoCo → EGIA → IsosUI path. Include failure, restart and safe stop where applicable. Preserve complete commands and output under `logs/test/<run-id>/`; compare the actual result with the milestone exit row and the first-use log order.
6. **Review and merge.** Have an independent agent review code, contracts, tests and the integration evidence; fix findings and rerun affected checks. Review the PR, squash merge to the integration branch, confirm the remote target, and remove only the completed topic branch/worktree after preserving logs.
7. **Close the milestone.** Replay the milestone's applicable bilingual first-use steps; M5 replays the complete guide from a clean IsOS home. Mark only verified TODO items complete, update current-versus-planned labels and the evidence summary, and close the milestone only when every exit condition in its row passes. An unmet condition returns to the relevant design or implementation step.

## Operator-visible first-use order

The qualification run reads like the operator guide: install builds and exact package → choose nodes and assets → Validate and Apply → inspect the manager-session first package/Apply failure if launch has not begun → launch and confirm live status → inspect a node and invoke one active primitive binding → read the deployment run's first ready or failure event, then filter by correlation ID → stop → upgrade by explicit migration. Status is authoritative live state; a log startup line is evidence of a transition. One successful readiness event per module and later state-change events keep the first-use log readable.
