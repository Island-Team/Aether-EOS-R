## Ownership and graph identity

IsOS (Island OS) is the product and the only graph core in newly authored graph `0.2.0`. EI (Embodied Intelligence, formerly EGIA) and EOS (Embodied OS) are domains within that core, not separate graph cores. IsOS retains saved-graph, package, process and log authority. EI owns cognition, decision and its safety gate. EOS owns hardware adapters, the dispatcher, command outcomes and the direct MuJoCo child. IsosUI presents the selected graph and live owner state. The processes may remain separate, and a graph path does not replace an explicit transport or grant.

The address hierarchy remains `core → layer → group → node`. The new core key is `isos`. Existing IsOS manager layers retain their names. An EOS layer `<layer>` becomes `eos_<layer>`; an EGIA layer `<layer>` becomes `ei_<layer>`. Browser input and display nodes use the existing `ui` layer. Groups and instance IDs are retained when unique within their target group. New registered node type IDs use `isos.<layer>.<name>@v0.2`. The owning interface pages define every new type's settings, ports and validation; this design does not duplicate payload contracts.

The public product version is `0.2.1`; the new graph format is `0.2.0` and new node type suffix is `@v0.2`. Existing HTTP routes, protobuf identities, package descriptors, simulator socket and MuJoCo package version retain their independently documented identities unless an owner contract introduces an explicitly versioned replacement. In particular, `island/mujoco-sim@0.1.1` remains an external, verified package. A verified legacy sidecar may supply a mapped new node type only through an explicit IsOS-owned compatibility adapter that preserves its exact package receipt; spelling a new type ID in a graph does not create executable authority.

## Atomic migration

IsOS reads supported `0.1.0` and legacy `1.0.0` graphs without changing their saved bytes. A `0.1.0` graph is read-only until an operator requests migration. The migration constructs a candidate `0.2.0` graph in memory, moves all supported `isos`, `eos`, `egia` and `isosui` nodes into the single `isos` core, rewrites known type IDs, node paths, references, input edges, bindings and process dependencies, and validates the complete candidate against the selected registered catalog. Unknown types, duplicate destination paths, ambiguous aliases and unsupported cross-process transports fail with a precise source path and leave the saved graph and active revision unchanged. IsOS writes the candidate and generated EI/EOS projections atomically only after complete validation and revision comparison. It retains the original graph bytes and revision for audit and rollback.

IsOS projects the admitted EOS layers to EOS and EI layers to EI under the same saved revision. Each process validates its projection and selected package bytes before readiness. EI safety remains the only EI proposal egress; EOS Dispatcher remains the only actuator admission route. A cross-process edge needs a declared transport even though both endpoints now share a graph core. On Stop, admission closes and EOS stops admitted actuators before its simulator child is terminated; IsOS then reaps dependent processes in order.

## Repository and publication boundary

The private integration repository is `Island-Team/isos-p`, renamed from `Island-eos`; the public source repository is `Island-Team/isos`, renamed from `Aether-EOS-R` after the former public `isos` vacates the name. The private repository retains imported histories and source-to-imported commit receipts. The public repository receives a reviewed source snapshot with independent history. IsOS, EOS, EI and IsosUI source versions become `0.2.1`, but `v0.2.1` is not tagged or published in this migration. Historical IsOS and IsosUI `v0.1.0` assets and checksums are mirrored as legacy preservation artifacts before their old repositories are deleted. Their old GitHub URLs are historical coordinates, not future download endpoints.

The completion gate is a clean-home first-use replay from the combined tree: verify the external MuJoCo package; migrate and Apply; launch EI and EOS; observe readiness, camera data and one admitted control result; inject failure and restart; then confirm Stop and child reap. Record full format, lint, unit, integration and bilingual documentation-link output under ignored `logs/test/<run-id>/`. Draft 0.2.1 release notes may be prepared, but no 0.2.1 tag, release or product assets are published.
