# 代码与文档规范

**规范版本：1.3.1**

本共享规范适用于源代码、接口和手写文档。组件指南可以为自身范围增加更严格的规则。公开线协议身份及兼容性由所属契约决定。规范版本独立于产品、包和线协议版本。英文和中文副本须同步修改。兼容性新增提升次版本，修正提升修订版本，删除或替换既有规则提升主版本。

## 源代码与模块归属

每个模块只承担一种职责，并有明确归属。分离准入与校验、领域决策、运行时状态、传输和呈现，使每个字段只有一种权威含义。跨进程或组件依赖公开契约，不依赖其他组件的私有实现。函数保持专注。将非平凡算法和故障处理置于可测试的接口之后；简单包装无需人为创建测试模块。

采用领域名称。文件名尽量只用一个词；必要时使用既有的简短缩写。内部名称变化时保留稳定的公开命令和线协议名称。公开模块集合或重要子系统需要概览，说明归属、数据流并链接专题页面；专题页面链接回概览。先解释数据来源、准入、转换、生命周期、可观测故障和验证，再列源文件。

## 行内文档

注释和文档字符串使用英语，并在相关代码旁说明不显然的约束、单位、归属、并发、安全或意外故障。不要复述清晰的名称或操作。公开 C/C++ 接口在调用者需要时说明所有权、阻塞和错误行为。行为变化时更新注释；详细设计放在文档中。

## 文档结构与写作

手写文档置于所属产品或组件的 `docs/` 中；`docs_cn/` 镜像相同阅读路径，译文文件名在扩展名前加 `_cn`。两种语言保持标题、字段含义、示例和相对链接一致。每个文档树有简短的入口 README。按读者任务组织页面：`usage/` 用于设置和操作，`debug/` 用于运行故障，`develop/` 用于扩展工作，`interfaces/` 用于契约，`design/` 用于架构，适用时以 `layers/` 收录类型目录，以 `legacy/` 导航历史兼容内容，以 `maintenance/` 记录发布和工作跟踪。不要手工修改生成的参考文档。

像写文章一样写文档：术语首次使用前先介绍，每段只讲一个主题，独立打开的页面无需依赖上级页面也能理解。Markdown 正文段落在源文件中保持单个物理行。序列和清单用项目符号，确有比较价值时使用表格，精确语法重要时使用简短代码示例。设计、层级和使用页面不重复定义载荷。未来行为标记为 **目标设计——尚未实现**，并链接可执行的 TODO。已实现行为使用现在时。

首次使用指南按操作员的实际顺序组织：前置条件、包发现与验证、配置与校验、Apply 或等价准入、启动与就绪、运行监控、日志与调试、停止、升级与恢复。日志指南先说明如何找到当前运行及其第一条就绪或失败事件。

## 接口契约

所有手写 HTTP、WebSocket、RPC、IPC、插件、技能、硬件或数据契约，都放在所属组件的 `interfaces/` 目录及其中文镜像。说明调用者和所有者、传输或调用方式、认证与准入、输入输出、生命周期与超时、错误和兼容性。每个公开字段说明类型、单位（或“—”）、用途、缺省或缺失行为、校验和兼容性规则。使用实际线协议名称给出简短有效的请求、成功和错误示例。示例与模式、处理器和测试保持同步。设计页面说明原因并链接唯一的所属契约。

REST API 按 API 根路径之后的第一个路径段，每个领域独立成页。每页按易读顺序覆盖 **Overview**、**Authentication**、**Interfaces** 和 **Routes**。每个端点使用 `## METHOD /path` 标题，展示允许的调用者、请求、成功结果，以及适用的准确校验、授权、未找到和服务故障代码。说明 JSON 信封及例外、媒体类型、枚举字面值、边界、ID 格式和时间戳格式。若共享认证细节重复较多，集中于一个认证页面。端点载荷保留在所属领域页面。客户端映射写在自身设计页面，不在 JSON 示例中引入替代线协议名。

兼容变更须保留既有字段编号和名称；增加可选字段时说明默认值，并让新读取器接受旧数据。破坏性变更需要新的契约身份和迁移指南。产品版本低于 1.0.0 不表示各线协议具有相同稳定性。

## 代码风格与工具

仓库配置是格式、lint、缩进和类型检查的权威来源。编辑器应使用该配置；不要求专有编辑器设置目录。除权威语言格式化工具另有要求外，使用两个空格且不用制表符。提交前运行仓库规定的格式化、lint 和测试。若机械格式化会掩盖行为变更，单独提交格式化。不要提交日志、构建输出、缓存、凭据或机器专有文件。

Rust 遵循官方 Rust 风格指南，所有目标使用仓库根目录 `rustfmt.toml`。不要增加 crate 局部格式覆盖。运行 `cargo fmt --all`，以 `cargo fmt --all -- --check` 验证，并运行 Clippy 及相关测试。单元测试放在实现附近，集成测试放在包的 `tests/` 目录。使用结构化日志，避免泄露秘密，传播错误时提供上下文，避免在异步上下文中执行阻塞操作。

TypeScript 使用严格类型、仓库 lint 和格式化工具，JSX 使用 `.tsx`，逻辑使用 `.ts`。导出函数尽量明确返回类型，控件使用无障碍语义。集中管理网络访问。保留共享视觉变量、响应式布局、键盘访问和至少 44×44 px 的触摸目标。Python 使用仓库指定版本（否则 3.12），公开函数标注类型，并在共享配置中设置类型检查模式。C/C++ 使用仓库指定的标准和根目录格式化配置；公开头文件与私有辅助实现分开，并在 CMake 中明确每个编译模块的依赖。

## 语言与接口实现细则

Rust 应用可用 `anyhow` 表示应用错误，库可用 `thiserror` 表示类型化错误；优先返回 `Result` 而非 panic，传播错误时添加上下文。仓库采用 Tokio 时，异步 Rust 使用 `tokio`，阻塞工作移到阻塞线程。测试名写成句子，例如 `test_<what>_<condition>_<expected>()`。单元测试使用 mock 或 stub 检验边界，不依赖真实硬件。

TypeScript 项目使用配置的 ESLint 和 Prettier 规则。对象契约优先使用 interface，有限选项在准确表达线协议时使用字面量联合。React 项目使用函数组件。组件和入口文件使用 `PascalCase.tsx`，辅助文件使用简短的小写名称。适当就近放置样式。分号与引号遵循仓库规则。在服务层集中 HTTP 和 WebSocket 代码。除非部署文档明确允许运行时外部资源，否则前端构建应自包含；客户端路由需要宿主回退到 `index.html`。

前端控件使用语义化区域；操作用按钮，导航用链接。每个控件有可见文本或无障碍名称。颜色、字体、间距、状态和焦点使用共享主题变量，并保持可读对比度。桌面控件遵循产品的紧凑高度，通常为 28–30 px；触摸目标至少 44×44 px。工作页面重视易扫描的行、可见状态、有界滚动和键盘访问。解释性页面可以使用更多空间。浮动、停靠和窄屏布局仍须显示关键停止和故障状态。页面外壳使用响应式网格，组件内部使用弹性布局。

C 和 C++ 模块至少采用 C++17，除非仓库指定更新版本。CMake 明确设置语言标准，避免未记录的编译器扩展。适用时遵循配置的 Google 风格格式化和 100 列目标。每个编译的 C/C++ 模块有自己的 `CMakeLists.txt`，声明源文件、公开/私有包含路径和链接依赖；生成接口通过辅助目标连接，不直接引用生成路径。根 CMake 按依赖顺序加入模块。公开 ABI 和类头文件放在 `include/`；私有辅助实现留在模块或 `detail/`，不得从模块外包含。简短 Doxygen 可用于调用方需要的所有权、单位、线程安全、阻塞和错误；不手工修改生成的 Doxygen。

Python 遵循已配置的 Google 风格指南；仓库采用本规范时使用两个空格缩进。非显然契约使用简短文档字符串，公开函数使用类型标注。项目使用 Python 时，至少在 `pyproject.toml` 中配置 standard 类型检查。用英文注释解释非显然的数值、并发、硬件和故障假设，不注释显而易见的赋值。

新增配置时，在同一变更中更新结构或模式、受版本控制的示例、默认值、有效范围以及所属接口或使用页面。示例和日志不得包含秘密。

## 模块验证与交付

模块专题文档在适用时说明稳定输入输出、类型、归属、单位、时序、调用方职责、兼容性、状态转移、顺序、依赖降级、已知限制和明确不支持的场景。解释算法选择和不变量，不复制源码签名。适用时链接生成的 API 细节。可行时让仿真、回放、mock、硬件和在线服务位于同一公开接口之后。最近的概览定义共享边界和端到端数据流；专题页面记录条件细节。

新增或重设计模块按以下顺序交付：定义问题、成功条件、约束和非目标；研究依赖及故障模式；定义公开接口；更新概览、专题设计和契约；构建最小可用实现；按需加入单元和集成证据；完成格式化、lint、测试和双语文档；提交连贯的变更。小改动更新受影响的契约和设计，实现并测试变化行为，仅更新相关文档。记录可复现命令及通过或失败结果，不粘贴冗长日志。

单元测试可按语言放在局部 `tests/` 目录或行内测试模块。每个测试文件针对一个单元，输入 mock 或 stub，并断言预期输出。跨模块 smoke 测试靠近组合进程。说明测试方法：smoke、mock 单元、stub 集成、仿真、回放、基准、硬件在环或人工验收。大型模块、非显然算法以及手工排查代价高的行为须有测试。验证故障和停止行为以及成功行为。

## 事件与发布记录

机器可读事件使用脱敏的 UTF-8 JSON Lines。共享信封包含 RFC3339 UTC `timestamp`、`level`（`trace`、`debug`、`info`、`warn` 或 `error`）、`source`、所属 `core` 或服务、可选规范 `node_path`、稳定的 `event_code`、存在运行时的 `run_id`、可选 `correlation_id`、供人阅读的 `message` 和有界 `fields`。发出有信息量的启动或就绪事件，随后记录状态变化和可操作故障。部署所有者汇聚来源并定义按来源的文件、轮转和游标读取；每个组件仍是结构化事件生产者。

图格式、节点类型 ID、protobuf 命名空间、HTTP 路由、软件包和 socket 协议分别版本化。发布说明按固定短顺序记录版本与日期、操作员可见变化、兼容与迁移、安装或升级、已知限制和验证。发行版本变化不自动改变其他契约身份。不得从低于 1.0 的产品版本推断稳定性。

## 审查与发布

共享分支前确认格式化、lint、聚焦和集成测试、带上下文的错误传播、有用的日志、最新接口及配置文档、译文对应，以及 diff 中没有秘密或生成产物。机械格式化若会妨碍行为审查，应与行为变更分开。仓库的发布流程决定是否推送分支或通过 PR 审查；使用 PR 时说明行为、验证和文档，使分支跟上目标，并遵循仓库的合并策略。未经团队同意不得强推共享分支。

## 测试与可观测性

重要模块逻辑添加使用 mock 的单元测试；边界需要时添加 stub 集成、仿真、回放或硬件测试。按场景测试成功、拒绝、依赖故障、停止和恢复。在模块文档中写明测试方法及可复现命令。基准使用固定负载，在声称性能目标前报告环境、吞吐量、中位数和 p99。

发出经过脱敏的结构化事件，使用稳定代码和有界字段。包含时间戳、级别、来源、所属 core 或服务，以及适用的运行或关联身份和可操作消息。记录启动、重要状态变化和故障；避免重复的成功噪声。不得记录秘密、原始媒体、提示词、原始参数或无限大的提供方载荷。所属接口说明日志保留和游标恢复。

## 变更与发布流程

从当前目标分支创建主题分支；不要直接在集成分支开发。保持提交聚焦，并使用 `feat:`、`fix:`、`docs:`、`refactor:`、`test:` 或 `chore:` 前缀。行为变化时同步更新代码、契约、测试和中英文文档。发布前审查 diff 和本地检查。仅在请求发布时遵循仓库的审查与合并流程。

发布说明包括版本和日期、操作员可见变化、兼容性与迁移、安装或升级步骤、已知限制以及可复现验证。明确标识候选项和目标设计。历史发布标签不可变。
